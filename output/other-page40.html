Stop Treating CSS Container Queries Like Traditional Media Queries

📅 Sep 16, 2026  |  Category: Other  |  Read Source →

<p>To be completely honest with you, I missed the news when CSS Container Queries first shipped. And when I finally heard about it, my very first thought was, <em>“Why exactly do I need this when media queries already exist?”</em></p> <p>I’m not proud of that reaction, knowing what I know now, but it was comforting to know that I wasn’t alone. In fact, there are legions of us out there.</p> <p>What baffles me is that container queries aren’t a new feature, as it currently sits at around <a href="https://caniuse.com/css-container-queries">94% browser support</a>. And yet, very few people are actually using it. According to the <a href="https://2025.stateofcss.com/en-US/features/">State of CSS</a> survey, 86% of developers are aware of container queries, but only 41.4% actually use them. Surveys can be biased and not completely representative of our entire field, but this one is certainly the best indicator we’ve got.</p> <p><a href="http://youtu.be/4IBXIFe2CKA?si=2g3869tmp0yLOYz_&amp;t=297">Kevin Powell also talked about this</a> at SmashingConf Amsterdam 2026: <strong>Container Queries adoption has been terrible.</strong> And that is so strange to me, knowing that the ability for components to adapt to the size of their outer container <a href="https://css-tricks.com/2019-css-wishlist/">has been at the top of so many CSS wishlists</a> over the years.</p> <p>I’m not particularly interested in how many people are using container queries as much as in <em>how</em> they are using them. I can’t account for everyone, but from what I’ve seen — including in my own early attempts — many of us are using them <em>wrong</em>.</p> <p>The bottom line is that incorrect use comes down to the same impression I had when learning about them: <strong>they absolutely look just like media queries at first glance</strong>. And since they look similar, it’s easy to assume they serve similar purposes and work the same way.</p> <p>They don’t.</p> <p><strong>Note</strong>: I should state up front that what I’m focusing on in this article is using container <em>size</em> queries, i.e., a responsive design technique for responding to the size of a particular container. There are also container <em>style</em> queries that respond to a container’s computed styles (and are experimental at the time of this writing). You can catch up on those in <a href="https://www.smashingmagazine.com/2024/06/what-are-css-container-style-queries-good-for/">Juan Diego’s piece here on Smashing Magazine</a> where he examines their possible use cases.</p> Media Queries Look Outward <p>The viewport is a proxy. It always has been. Media queries are what gave us the illusion that screen width alone is responsible for how responsive apps adapt to their environment.</p> <p>Ask yourself this: When you write <code>@media</code>, what are you asking the browser?</p> <pre><code>@media (min-width: 1024px) { .card { display: flex; } </code></pre> <p>I, like most developers, am asking the browser: <em>How wide is the screen right now?</em> That’s it.</p> <p>Media queries answer that beautifully, but what happens when this <code>.card</code> component is placed in a grid cell that’s <code>300px</code> wide on a <code>1920px</code> desktop screen?</p> <p>The media query doesn’t care; it does its job. The viewport is still <code>1920px</code>, so <code>min-width: 1024px</code> fires and the matched query styles are applied, even though the card only has <code>300px</code> of space to work with. Eventually, everything in the card deforms, overflows, or cramps up.</p> <blockquote>“Media queries are dumb. Not dumb in terms of the concept, but dumb in that they don’t know very much. In fact, most people assume that they know more than they do.”<br /><br />— <a href="https://css-tricks.com/smart-layouts-with-container-queries/#:~:text=Because%20of%20how,than%20they%20do.">Kevin Powell</a></blockquote> <p>It’s common to think of responsive design purely as a system for updating complete page layouts, like going from two columns on a large screen to a single column on a small screen.</p> Container Queries Look Inward <p>Container queries are smarter than that. They make responsive layouts more reliant on what’s happening <strong>inside</strong> a component rather than on the outer context that has no insight into a component’s contents. It is more like: <em>“How much space is available for me in this specific spot, right now?”</em></p> <p>Here is the same card code example we looked at in the last section, but with a container query:</p> <pre><code>.card-wrapper { container-name: card; container-type: inline-size; } @container card (min-width: 450px) { .card { display: flex; flex-direction: row; } } </code></pre> <p>This changes everything. The card isn’t influenced by the viewport; its only concern is whether the <code>.card</code> component’s parent wrapper has at least <code>450px</code> of inline (i.e., horizontal in a left-to-right writing mode) space. If that condition is true, the component goes horizontal; if not, it goes to its default <code>block</code> display.</p> <p><img src="https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/1-normal-state-vs-wrapped-state.jpg" /></p> <p>The logic works like this:</p> <ol> <li>When there’s enough room, both items (<code>.flex-item</code>) sit side-by-side, each exactly half the parent container’s width.</li> <li>When there is limited space, the second item wraps to the next line.</li> <li>Because <code>flex-grow</code> is active on each item, the wrapped items stretch to fill most of the parent’s width.</li> <li>If the item is a container itself, it detects the sudden width expansion and fires.</li> </ol> <pre><code>/* The flex parent */ .flex-layout { display: flex; flex-wrap: wrap; } /* Register a flex item as a container */ .flex-item { container-type: inline-size; flex: 1 1 390px; /* Grow to fill space, wrap at 390px */ } /* Default Card Styles (narrow / side-by-side) */ .card { display: flex; flex-direction: column; background: #f4f4f4; } /* Once there's enough room for a full row */ @container (min-width: 600px) { .card { flex-direction: row; align-items: center; background: #e2f0d9; } } </code></pre> <p>This works. As the parent size shrinks and the cards wrap to two lines, the card item expands, the container query fires, and applies the necessary styles. </p> <p><img src="https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/2-reusable-component.jpg" /></p> Conclusion <p>At the end of the day, the core reason why container queries look incredibly similar to media queries is simply familiarity. They’re not exactly “new”, but they are way less understood and adopted than media queries. But media queries have plenty of their own limitations; otherwise, we wouldn’t need container queries to fill those gaps.</p> <p>What we have is a more effective feature for detecting when a specific component’s context changes and a means for adjusting styles based on its content, as it should be when that component can exist in multiple contexts.</p>
