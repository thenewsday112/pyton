Compare offers in net-worth-per-hour, not headline salary

📅 Oct 31, 2026  |  Category: Business  |  Read Source →

<p>Compare offers in net-worth-per-hour, not headline salary</p> <p>A larger number on an offer letter often hides a worse deal. The human mind anchors on base pay because it is the most visible figure, but compensation is a bundle of conflicting variables. </p> <p>Do the arithmetic on paper, because the gut always loses to the printer. Start by converting every offer into an hourly rate based on expected actual hours worked, not the forty hours listed in the handbook. If a role requires ten hours of uncompensated overtime each week, a ten percent salary bump disappears instantly. A longer week can eat a ten percent premium in a year through sheer time dilution.</p> <p>Next, examine the mechanics of the non-cash components. Bonus structures tied to company metrics that never trigger are worth zero. Equity with a four-year cliff and no secondary market is a lottery ticket, not income. Calculate the real cost of the commute, both in fuel and in dead hours that could be spent building equity of your own.</p> <p>Ask the boring benefits questions early, because they are checks, not fights. Find out the exact health insurance deductible, the employer match on retirement accounts, and the policy on hardware replacement. These details shift your annual take-home pay by thousands of dollars without showing up in the headline figure. </p> <p>When you strip away the branding and the recruiter's enthusiasm, an offer is simply a contract to trade specific units of time and skill for specific units of capital. Run the math before you sign.</p>

OpenNVR 0.1.10: running an open-source NVR's AI on the Qualcomm Hexagon NPU

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

<p>OpenNVR is an open-source (AGPL) NVR that records and streams from any ONVIF or RTSP camera and runs the AI model you choose behind them: YOLO detection, pose, face recognition, plate OCR, open-vocabulary detection, and a vision-language agent that can look at a scene and reason about it. It runs on hardware you own, air-gapped if you need, with every inference audited.</p> <p>Version 0.1.10 is the first release with hardware acceleration flavours, and this post is about the one I have numbers for: Qualcomm's Hexagon NPU.</p> <h2> The board </h2> <p>Arduino Ventuno Q: Qualcomm Dragonwing IQ-8275 (QCS8275), eight ARM cores, a Hexagon NPU, Ubuntu 24.04. Small, fanless, the kind of thing that sits behind a few cameras in a shop or a plant.</p> <h2> The numbers </h2> <p>All measured on that board with the published container images. Full windows, settle times and caveats are in the <a href="https://github.com/open-nvr/open-nvr/blob/main/bench/ventuno-q-benchmark-2026-10-30.md" rel="noopener noreferrer">benchmark doc</a>.</p> <p>Tier-0 detector (YOLO, one frame):</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Device</th> <th>ms per frame</th> </tr> </thead> <tbody> <tr> <td>CPU, 8 threads</td> <td>164</td> </tr> <tr> <td>Hexagon NPU, fp16</td> <td>8.6</td> </tr> </tbody> </table></div> <p>In the full stack (streams, decode, tracking, the API, all on the same box):</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Device</th> <th>Cameras at 2 fps, no drops</th> <th>Host idle</th> </tr> </thead> <tbody> <tr> <td>CPU</td> <td>4 (10 cameras drop half their frames)</td> <td>~4 %</td> </tr> <tr> <td>NPU</td> <td>16, 0 dropped</td> <td>46 %</td> </tr> </tbody> </table></div> <p>The adapters that sit behind the detector, end-to-end on one 1080p JPEG:</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Adapter</th> <th>CPU</th> <th>NPU</th> </tr> </thead> <tbody> <tr> <td>YOLO</td> <td>141 ms</td> <td>77 ms</td> </tr> <tr> <td>Pose</td> <td>108 ms</td> <td>64 ms</td> </tr> <tr> <td>Package detection</td> <td>100 ms</td> <td>60 ms</td> </tr> <tr> <td>Face recognition (InsightFace)</td> <td>443 ms</td> <td>62 ms</td> </tr> <tr> <td>Plate OCR</td> <td>248 ms</td> <td>62 ms</td> </tr> </tbody> </table></div> <p>The NPU's own share of an adapter call is about 9 ms. The rest is JPEG decode and preprocessing on a busy CPU, so the adapter path is now bounded by image handling, not inference.</p> <h2> How it works </h2> <p>Everything goes through ONNX Runtime's QNN execution provider, shipped as a plugin wheel (<code>onnxruntime-qnn</code>). There is no Qualcomm SDK to install on the host. The <code>-qualcomm</code> container gets the DSP device node, the DMA heap, and two host libraries bind-mounted, and that is it.<br /> </p> <div class="highlight js-code-highlight"> <pre class="highlight shell"><code>git clone https://github.com/open-nvr/open-nvr.git <span class="o">&amp;&amp;</span> <span class="nb">cd </span>open-nvr ./start.sh <span class="c"># OPENNVR_ACCEL=auto detects /dev/fastrpc-cdsp and picks the qualcomm flavour</span> </code></pre> </div> <p><code>OPENNVR_ACCEL=cpu|intel|qualcomm</code> overrides the probe. A box with only a CPU gets exactly the images it got before.</p> <p>Compiled graphs are cached, so the second start skips the ~6 s compile. The pipeline reports which provider ONNX Runtime really ran on, and a request for an accelerator that silently fell back to CPU shows up as <code>requested != effective</code> in the metrics instead of being hidden.</p> <h2> Things that cost a day each </h2> <ul> <li>A plugin execution provider named in the <code>providers=</code> list is silently ignored. It has to be attached by device with <code>add_provider_for_devices</code>.</li> <li> <code>python:slim</code> lacks <code>libatomic1</code>. <p>Most Transformer explainers start with the famous diagram from "Attention Is All You Need" and lose half their readers at the first box. As a developer, I found it easier to learn the architecture by answering the five questions I kept asking myself, and by writing the core operation in code.</p> <h3> 1. What problem was the Transformer actually solving? </h3> <p>RNNs and LSTMs read a sentence one token at a time, like a message passed down a line of people. That makes long-range relationships fragile and training hard to parallelise. The Transformer replaced the chain with attention: every token can look directly at every other token in one step. Think of it as moving from a relay race to a meeting room where everyone can hear everyone.</p> <h3> 2. What are Q, K and V, really? </h3> <p>Each token is projected into three vectors by learned weight matrices:</p> <ul> <li> <strong>Query</strong>: what this token is looking for</li> <li> <strong>Key</strong>: what this token offers</li> <li> <strong>Value</strong>: the information it passes on if it turns out to be relevant</li> </ul> <p>Compare queries with keys, turn the scores into weights, and use the weights to mix values. That is the whole idea.</p> <h3> 3. Run It Twice, Charge Once: Idempotency Keys in n8n

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

<p><em>This is part of my build-in-public series on running LLM workflows in n8n in production. Everything here is from real templates I sell and support — the mistakes are mine, the fixes are tested.</em></p> <h2> The customer got charged twice, and every log said "success" </h2> <p>A workflow sent a payment, then a message, then a record update. One night the provider call timed out — not failed, timed out. n8n did the sensible thing and retried. The retry succeeded. So did the first attempt, it turned out: the timeout was on the way back, not on the way in. The customer was charged twice, messaged twice, and every log said "success," because each execution had, in isolation, succeeded.</p> <p>Retries fix "not yet" failures. They create duplicate side effects. Any workflow that retries — and any workflow that replays from a dead-letter queue, or resumes from a checkpoint — will eventually run the same side effect twice. If that side effect is sending a message, charging a card, or creating a record, "eventually" is a bug report, not a theory.</p> <h2> An idempotency key is a promise about the second run </h2> <p>The fix is one extra field, carried through the whole workflow: an idempotency key. It identifies the intended operation, not the attempt. The same key on a second attempt must produce the same result as the first — without doing the work again.</p> <p>The key has to be stable across retries, replays, and restarts. That rules out anything generated inside the attempt: a fresh UUID per run is a new operation every time, which is exactly what you are trying to prevent. The key comes from the job itself: the job id plus the operation name is the usual shape — <code>job-4821:charge</code>, <code>job-4821:notify</code>. Same job, same operation, same key, no matter how many times it runs.</p> <h2> Check the key before the side effect, not after </h2> <p>Ordering is the whole mechanism, and it is easy to get backwards. The workflow must look up the key before it performs the side effect, not log it afterwards:</p> <ol> <li>Before the charge, the send, or the create, check a small store for this key.</li> <li>If a completed result exists for the key, return that result and skip the side effect entirely. The retry becomes a no-op that reports the original outcome.</li> <li>If no result exists, perform the side effect, then store the result under the key — and the store write must be part of the same step, not a best-effort log line afterwards.</li> </ol> <p>Step 3 is where most hand-rolled versions break. If the workflow charges the card and then crashes before recording the key, the retry sees no key and charges again. The record has to be written as close to the side effect as the system allows, and the window between them is the window where duplicates still live. Where the provider offers a native idempotency key — Stripe is the classic example — use it: the provider's store is atomic in a way your workflow's two-step version is not, and passing your key through means the provider itself dedupes the second call.</p> <p>The store does not need to be fancy. A table with the key, the operation, the result, and a timestamp is enough. What it must be is durable and shared: not execution-local state, not a variable that dies with the run, and visible to every retry path — the ordinary retry, the DLQ replay, and the checkpoint resume. A key that only one retry path checks is a key that the other paths will ignore.</p> <h2> Keys expire, results do not vanish silently </h2> <p>Two practical details. First, keys need a retention policy. Keep them at least as long as your longest retry and replay window — if a DLQ entry can be replayed a week later, a key that expired after a day will not protect it. Second, a stored result is a decision, not just a cache entry: when a retry returns a stored "already charged" result, that outcome should be visible in the job record, so a human reading the run can tell "skipped as duplicate" from "never ran." A silent no-op looks identical to a skipped step in the logs, and the next person debugging will not know which one happened.</p> <p>This is a different job from the failure classification in the poison-message piece and the retry budget in the backoff piece. Classification decides whether to retry at all; the retry budget decides how many times. Idempotency decides what the second attempt is allowed to do. All three have to hold: a workflow that retries without idempotency will eventually double-charge; a workflow with idempotency but no classification will retry poison inputs forever, harmlessly but pointlessly.</p> <h2> The test is a double delivery, not a happy path </h2> <p>Testing this means deliberately delivering the same job twice and asserting three things: the side effect happened exactly once, the second run returned the first run's result, and the job record shows the second run as a duplicate skip rather than a fresh success. The test I actually run is boring and specific: one job, two deliveries — one of them forced by killing the run between the side effect and the record, if the system allows it — and a count of side effects at the end. Anything more than one means the key is not being checked where it matters.</p> <h2> The principle </h2> <p>A retry is a second attempt at the same operation, and the system has to treat it that knows that. Give every side effect a key derived from the job and the operation, check it before acting, store the result with it, and let the provider dedupe where it can. The workflow gets slightly slower — one lookup per side effect — and in return a timeout stops being a double charge. When a run is retried, and it will be, the question should never be "did we already do this?" The key should already have answered it.</p> <p><em>I'm building <a href="https://payhip.com/haopengailab" rel="noopener noreferrer">AI Automation Lab</a> — production-ready n8n workflow templates.
