Coding Agent Horror Stories: The CVE That Did Not Exist

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

<p class="wp-block-paragraph"><em>This is Part 6 of our</em> <a href="https://www.docker.com/blog/ai-coding-agent-horror-stories-security-risks/" id="dkr_ai-coding-agent-horror-stories-series-95520"><em>AI Coding Agent Horror Stories series</em></a><em>, where we look at real security incidents involving AI coding agents and at how Docker Sandboxes contain agent execution at the boundary rather than at the command line.</em><br /></p> <p class="wp-block-paragraph">Every story in this series so far has been about an agent reaching for something it should not have touched. We have seen agents wander into home directories, drop production databases, leak credentials, and run shell commands that did something very different from what the developer expected. In each case, the damage came from the agent having more reach than it needed.</p> <p class="wp-block-paragraph">This story is the opposite. The agent in this one reached nothing at all, because it was deliberately built so that it could not. And yet, on the night in question, it was still the most dangerous thing in the pipeline. </p> <p class="wp-block-paragraph">This story was shared by Pratik Kumar Singh as part of our Agent Hall of Shame contest on social media.</p> <h2 class="wp-block-heading">Today&#8217;s Horror Story: The Review That Made Everything Up</h2> <p class="wp-block-paragraph">A platform engineer built a code review bot for his team. The idea was simple and useful. Every time someone pushes code, the bot reads what changed and writes a review into the pipeline, the same kind of first pass a human teammate would give before a person looks at the change.</p> <p class="wp-block-paragraph">He named the bot <a href="https://gitlab.com/kitarp29/buaji" id="dkr_buaji-95520" rel="nofollow noopener" target="_blank">BuaJi</a>. In India, your bua is your father&#8217;s sister, and in many families she is the relative who inspects everything you do and always manages to find something wrong with it. For a code reviewer, it is a fitting name.</p> <p class="wp-block-paragraph">What made BuaJi interesting was how carefully it was set up. The bot runs on local models through Ollama, which means the model weights sit on the engineer&#8217;s own hardware and no request ever goes out to an AI vendor. It also runs as a job in his CI pipeline, triggered whenever someone pushes code. Taken together, this makes the whole setup self-hosted. The code it reads is company source code, and with this design none of it ever leaves the building. That was a deliberate choice, because his company takes that seriously.</p> <p class="wp-block-paragraph">He also gave BuaJi one firm rule: it can read, and it can comment, and that is all. It cannot run <code>terraform apply</code>, which is the command that creates or changes real cloud infrastructure. It cannot run <code>kubectl apply</code>, which changes what is actually running in the Kubernetes cluster. And it cannot push a commit, so it has no way to change the code itself. Those are the commands that change the real world, and BuaJi was given none of them. On paper, this is exactly how you would want an AI reviewer to be built.</p> <p class="wp-block-paragraph">The version of BuaJi in the companion <a href="https://gitlab.com/kitarp29/buaji" id="dkr_repo-95520" rel="nofollow noopener" target="_blank">repo</a> is a deliberately minimal reviewer. It checks Go files against a handful of style rules. The report below is the kind of free-form finding any reviewer produces once you let it comment in prose rather than pass/fail, which is exactly the direction these bots get pushed in practice.</p> <h3 class="wp-block-heading">The change he pushed that night</h3> <p class="wp-block-paragraph">His product ships with a bundled copy of PostgreSQL. Older PostgreSQL releases have published vulnerabilities with CVE numbers attached, and upgrading to a newer patch release is how you make those known issues go away. So he bumped the version.</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: plain; gutter: false; title: ; notranslate"> - POSTGRES_VERSION=16.11 + POSTGRES_VERSION=16.13 </pre></div> <p class="wp-block-paragraph">This is about as boring and as responsible as a code change gets. It touches a few lines, it changes a version number, and its only purpose is to close security holes that are already public. Any reviewer, human or machine, should look at it and approve it in a few seconds. There is nothing in that diff to be suspicious about, and that is precisely why what happened next matters.</p> <h3 class="wp-block-heading">What came back</h3> <p class="wp-block-paragraph">BuaJi responded with roughly fifteen hundred words rejecting the change. For context, a normal review comment is a sentence or two.</p> <p class="wp-block-paragraph">The report described the version bump as an &#8220;architectural takeover,&#8221; a structural change smuggled into the codebase under the cover of routine maintenance. It claimed that the new PostgreSQL build was a vehicle for sending internal data to a third-party company, and it named that company outright. The company does not exist.</p> <p class="wp-block-paragraph">It went further. It referred to specific Kubernetes resources by name, as though it had inspected the cluster and found them. Those resources had never existed, and BuaJi had no access to the cluster that would have let it look. It then wrote Go scripts to &#8220;isolate the infected PostgreSQL nodes,&#8221; even though nothing was infected. Finally, it told the engineer to revoke all IAM access immediately, an action that would lock out every person in the organization, including the people who would be needed to fix any real problem.</p> <p class="wp-block-paragraph">Holding the whole argument together was a CVE number that has never been issued by anyone. Of everything in the report, this is the detail worth pausing on. A CVE identifier is one of the easiest things in security to verify, since you can look it up in a public registry in a few seconds. The bot invented a fact in the one place where invented facts are easiest to catch.</p> <p class="wp-block-paragraph">And yet the report looked completely convincing. The Markdown was clean and well structured. The YAML it proposed would have parsed without errors. The tone was urgent and confident, the way a senior security engineer writes when they have found something serious and need you to act before it gets worse. The engineer spent about two minutes reading the CI logs, realized that none of it was real, and went back to what he was doing.</p> <h3 class="wp-block-heading">In this issue, you&#8217;ll learn:</h3> <ul class="wp-block-list"> <li>Why a read-only agent that only writes comments can still get your cluster taken down</li> <li>What makes a fabricated security finding harder to dismiss than an obviously broken one</li> <li>Why agent output belongs in the untrusted column, the same as agent input</li> <li>How to move a real AI code reviewer into a Docker Sandbox, step by step, and what that does and does not protect you from</li> </ul> <div class="wp-block-ponyo-image"> <img alt="image2 1" class="fade-in" height="811" src="https://www.docker.com/app/uploads/2026/10/image2-1.png" title="- image2 1" width="1218" /> </div> <p class="wp-block-paragraph"><em>Caption: Comic illustrating how a confident, well-formatted security report from an AI reviewer can be entirely fabricated, and what happens when somebody acts on it.</em></p> <h2 class="wp-block-heading">The Problem</h2> <p class="wp-block-paragraph">It is important to say clearly that the read-only rule did its job. BuaJi could not carry out any of its own recommendations, and it never had any access to the cluster. Because of that, the entire episode cost the engineer two minutes of his evening and nothing more.</p> <p class="wp-block-paragraph">The trouble is that the rule only controlled what BuaJi could do. Nobody had thought about what BuaJi could say. A read-only agent is still allowed to tell people what to do, and the person reading its output usually has exactly the access that the agent was denied. BuaJi could not run the scripts it wrote, but it could write them down and hand them to someone who could.</p> <p class="wp-block-paragraph">This engineer caught the problem because he knows his own cluster well. He knew those Kubernetes resources were not real and that nothing had been compromised. Now imagine a newer engineer on call at two in the morning, half awake, looking at a long and alarming security report in the pipeline. Revoking all IAM access in production in the middle of the night is an outage all by itself. Running an unreviewed Go script against your database nodes could be considerably worse. In both scenarios, BuaJi would not have done anything. A person would have done all of it, in good faith, because the report told them to.</p> <p class="wp-block-paragraph">What makes this so hard to defend against is that no permission model would have flagged it, because no permission was ever violated. The agent stayed within its boundary. The engineer had every right to run those commands on his own systems. The only thing in the entire chain that was false was the content of the report.</p> <div class="wp-block-ponyo-image"> <img alt="image1 1" class="fade-in" height="931" src="https://www.docker.com/app/uploads/2026/10/image1-1.png" title="- image1 1" width="1999" /> </div> <p class="wp-block-paragraph"></p> <h2 class="wp-block-heading">How Docker Sandboxes Contain This</h2> <p class="wp-block-paragraph">Here&#8217;s the honest part: a sandbox is not a fact-checker. No microVM boundary will ever make a review comment accurate. What a boundary changes is what that fabricated output can do once it exists.</p> <p class="wp-block-paragraph">Remember where BuaJi&#8217;s read-only rule actually lived, in a convention. One engineer configured it in his own pipeline and has to keep remembering to leave it in place. Rules like that hold until someone is in a hurry, or a new teammate copies the config and drops a section they did not understand, or a small exception made for a good reason quietly becomes permanent. None of this needs bad intent; it is just how real teams work.</p> <p class="wp-block-paragraph">Docker Sandboxes run agents inside isolated microVMs each with its own kernel, its own filesystem, and a network that denies everything by default. An agent inside one can invent anything it likes, but the invention has nowhere to go: no credentials to use, no cluster to reach, no commit to push, unless someone allowed that access ahead of time. The read-only rule stops being something a person remembers and becomes a property of the environment. And when a report claims it inspected your cluster, the policy log is your proof it never could have.</p> <p class="wp-block-paragraph">That protects you from the agent. It does nothing for the human who reads the output, and no sandbox ever will. For that half, treat agent review output the way you already treat agent input, untrusted until something checks it: label it so it doesn&#8217;t carry a colleague&#8217;s weight, verify any CVE numbers, and never run agent-written remediation until a person has read and understood it.</p> <p class="wp-block-paragraph">This is the same pattern as the <a href="https://www.pillar.security/blog/the-week-of-sandbox-escapes" id="dkr_sandbox-escapes-95520" rel="nofollow noopener" target="_blank">sandbox escapes</a> Pillar published in July. The boundary itself was never broken; a file was written inside the sandbox, and a tool outside later trusted it. An agent&#8217;s output is always an input to whatever reads it next and somewhere downstream, something trusts what it receives. Very often, that something is a person.</p> <p class="wp-block-paragraph">Let&#8217;s move BuaJi into a Docker Sandbox, one step at a time. By the end, the read-only rule is enforced by the environment, not by memory.</p> <h2 class="wp-block-heading">How BuaJi runs today</h2> <p class="wp-block-paragraph">BuaJi is a small Python script, <code>buaji.py</code>. Its GitLab job installs Ollama on a GPU runner, starts <code>ollama serve</code>, loads the model named in <code>LLM</code>, and runs the script.</p> <p class="wp-block-paragraph">The script reads review rules from <code>rules.md</code> and finds the changed files with <code>git diff HEAD^ HEAD --name-only</code>. It sends each file and rule to Ollama at <code>http://localhost:11434</code> and prints the answers to the CI log.</p> <p class="wp-block-paragraph">The catch is that everything shares one container: the model, the script, the checkout and every CI variable, including <code>CI_JOB_TOKEN</code>. BuaJi is read-only only because the script happens not to write anything.</p> <h2 class="wp-block-heading">What we want instead</h2> <p class="wp-block-paragraph">We split the job in two. The model stays on the runner next to the GPU. BuaJi moves into a microVM that can read the code, talk to the model, and nothing else.</p> <div class="wp-block-ponyo-image"> <img alt="image3 1" class="fade-in" height="1092" src="https://www.docker.com/app/uploads/2026/10/image3-1.png" title="- image3 1" width="1924" /> </div> <p class="wp-block-paragraph"></p> <p class="wp-block-paragraph">One open path to the model, everything else blocked, and a CVE check on the way out.</p> <h3 class="wp-block-heading">Step 1: Let BuaJi find Ollama somewhere other than localhost</h3> <p class="wp-block-paragraph">Inside a sandbox, <code>localhost</code> is the sandbox itself. So we read the Ollama address from an environment variable and keep the old value as the default:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> - url = &quot;http://localhost:11434/api/generate&quot; + base = os.environ.get(&quot;OLLAMA_URL&quot;, &quot;http://localhost:11434&quot;) + url = f&quot;{base}/api/generate&quot; </pre></div> <p class="wp-block-paragraph">Outside a sandbox, nothing changes. Inside one, we point <code>OLLAMA_URL</code> at the runner.</p> <h3 class="wp-block-heading">Step 2: Bake BuaJi&#8217;s dependencies into a sandbox image, once</h3> <p class="wp-block-paragraph">Today the job runs <code>apt-get</code> and <code>pip3 install</code> on every run, which needs internet access each time.</p> <p class="wp-block-paragraph">Instead, build a small image once with everything BuaJi needs, so the sandbox never downloads anything:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> FROM docker/sandbox-templates:shell USER root RUN apt-get update \ &amp;&amp; apt-get install -y --no-install-recommends python3 python3-requests git \ &amp;&amp; rm -rf /var/lib/apt/lists/* USER agent </pre></div> <p class="wp-block-paragraph">Push it to your registry and store its name in a CI variable called <code>BUAJI_TEMPLATE</code>.</p> <h3 class="wp-block-heading">Step 3: Keep the model on the runner</h3> <p class="wp-block-paragraph">Ollama stays on the runner with the GPU. Install it once on the runner instead of running <code>curl | sh</code> in every pipeline.</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> ollama serve &gt; /tmp/ollama.log 2&gt;&amp;1 &amp; sleep 2 ollama pull &quot;$LLM&quot; </pre></div> <p class="wp-block-paragraph">The model never enters the sandbox. BuaJi reaches it through one port, opened in Step 5.</p> <h3 class="wp-block-heading">Step 4: Create the sandbox with the code mounted read-only</h3> <p class="wp-block-paragraph">This step decides what BuaJi can see and change.</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> mkdir -p &quot;$CI_BUILDS_DIR/buaji-scratch&quot; sbx run -d --name &quot;$SBX_NAME&quot; -t &quot;$BUAJI_TEMPLATE&quot; \ shell &quot;$CI_BUILDS_DIR/buaji-scratch&quot; &quot;$CI_PROJECT_DIR:ro&quot; </pre></div> <p class="wp-block-paragraph">Here is what each part does:</p> <ul class="wp-block-list"> <li><code>--name</code> gives each pipeline its own sandbox.</li> <li><code>-t</code> uses the image from Step 2.</li> <li><code>shell</code> is the agent type. BuaJi is a plain script, so a shell sandbox is enough.</li> <li><code>buaji-scratch</code> is an empty folder, the only place BuaJi can write.</li> <li><code>:ro</code> mounts the repository read-only. BuaJi can read files and run <code>git diff</code>, but cannot change anything.</li> </ul> <p class="wp-block-paragraph">Notice what is missing: no GitLab token, no kubeconfig, no cloud credentials. Even if BuaJi tried <code>kubectl</code> or <code>terraform</code>, it would have nothing to connect with.</p> <h3 class="wp-block-heading">Step 5: Open one network path, to the model</h3> <p class="wp-block-paragraph">Sandboxes block all outgoing traffic by default. We open one path, for this sandbox only. (This assumes the runner&#8217;s default policy is deny-all; on a balanced or open default, set the default to deny-all first.)</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> sbx policy allow network --sandbox &quot;$SBX_NAME&quot; localhost:11434 </pre></div> <p class="wp-block-paragraph">The allow target (localhost:11434) and the address BuaJi dials (host.docker.internal:11434) are two names for the same runner port,  the first from the runner&#8217;s point of view, the second from inside the microVM. Kubernetes, your cloud APIs, and GitLab all stay blocked. If a report claims BuaJi &#8220;inspected the cluster,&#8221; this rule proves it could not have.</p> <p class="wp-block-paragraph">Kubernetes, your cloud APIs and GitLab all stay blocked. If a report claims BuaJi &#8220;inspected the cluster,&#8221; this rule proves it could not have.</p> <h3 class="wp-block-heading">Step 6: Run the review</h3> <p class="wp-block-paragraph">BuaJi runs as before, just in a new place with only two variables:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> sbx exec -w &quot;$CI_PROJECT_DIR&quot; \ -e LLM=&quot;$LLM&quot; \ -e OLLAMA_URL=http://host.docker.internal:11434 \ &quot;buaji-$CI_PIPELINE_ID&quot; python3 buaji.py | tee buaji-review.log </pre></div> <ul class="wp-block-list"> <li><code>-w</code> starts in the checkout, where <code>buaji.py</code> expects <code>rules.md</code>.</li> <li>The two <code>-e</code> flags are the only variables BuaJi can see.</li> <li><code>tee</code> saves the review to a file on the runner, outside the sandbox.</li> </ul> <p class="wp-block-paragraph">The review is now just text. BuaJi cannot post it, act on it, or change what happens to it next.</p> <h3 class="wp-block-heading">Step 7: Check every CVE number before anyone acts on the report</h3> <p class="wp-block-paragraph">This check would have caught the fake report in seconds. It runs on the runner, so BuaJi cannot skip it.</p> <p class="wp-block-paragraph">It looks up every CVE ID in the NVD database and fails the job if any of them do not exist:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> unverified=&quot;&quot; for id in $(grep -oE &#039;CVE-&#x5b;0-9]{4}-&#x5b;0-9]{4,}&#039; buaji-review.log | sort -u); do count=$(curl -s &quot;https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=$id&quot; \ | jq -r &#039;.totalResults // 0&#039;) &#x5b; &quot;$count&quot; = &quot;0&quot; ] &amp;&amp; unverified=&quot;$unverified $id&quot; done if &#x5b; -n &quot;$unverified&quot; ]; then echo &quot;&amp;#x26a0;&amp;#xfe0f; BuaJi output mentions CVE IDs that do not exist:$unverified&quot; echo &quot;&amp;#x26a0;&amp;#xfe0f; Treat this review as unverified. Do not run any commands it suggests.&quot; exit 1 fi </pre></div> <p class="wp-block-paragraph">Because the job is <code>allow_failure: true</code>, GitLab marks it &#8220;passed with warnings.&#8221; The pipeline keeps moving, but nobody mistakes the report for a trusted one. This degrades the signal, it does not block the human. The warning is a nudge, not a guardrail ~ a tired on-call engineer can still scroll past it..</p> <p class="wp-block-paragraph">It won&#8217;t catch every made-up detail, like a fake Kubernetes resource name. But it catches the one that holds most fake reports together.</p> <h3 class="wp-block-heading">Step 8: Check what BuaJi tried to reach, then clean up</h3> <p class="wp-block-paragraph">Finally, review the policy log and remove the sandbox:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> sbx policy log &quot;$SBX_NAME&quot; sbx stop &quot;buaji-$CI_PIPELINE_ID&quot; sbx rm -f &quot;buaji-$CI_PIPELINE_ID&quot; </pre></div> <p class="wp-block-paragraph">The log shows every host BuaJi tried to reach. On a deny-all runner, a healthy run shows only the model on port 11434. Anything else is a signal worth looking at.</p> <p class="wp-block-paragraph">Removing the sandbox means every pipeline starts clean.</p> <h3 class="wp-block-heading">The complete pipeline job</h3> <p class="wp-block-paragraph">Put together, the <code>buaji</code> job in <code>.gitlab-ci.yml</code> looks like this:</p> <div class="wp-block-syntaxhighlighter-code "><pre class="brush: bash; gutter: false; title: ; notranslate"> # BuaJi, moved into a Docker Sandbox. The read-only rule is now a property of # the environment, not a convention in the script: the code is mounted :ro, no # credentials are passed in, and only one network path (to the model) is open. buaji: stage: buaji tags: - self-hosted-gpu-kvm # GPU for Ollama, KVM for sbx microVMs variables: LLM: gemma GIT_DEPTH: &quot;2&quot; # buaji.py diffs HEAD^ against HEAD SBX_NAME: buaji-$CI_PIPELINE_ID before_script: - ollama serve &gt; /tmp/ollama.log 2&gt;&amp;1 &amp; - sleep 2 - ollama pull &quot;$LLM&quot; - mkdir -p &quot;$CI_BUILDS_DIR/buaji-scratch&quot; - sbx run -d --name &quot;$SBX_NAME&quot; -t &quot;$BUAJI_TEMPLATE&quot; shell &quot;$CI_BUILDS_DIR/buaji-scratch&quot; &quot;$CI_PROJECT_DIR:ro&quot; - sbx policy allow network --sandbox &quot;$SBX_NAME&quot; localhost:11434 script: - sbx exec -w &quot;$CI_PROJECT_DIR&quot; -e LLM=&quot;$LLM&quot; -e OLLAMA_URL=http://host.docker.internal:11434 &quot;$SBX_NAME&quot; python3 buaji.py | tee buaji-review.log - ./scripts/verify-cves.sh buaji-review.log after_script: - sbx policy log &quot;$SBX_NAME&quot; - sbx stop &quot;$SBX_NAME&quot; &amp;&amp; sbx rm -f &quot;$SBX_NAME&quot; allow_failure: true only: changes: - &quot;**/*.go&quot; </pre></div> <p class="wp-block-paragraph">The runner needs a GPU and KVM, which usually means self-hosted. <code>GIT_DEPTH: "2"</code> gives <code>buaji.py</code> the two commits it compares. The cleanup sits in <code>after_script</code>, so it runs even when the job fails.</p> <h3 class="wp-block-heading">What changed</h3> <p class="wp-block-paragraph">Before, the read-only rule lived in the script. Now it lives in the environment: a read-only checkout, one network path, no credentials, and only checked text coming out.</p> <p class="wp-block-paragraph">What hasn&#8217;t changed is the human reading the output. The sandbox stops BuaJi from running its scripts. Only the CVE check and a careful reader stop someone else from running them.</p> <h2 class="wp-block-heading">Best Practices</h2> <p class="wp-block-paragraph"><strong>Treat an agent&#8217;s security finding as a hypothesis, not a conclusion.</strong> A report from an AI reviewer is a claim with good formatting. When a human reviewer flags a security issue, there is an implied step where they checked their reasoning. With an agent, that step has not happened, so you have to do it yourself.</p> <p class="wp-block-paragraph"><strong>Verify every CVE number before acting on it.</strong> This is the cheapest check in the whole process and it catches the single most convincing part of a fabricated report. Automate it, as in Step 7, so it runs on every review without anyone having to remember.</p> <p class="wp-block-paragraph"><strong>Never run agent-written remediation without reviewing it first.</strong> Scripts and commands supplied by an agent are the point where a false finding turns into a real incident. Read them with the same care you would give an unknown script from the internet.</p> <p class="wp-block-paragraph"><strong>Make read-only a property of the environment, not a habit.</strong> A restriction you enforce by hand in a pipeline config is always one rushed change away from disappearing. Mount the code read-only, pass in no credentials, and open only the network paths the agent needs, as in Steps 4 to 6.</p> <p class="wp-block-paragraph"><strong>Clearly label agent review output as agent output.</strong> When a bot&#8217;s review looks identical to one from a senior engineer, it borrows authority it has not earned. A clear label helps readers apply the right level of skepticism.</p> <p class="wp-block-paragraph"><strong>Keep an eye on your signal-to-noise ratio.</strong> The curl story is the warning here. A review channel that fills up with noise eventually stops being read, and a review channel nobody reads is worse than having none, because people still assume it is protecting them.</p> <h2 class="wp-block-heading">Conclusion</h2> <p class="wp-block-paragraph">The engineer who built BuaJi was right that the read-only rule protected him, and it genuinely did. BuaJi could not touch the cluster, could not revoke anyone&#8217;s access, and could not run a single line of the code it had so carefully written. What the rule could not do was stop BuaJi from asking somebody else to run it.</p> <p class="wp-block-paragraph">Every other story in this series has been about an agent reaching too far. This one never reached at all. It stayed inside its boundary, did exactly what it was permitted to do, and still produced a document that would have caused a real outage if the person reading it had been a little more tired, or a little less familiar with their own cluster.</p> <p class="wp-block-paragraph">As we give agents more responsibility in our pipelines, containing what they can do is only half the job. A sandbox handles that half. The other half is deciding how much we trust what they tell us, and that part is still up to us.</p>
