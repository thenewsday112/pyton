One installer filename lives in three files, and the version number lives in a header nothing reads

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Notifio ships three installers: one NSIS setup for Windows and two DMGs for Mac, because a universal build would bundle two copies of Chromium. They are built locally, uploaded to Cloudflare R2 under fixed object keys, and served through an API route that presigns a URL and redirects to it.

That means one filename, notifio-arm64.dmg, has to be written identically in three files that know nothing about each other.

The triangle

First, electron-builder decides what the file on disk is called:

"mac": { "target": [{ "target": "dmg", "arch": ["arm64", "x64"] }], "artifactName": "notifio-${arch}.dmg" }, "win": { "target": ["nsis"], "artifactName": "notifio-setup.exe" }

Second, the release script decides what to upload and under what key, and its comment is doing all of the work that a type would otherwise do:

// Artifact name -> content type. Names must match package.json build.artifactName // and the FILES map in server/src/app/api/download/[platform]/route.ts. const ARTIFACTS = { win: [{ file: 'notifio-setup.exe', contentType: 'application/octet-stream' }], mac: [ { file: 'notifio-arm64.dmg', contentType: 'application/x-apple-diskimage' }, { file: 'notifio-x64.dmg', contentType: 'application/x-apple-diskimage' }, ], };

Third, the web app decides which key to presign for a given download button:

const FILES: Record<string, string> = { "mac-arm64": "notifio-arm64.dmg", "mac-x64": "notifio-x64.dmg", win: "notifio-setup.exe", };

Three files, two packages, one of them a desktop app and one a Next.js site, and the only thing keeping them in step is a sentence in a comment. Change artifactName and the build succeeds, the upload succeeds for the two files that still match, and the third fails with "Artifact missing" if you are lucky or uploads nothing if you changed all of them. Change only the download route and the build and upload both pass, and the download page serves a 403 from R2 for a key that is not there.

In fairness to the release script, it does not take electron-builder's word for anything. It checks that each expected artifact exists and that it was modified during this run:

const stat = fs.statSync(full); if (stat.mtimeMs < buildStart - 5000) { fail( `${file} was not rebuilt (last modified ${stat.mtime.toISOString()}).\n` + ' The build reported success but produced no new artifact.' ); }

So a renamed artifact is caught on the build side. It is the web side that has no idea.

The keys are fixed, so a release overwrites

The comment at the top of the release script states the consequence rather than burying it:

/** * R2 object keys are fixed (the download API serves them by name), so a release * overwrites the previous one. See RELEASES.md. */

There is a --archive flag that also uploads notifio-setup-1.1.0.exe alongside, and it is opt-in and off by default. So in the normal case there is exactly one copy of each installer and no history, which means no rollback: shipping a broken build and shipping the fix are the same operation at the same key.

What I did not appreciate until I went looking is that every upload records its version anyway:

const res = runAws([ 's3', 'cp', local, `s3://${r2.bucket}/${key}`, '--endpoint-url', r2.endpoint, '--content-type', contentType, '--metadata', `version=${version}`, ... ], r2);

And reads it back as part of the verify step, comparing the remote size against the local one:

if (head.ContentLength !== size) { fail(`Size mismatch for ${key}: local ${size} bytes, remote ${head.ContentLength} bytes`); } const remoteVersion = head.Metadata?.version ?? '?'; info(`\x1b[32mok\x1b[0m ${key} ${humanSize(head.ContentLength)} version=${remoteVersion}`);

That is the only code in either package that reads it. The download route presigns a GET and redirects. It does not look at the metadata, it does not surface a version, and nothing on the website knows which build it is handing you.

One byte is enough to find out

The object metadata is served on the download response, so you can read it from outside with a range request for a single byte. Grab the redirect target first, since the presigned URL only lives for 60 seconds:

$ for p in win mac-arm64 mac-x64; do loc=$(curl -s -D- -o /dev/null "https://notifio.app/api/download/$p" \ | grep -i '^location:' | sed 's/^[Ll]ocation: //;s/\r//') echo "== $p" curl -s -r 0-0 -D- -o /dev/null "$loc" \ | grep -iE "^(content-range|last-modified|x-amz-meta-version)" done == win Content-Range: bytes 0-0/237616310 Last-Modified: Tue, 28 Jul 2026 11:35:55 GMT x-amz-meta-version: 1.0.3 == mac-arm64 Content-Range: bytes 0-0/291511009 Last-Modified: Tue, 22 Sep 2026 12:24:46 GMT x-amz-meta-version: 1.1.0 == mac-x64 Content-Range: bytes 0-0/301712899 Last-Modified: Tue, 22 Sep 2026 12:25:03 GMT x-amz-meta-version: 1.1.0 Platform Key Size Version Uploaded Windows notifio-setup.exe 237,616,310 1.0.3 28 July Mac arm64 notifio-arm64.dmg 291,511,009 1.1.0 22 September Mac x64 notifio-x64.dmg 301,712,899 1.1.0 22 September

I have written before about the two months between those dates, and the conclusion there was that nothing in the product can tell you which version you are downloading. That still holds for the product, and it is less true than I thought of the system around it. The answer has been sitting in x-amz-meta-version on every object since the first upload, written by the release script, verified by the release script, and read by nobody after that.

The reason for the split is structural rather than careless. Installers are not cross-buildable, and the script refuses rather than pretending:

fail( `Cannot build ${impossible.join(' + ')} on ${os.platform()}.\n` + ` Installers are not cross-buildable here: run this script on a ${impossible.includes('mac') ? 'Mac' : 'Windows machine'}, ` + `then use --skip-build to upload artifacts copied over from the other machine.` );

A release is therefore two machines, and a release that only happens on one of them leaves the other key untouched at whatever version it last was. The script even says so at the end of a single-platform run. It just says it in a terminal that nobody is looking at two months later.

Why HEAD does not work

The obvious way to read that metadata is a HEAD request, and it returns 403. The presigned URL is signed for a specific operation, which you can see in the query string it hands you:

...&X-Amz-Expires=60&X-Amz-SignedHeaders=host&x-amz-checksum-mode=ENABLED&x-id=GetObject

x-id=GetObject is part of the signed material, so switching the verb invalidates the signature. A range GET is still a GET, which is why one byte works where zero bytes does not. The release script does use head-object, but it does so with the R2 credentials directly rather than through a presigned link, so it is not constrained the same way.

The 60 second expiry is deliberate and documented in the route:

// Presigned URL valid for 60 seconds — enough for the browser to start the // download without permanently exposing the file.

Which is the right trade for a download button and is also why the shell loop above has to fetch a fresh redirect for each platform rather than reusing one.

One more number worth looking at

The release script requires the AWS CLI, and explains why:

fail( 'AWS CLI not found. It is used to upload files larger than R2\'s 300MB web UI limit.\n' + ... );

The x64 DMG is 301,712,899 bytes. That is 287.7 MiB, so it is under 300MB if you mean the binary kind and over it if you mean the decimal kind. Either way the biggest artifact is now sitting on the exact boundary that the dependency exists to get around, and it is only that size because each installer bundles its own Chromium. The afterPack hook already deletes the browser for the architecture that build will never run, which is the only reason it is not twice as large.

What I would change

Both fixes are small and neither is about the upload.

The filename triangle wants one shared constant, and it cannot have one, because app/ and server/ are separate packages that do not import each other. The next best thing is a test in server/ that reads app/package.json, expands ${arch} and asserts the resulting set equals the values of FILES. It is a ten-line test that converts a comment into a failure.

The version header wants a reader. The download route already talks to R2 with credentials; a HeadObjectCommand before the redirect would let the download page print the version and build date next to each button. That is a real feature for a desktop app whose update mechanism is reinstalling, and the data is already there. The only reason it is not on the page is that nobody thought to ask the object what it was.

If you want to run the range-request loop above against the live endpoints, it is three HTTP requests and three bytes, and it will tell you more about what Notifio currently ships than the download page itself will.

Compare offers in net-worth-per-hour, not headline salary

A larger number on an offer letter often hides a worse deal. The human mind anchors on base pay because it is the most visible figure, but compensation is a bundle of conflicting variables.

Do the arithmetic on paper, because the gut always loses to the printer. Start by converting every offer into an hourly rate based on expected actual hours worked, not the forty hours listed in the handbook. If a role requires ten hours of uncompensated overtime each week, a ten percent salary bump disappears instantly. A longer week can eat a ten percent premium in a year through sheer time dilution.

Next, examine the mechanics of the non-cash components. Bonus structures tied to company metrics that never trigger are worth zero. Equity with a four-year cliff and no secondary market is a lottery ticket, not income. Calculate the real cost of the commute, both in fuel and in dead hours that could be spent building equity of your own.

Ask the boring benefits questions early, because they are checks, not fights. Find out the exact health insurance deductible, the employer match on retirement accounts, and the policy on hardware replacement. These details shift your annual take-home pay by thousands of dollars without showing up in the headline figure.

When you strip away the branding and the recruiter's enthusiasm, an offer is simply a contract to trade specific units of time and skill for specific units of capital. Run the math before you sign.

Introducing AUTONET - A Rust CLI That Finds the Right Local IP for Your Development Server

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

Ever switched between office Wi-Fi, home Wi-Fi, Ethernet, or a mobile hotspot and had to update your development server's IP address again?

That's the problem I'm trying to solve with AUTONET, an open-source, cross-platform networking tool built in Rust.

The Problem

When developing web or mobile applications, your machine can have multiple IP addresses from Wi-Fi, Ethernet, Docker, virtual machines, and VPNs.

Finding the correct address to access your local development server from another device can become frustrating.

For example, your application might be running on localhost:3000, but you want to test it from your phone.

Which IP address should you use?

What AUTONET Does

AUTONET inspects your machine's network interfaces and routing information to select a suitable IP address for local development.

Some of its capabilities include:

  • Automatic IP selection — Finds a suitable local network address.
  • Network change detection — Monitors changes between Wi-Fi, Ethernet, and other interfaces.
  • Docker and VPN awareness — Avoids selecting unsuitable virtual network addresses by default.
  • Developer integration — Provides environment variables for development applications.
  • Local hostname discovery — Supports .local hostname advertisement using mDNS.
  • QR code generation — Makes it easier to open development applications on mobile devices.
  • Network diagnostics — Helps identify potential connectivity problems.

Built with Rust

AUTONET uses a modular Rust architecture with separate components for network discovery, address selection, and CLI operations.

It uses native operating-system networking APIs to inspect interfaces and routes.

Linux support is implemented, while macOS and Windows implementations still need real-hardware validation.

Still Evolving

The project is open-source and under active development.

I'm particularly interested in feedback and contributions around:

  • Testing across Linux, macOS, and Windows
  • Network switching and connectivity edge cases
  • Improving address selection and diagnostics
  • Documentation and developer experience

If you're interested in Rust, networking, operating systems, or developer tools, feel free to explore the repository.

GitHub: https://github.com/phravins/AUTONET

I'd love to hear your thoughts on the approach.

How do you currently handle changing local IP addresses when testing applications across multiple devices?

Feedback, issues, and pull requests are always welcome!

OpenNVR 0.1.10: running an open-source NVR's AI on the Qualcomm Hexagon NPU

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

OpenNVR is an open-source (AGPL) NVR that records and streams from any ONVIF or RTSP camera and runs the AI model you choose behind them: YOLO detection, pose, face recognition, plate OCR, open-vocabulary detection, and a vision-language agent that can look at a scene and reason about it. It runs on hardware you own, air-gapped if you need, with every inference audited.

Version 0.1.10 is the first release with hardware acceleration flavours, and this post is about the one I have numbers for: Qualcomm's Hexagon NPU.

The board

Arduino Ventuno Q: Qualcomm Dragonwing IQ-8275 (QCS8275), eight ARM cores, a Hexagon NPU, Ubuntu 24.04. Small, fanless, the kind of thing that sits behind a few cameras in a shop or a plant.

The numbers

All measured on that board with the published container images. Full windows, settle times and caveats are in the benchmark doc.

Tier-0 detector (YOLO, one frame):

Device ms per frame CPU, 8 threads 164 Hexagon NPU, fp16 8.6

In the full stack (streams, decode, tracking, the API, all on the same box):

Device Cameras at 2 fps, no drops Host idle CPU 4 (10 cameras drop half their frames) ~4 % NPU 16, 0 dropped 46 %

The adapters that sit behind the detector, end-to-end on one 1080p JPEG:

Adapter CPU NPU YOLO 141 ms 77 ms Pose 108 ms 64 ms Package detection 100 ms 60 ms Face recognition (InsightFace) 443 ms 62 ms Plate OCR 248 ms 62 ms

The NPU's own share of an adapter call is about 9 ms. The rest is JPEG decode and preprocessing on a busy CPU, so the adapter path is now bounded by image handling, not inference.

How it works

Everything goes through ONNX Runtime's QNN execution provider, shipped as a plugin wheel (onnxruntime-qnn). There is no Qualcomm SDK to install on the host. The -qualcomm container gets the DSP device node, the DMA heap, and two host libraries bind-mounted, and that is it.

git clone https://github.com/open-nvr/open-nvr.git && cd open-nvr ./start.sh # OPENNVR_ACCEL=auto detects /dev/fastrpc-cdsp and picks the qualcomm flavour

OPENNVR_ACCEL=cpu|intel|qualcomm overrides the probe. A box with only a CPU gets exactly the images it got before.

Compiled graphs are cached, so the second start skips the ~6 s compile. The pipeline reports which provider ONNX Runtime really ran on, and a request for an accelerator that silently fell back to CPU shows up as requested != effective in the metrics instead of being hidden.

Things that cost a day each

  • A plugin execution provider named in the providers= list is silently ignored. It has to be attached by device with add_provider_for_devices.
  • python:slim lacks libatomic1. The HTP backend fails to load and the session falls back to CPU with no error.
  • The first "NPU" number I got (12 ms, looked great) was a stub detector after a failed session. Check the health endpoint and the degraded counter before trusting a number.
  • The Ubuntu image ships Docker Compose 2.24.6, which randomly drops a container's second network at create. The installer now checks the Compose version and repairs network membership after every up.

Measure your own hardware

python -m detect_pipeline.bench --latency 200 --providers CPUExecutionProvider python -m detect_pipeline.bench --latency 200 --providers QNNExecutionProvider:htp

It reports median, p90 and min per device, names the provider that really ran, and exits non-zero if the accelerator fell back.

Also in 0.1.10

  • Intel iGPU and NPU flavour via OpenVINO, VAAPI decode
  • Signed self-update: each release ships a manifest signed by us and verified on the box, opt-in
  • Camera tours for display boards, camera CSV/Excel import and export, bulk actions
  • The app SDK's Look and Investigate steps for writing your own camera workflows

Next

NVIDIA, desktop GPUs and Jetson. If you have a Jetson, Rockchip or Hailo box you'd lend to a benchmark, I have one board and would like more.

Transformer Architecture in 5 Questions Developers Actually Ask (with 12 Lines of PyTorch)

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

Most Transformer explainers start with the famous diagram from "Attention Is All You Need" and lose half their readers at the first box. As a developer, I found it easier to learn the architecture by answering the five questions I kept asking myself, and by writing the core operation in code.

1. What problem was the Transformer actually solving?

RNNs and LSTMs read a sentence one token at a time, like a message passed down a line of people. That makes long-range relationships fragile and training hard to parallelise. The Transformer replaced the chain with attention: every token can look directly at every other token in one step. Think of it as moving from a relay race to a meeting room where everyone can hear everyone.

2. What are Q, K and V, really?

Each token is projected into three vectors by learned weight matrices:

  • Query: what this token is looking for
  • Key: what this token offers
  • Value: the information it passes on if it turns out to be relevant

Compare queries with keys, turn the scores into weights, and use the weights to mix values. That is the whole idea.

3. What does that look like in code?

Here is scaled dot-product attention, the heart of every Transformer block:

import torch import torch.nn.functional as F def attention(q, k, v, mask=None): # q, k, v: (batch, seq_len, d_k) d_k = q.size(-1) scores = q @ k.transpose(-2, -1) / d_k ** 0.5 # compare + scale if mask is not None: scores = scores.masked_fill(mask == 0, float("-inf")) weights = F.softmax(scores, dim=-1) # normalise return weights @ v # collect values

The / d_k ** 0.5 line is easy to skip, but it stops large dot products from pushing softmax into near one-hot outputs, which would kill gradients.

4. Why multiple heads?

One attention pattern can't capture everything in "Aman told Ravi that he would lead the project": who "he" is, which verb goes with which noun, what "lead" applies to. Multi-head attention runs several attention operations in parallel on different learned projections and concatenates the results. Each head is like a different camera angle on the same match.

5. How does a model like GPT generate text with this?

Two more pieces make it work:

  • Positional encoding: attention by itself ignores order, so "dog bites man" and "man bites dog" would look identical without it.
  • Causal masking: in a decoder, the mask argument above blocks each token from attending to future tokens. The model predicts one token, appends it, and repeats.

Add a feed-forward layer, residual connections and layer normalisation around each sublayer, stack the block N times, and you have the architecture behind modern LLMs.

Family Example Best at Encoder-only BERT Understanding: classification, search Decoder-only GPT Generation Encoder-decoder T5, original Transformer Translation, summarisation

Fifteen site pages, 45 hand-written links between them, and the one page nothing points at

📅 Oct 31, 2026  |  Category: Business  |  Read Source →

Notifio has fifteen per-site guide pages: Kamernet, Rightmove, Idealista and twelve more. They are not CMS entries. Each one is a TypeScript object in src/lib/alerts/sites/, split across three files by region, assembled into one array:

/** * Every site that has an /alerts/<slug> page. * * This array is the single source for the hub grid, the route's static params, * the footer column and the sitemap. Adding a site is one edit here; forgetting * to list it somewhere is not a failure mode that exists. */ export const ALERT_SITES: readonly AlertSite[] = [ ...NETHERLANDS_SITES, ...UK_SITES, ...EUROPE_SITES, ];

The last sentence of that comment turned out to be slightly optimistic, and the rest of this post is why.

Each page names its own siblings, by hand

The type has a related field, and the comment on it is the whole spec:

/** Slugs of three sibling pages, for internal linking. */ related: string[];

Fifteen pages, three slugs each, forty-five edges, all typed out by a human who was thinking about that one page at the time. The resolver is forgiving:

/** Resolves `related` slugs, dropping any that do not exist yet. */ export function relatedSites(site: AlertSite): AlertSite[] { return site.related .map(getAlertSite) .filter((related): related is AlertSite => related !== undefined && related.slug !== site.slug); }

That forgiveness is deliberate, because it lets you write a slug for a page you are about to add. It also means a typo is not an error, a failed build or a warning. It is one fewer link, silently, forever. So the first thing worth doing is counting the graph rather than trusting it:

$ node --experimental-strip-types - <<'EOF' const dir = "./src/lib/alerts/sites/"; const mods = await Promise.all(["netherlands.ts","uk.ts","europe.ts"].map(f=>import(dir+f))); const sites = mods.flatMap(m=>Object.values(m).flat()); const inbound = Object.fromEntries(sites.map(s=>[s.slug,0])); let edges = 0, dangling = []; for (const s of sites) for (const r of s.related) { edges++; r in inbound ? inbound[r]++ : dangling.push([s.slug, r]); } console.log({ sites: sites.length, edges, dangling }); console.log(Object.entries(inbound).sort((a,b)=>b[1]-a[1])); EOF { sites: 15, edges: 45, dangling: [] }

No dangling slugs. Good. The distribution is the interesting part:

Inbound from siblings Pages 8 kamernet 4 pararius, huurwoningen, spareroom, openrent, housinganywhere 3 rightmove, zoopla, idealista 2 funda, immobilienscout24, spotahome 1 roommatch, wg-gesucht 0 facebook-marketplace

The page with nothing pointing at it

The Facebook Marketplace page is named by none of the other fourteen. It names three of them itself, so it gives links and receives none, and you can confirm that from outside the repo without reading a line of it:

$ mkdir -p /tmp/alerts $ for p in idealista immobilienscout24 wg-gesucht housinganywhere spotahome \ facebook-marketplace rightmove zoopla spareroom openrent \ kamernet pararius funda huurwoningen roommatch; do curl -s https://notifio.app/alerts/$p -o /tmp/alerts/$p.html done $ grep -l '"/alerts/facebook-marketplace"' /tmp/alerts/*.html | wc -l 0 $ grep -l '"/alerts/kamernet"' /tmp/alerts/*.html | wc -l 15

Kamernet scores fifteen out of fifteen rather than eight because of the second linking mechanism, which I will come back to. Facebook Marketplace scores zero on both.

It is not orphaned from the site. The hub links all fifteen, and so does the sitemap, which is generated from the same array:

const alertPages: MetadataRoute.Sitemap = ALERT_SITES.map((site) => ({ url: `${APP_URL}/alerts/${site.slug}`, lastModified: new Date("2026-09-14"), changeFrequency: "monthly", priority: 0.8, }));

So it is reachable in two clicks from the home page and it is in the sitemap. What it has is the weakest internal link profile on the site, and the reason is obvious once you look at who would plausibly link it. The other fourteen are rental portals. This one is a general-purpose marketplace that happens to carry rentals, it sits alone in its own market section, and when I was writing each portal's three siblings I was picking other portals every time. Nobody decided to strand it. It is what you get when every edge is chosen locally and nothing looks at the graph.

Eleven of the forty-five edges are one-way, for the same reason. A page links a sibling, the sibling links three others, and nothing notices the asymmetry.

Why the footer duplicates five slugs

The second linking mechanism is the footer, which carries a hardcoded five:

/** * A hand-picked five, rather than the full catalogue from `lib/alerts`. * * The footer is a client component, and importing the catalogue here would ship * every word of every site page to the browser on every route to render five * links. These are the highest-traffic guides; everything else is one click away * behind "All supported sites". */ const FOOTER_SITES = [ { slug: "kamernet", name: "Kamernet" }, { slug: "pararius", name: "Pararius" }, { slug: "funda", name: "Funda" }, { slug: "rightmove", name: "Rightmove" }, { slug: "spareroom", name: "SpareRoom" }, ];

This is the one duplication in the system I would defend. Those site objects are large, every field is hand-written prose, and a client component importing the barrel would put all fifteen of them into the JavaScript bundle on every route on the site to render five anchors. Five slugs and five display names is a cheap copy.

It is still a copy, and it is why the counting above has two different answers for Kamernet. Five pages get a link from every page on the site including their own, and the ten that are not in that list get only what their siblings give them. The footer is also the reason "nothing in the catalogue can be half-added" is not quite true: add a site and the hub, the route, the sitemap and the footer's "all supported sites" link all pick it up, but the footer's five do not change, and nothing says they should.

What the template is not allowed to do

Worth saying why these pages exist as fifteen fat objects rather than one template with a name interpolated into it, because it is the decision that made the link graph matter at all:

/** * The shape of an /alerts/[site] page. * * Every field here is prose written for one specific site. The page template in * app/alerts/[site]/page.tsx contributes layout and nothing else: there is no * sentence in it with the site name interpolated into it, because a set of pages * that differ only by a noun is a doorway-page pattern and gets treated as one. * If a field below cannot be filled with something true about this site and this * site alone, the site does not get a page. */

Which is why there are fifteen and not fifty. Every claim about another company's notifications also carries a citation that renders on the page:

/** * A claim about a third party's product, with the page it came from. * * Anything we say about how another company's alerts behave carries one of * these. The citation is rendered on the page, which keeps us honest and gives * a reader a way to check a detail that may have changed since we wrote it. */ export type Source = { label: string; url: string; };

A template could not satisfy either rule, and a page that satisfies both is expensive enough that you write it only when you have something site-specific to say. That caps the catalogue, which is the actual mechanism keeping the thing honest.

The hub section nobody designed

One more artefact of deriving the hub from the array. Six market sections, rendered in a two-column grid:

$ curl -s https://notifio.app/alerts | grep -o "Another site?" | wc -l 6

Three, counted honestly. Each match appears twice because the RSC flight payload repeats the markup. The grid gets a filler card whenever a section has an odd number of sites:

{market.sites.length % 2 === 1 && ( <div className="hidden bg-[#0a0a0a] p-6 sm:block"> <p className="mb-2 text-[15px] font-semibold text-[#3a3a3a]">Another site?</p>

Netherlands has five, Spain has one, Marketplaces has one, so three of the six sections carry it. Nobody chose which sections get a "Notifio is not limited to this list" nudge. The parity of a hand-written array did.

What I would change

The graph needs a test more than it needs editing. Three assertions, all of them cheap next to the metadata-length test that already reads these same files:

  • Every slug in related resolves. Currently true, enforced by nothing, and silently false the moment it is not.
  • Every page has at least one inbound edge. This is the one that would have caught Facebook Marketplace on the commit that added it.
  • No page names itself. relatedSites already filters self-links at render time, which means the data is allowed to contain one and you would never find out.

Reciprocity I would leave alone. Forcing all forty-five edges to be mutual would make the UK four and the Dutch five into two closed cliques, and the whole point of Facebook Marketplace naming SpareRoom and OpenRent is that a person reading about a marketplace might want a real portal next. One-way is sometimes the correct answer. Zero inbound never is.

The pages are all up if you want to check the counts: the hub lists all fifteen, Kamernet is the one everything points at, and Facebook Marketplace is the one that found out about this post the hard way.
