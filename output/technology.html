Introducing AUTONET - A Rust CLI That Finds the Right Local IP for Your Development Server

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

<p>Ever switched between office Wi-Fi, home Wi-Fi, Ethernet, or a mobile hotspot and had to update your development server's IP address again?</p> <p>That's the problem I'm trying to solve with <strong>AUTONET</strong>, an open-source, cross-platform networking tool built in Rust.</p> <h3> The Problem </h3> <p>When developing web or mobile applications, your machine can have multiple IP addresses from Wi-Fi, Ethernet, Docker, virtual machines, and VPNs.</p> <p>Finding the correct address to access your local development server from another device can become frustrating.</p> <p>For example, your application might be running on <code>localhost:3000</code>, but you want to test it from your phone.</p> <p>Which IP address should you use?</p> <h3> What AUTONET Does </h3> <p>AUTONET inspects your machine's network interfaces and routing information to select a suitable IP address for local development.</p> <p><strong>Some of its capabilities include:</strong></p> <ul> <li> <strong>Automatic IP selection</strong> — Finds a suitable local network address.</li> <li> <strong>Network change detection</strong> — Monitors changes between Wi-Fi, Ethernet, and other interfaces.</li> <li> <strong>Docker and VPN awareness</strong> — Avoids selecting unsuitable virtual network addresses by default.</li> <li> <strong>Developer integration</strong> — Provides environment variables for development applications.</li> <li> <strong>Local hostname discovery</strong> — Supports <code>.local</code> hostname advertisement using mDNS.</li> <li> <strong>QR code generation</strong> — Makes it easier to open development applications on mobile devices.</li> <li> <strong>Network diagnostics</strong> — Helps identify potential connectivity problems.</li> </ul> <h3> Built with Rust </h3> <p>AUTONET uses a modular Rust architecture with separate components for network discovery, address selection, and CLI operations.</p> <p>It uses native operating-system networking APIs to inspect interfaces and routes.</p> <p>Linux support is implemented, while macOS and Windows implementations still need real-hardware validation.</p> <h3> Still Evolving </h3> <p>The project is open-source and under active development.</p> <p>I'm particularly interested in feedback and contributions around:</p> <ul> <li>Testing across Linux, macOS, and Windows</li> <li>Network switching and connectivity edge cases</li> <li>Improving address selection and diagnostics</li> <li>Documentation and developer experience</li> </ul> <p>If you're interested in Rust, networking, operating systems, or developer tools, feel free to explore the repository.</p> <p><strong>GitHub:</strong> <a href="https://github.com/phravins/AUTONET" rel="noopener noreferrer">https://github.com/phravins/AUTONET</a></p> <p>I'd love to hear your thoughts on the approach.</p> <p><strong>How do you currently handle changing local IP addresses when testing applications across multiple devices?</strong></p> <p>Feedback, issues, and pull requests are always welcome!</p>

OpenNVR 0.1.10: running an open-source NVR's AI on the Qualcomm Hexagon NPU

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

<p>OpenNVR is an open-source (AGPL) NVR that records and streams from any ONVIF or RTSP camera and runs the AI model you choose behind them: YOLO detection, pose, face recognition, plate OCR, open-vocabulary detection, and a vision-language agent that can look at a scene and reason about it. It runs on hardware you own, air-gapped if you need, with every inference audited.</p> <p>Version 0.1.10 is the first release with hardware acceleration flavours, and this post is about the one I have numbers for: Qualcomm's Hexagon NPU.</p> <h2> The board </h2> <p>Arduino Ventuno Q: Qualcomm Dragonwing IQ-8275 (QCS8275), eight ARM cores, a Hexagon NPU, Ubuntu 24.04. Small, fanless, the kind of thing that sits behind a few cameras in a shop or a plant.</p> <h2> The numbers </h2> <p>All measured on that board with the published container images. Full windows, settle times and caveats are in the <a href="https://github.com/open-nvr/open-nvr/blob/main/bench/ventuno-q-benchmark-2026-10-30.md" rel="noopener noreferrer">benchmark doc</a>.</p> <p>Tier-0 detector (YOLO, one frame):</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Device</th> <th>ms per frame</th> </tr> </thead> <tbody> <tr> <td>CPU, 8 threads</td> <td>164</td> </tr> <tr> <td>Hexagon NPU, fp16</td> <td>8.6</td> </tr> </tbody> </table></div> <p>In the full stack (streams, decode, tracking, the API, all on the same box):</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Device</th> <th>Cameras at 2 fps, no drops</th> <th>Host idle</th> </tr> </thead> <tbody> <tr> <td>CPU</td> <td>4 (10 cameras drop half their frames)</td> <td>~4 %</td> </tr> <tr> <td>NPU</td> <td>16, 0 dropped</td> <td>46 %</td> </tr> </tbody> </table></div> <p>The adapters that sit behind the detector, end-to-end on one 1080p JPEG:</p> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Adapter</th> <th>CPU</th> <th>NPU</th> </tr> </thead> <tbody> <tr> <td>YOLO</td> <td>141 ms</td> <td>77 ms</td> </tr> <tr> <td>Pose</td> <td>108 ms</td> <td>64 ms</td> </tr> <tr> <td>Package detection</td> <td>100 ms</td> <td>60 ms</td> </tr> <tr> <td>Face recognition (InsightFace)</td> <td>443 ms</td> <td>62 ms</td> </tr> <tr> <td>Plate OCR</td> <td>248 ms</td> <td>62 ms</td> </tr> </tbody> </table></div> <p>The NPU's own share of an adapter call is about 9 ms. The rest is JPEG decode and preprocessing on a busy CPU, so the adapter path is now bounded by image handling, not inference.</p> <h2> How it works </h2> <p>Everything goes through ONNX Runtime's QNN execution provider, shipped as a plugin wheel (<code>onnxruntime-qnn</code>). There is no Qualcomm SDK to install on the host. The <code>-qualcomm</code> container gets the DSP device node, the DMA heap, and two host libraries bind-mounted, and that is it.<br /> </p> <div class="highlight js-code-highlight"> <pre class="highlight shell"><code>git clone https://github.com/open-nvr/open-nvr.git <span class="o">&amp;&amp;</span> <span class="nb">cd </span>open-nvr ./start.sh <span class="c"># OPENNVR_ACCEL=auto detects /dev/fastrpc-cdsp and picks the qualcomm flavour</span> </code></pre> </div> <p><code>OPENNVR_ACCEL=cpu|intel|qualcomm</code> overrides the probe. A box with only a CPU gets exactly the images it got before.</p> <p>Compiled graphs are cached, so the second start skips the ~6 s compile. The pipeline reports which provider ONNX Runtime really ran on, and a request for an accelerator that silently fell back to CPU shows up as <code>requested != effective</code> in the metrics instead of being hidden.</p> <h2> Things that cost a day each </h2> <ul> <li>A plugin execution provider named in the <code>providers=</code> list is silently ignored. It has to be attached by device with <code>add_provider_for_devices</code>.</li> <li> <code>python:slim</code> lacks <code>libatomic1</code>. The HTP backend fails to load and the session falls back to CPU with no error.</li> <li>The first "NPU" number I got (12 ms, looked great) was a stub detector after a failed session. Check the health endpoint and the degraded counter before trusting a number.</li> <li>The Ubuntu image ships Docker Compose 2.24.6, which randomly drops a container's second network at create. The installer now checks the Compose version and repairs network membership after every <code>up</code>.</li> </ul> <h2> Measure your own hardware </h2> <div class="highlight js-code-highlight"> <pre class="highlight shell"><code>python <span class="nt">-m</span> detect_pipeline.bench <span class="nt">--latency</span> 200 <span class="nt">--providers</span> CPUExecutionProvider python <span class="nt">-m</span> detect_pipeline.bench <span class="nt">--latency</span> 200 <span class="nt">--providers</span> QNNExecutionProvider:htp </code></pre> </div> <p>It reports median, p90 and min per device, names the provider that really ran, and exits non-zero if the accelerator fell back.</p> <h2> Also in 0.1.10 </h2> <ul> <li>Intel iGPU and NPU flavour via OpenVINO, VAAPI decode</li> <li>Signed self-update: each release ships a manifest signed by us and verified on the box, opt-in</li> <li>Camera tours for display boards, camera CSV/Excel import and export, bulk actions</li> <li>The app SDK's Look and Investigate steps for writing your own camera workflows</li> </ul> <h2> Next </h2> <p>NVIDIA, desktop GPUs and Jetson. <p>Most Transformer explainers start with the famous diagram from "Attention Is All You Need" and lose half their readers at the first box. What problem was the Transformer actually solving? </h3> <p>RNNs and LSTMs read a sentence one token at a time, like a message passed down a line of people. That makes long-range relationships fragile and training hard to parallelise. The Transformer replaced the chain with attention: every token can look directly at every other token in one step. Think of it as moving from a relay race to a meeting room where everyone can hear everyone.</p> <h3> 2. What are Q, K and V, really? </h3> <p>Each token is projected into three vectors by learned weight matrices:</p> <ul> <li> <strong>Query</strong>: what this token is looking for</li> <li> <strong>Key</strong>: what this token offers</li> <li> <strong>Value</strong>: the information it passes on if it turns out to be relevant</li> </ul> <p>Compare queries with keys, turn the scores into weights, and use the weights to mix values. class="p">,</span> <span class="n">dim</span><span class="o">=-</span><span class="mi">1</span><span class="p">)</span> <span class="c1"># normalise </span> <span class="k">return</span> <span class="n">weights</span> <span class="o">@</span> <span class="n">v</span> <span class="c1"># collect values </span></code></pre> </div> <p>The <code>/ d_k ** 0.5</code> line is easy to skip, but it stops large dot products from pushing softmax into near one-hot outputs, which would kill gradients.</p> <h3> 4. Why multiple heads? </h3> <p>One attention pattern can't capture everything in "Aman told Ravi that he would lead the project": who "he" is, which verb goes with which noun, what "lead" applies to. Multi-head attention runs several attention operations in parallel on different learned projections and concatenates the results. Each head is like a different camera angle on the same match.</p> <h3> 5. How does a model like GPT generate text with this? </h3> <p>Two more pieces make it work:</p> <ul> <li> <strong>Positional encoding</strong>: attention by itself ignores order, so "dog bites man" and "man bites dog" would look identical without it.</li> <li> <strong>Causal masking</strong>: in a decoder, the <code>mask</code> argument above blocks each token from attending to future tokens. The model predicts one token, appends it, and repeats.</li> </ul> <p>Add a feed-forward layer, residual connections and layer normalisation around each sublayer, stack the block N times, and you have the architecture behind modern LLMs.</p> <h3> A quick map of the model families </h3> <div class="table-wrapper-paragraph"><table> <thead> <tr> <th>Family</th> <th>Example</th> <th>Best at</th> </tr> </thead> <tbody> <tr> <td>Encoder-only</td> <td>BERT</td> <td>Understanding: classification, search</td> </tr> <tr> <td>Decoder-only</td> <td>GPT</td> <td>Generation</td> </tr> <tr> <td>Encoder-decoder</td> <td>T5, original Transformer</td> <td>Translation, summarisation</td> </tr> </tbody> </table></div> <h3> Go deeper </h3> <p>I wrote a longer, beginner-friendly walkthrough that covers every block (encoder, decoder, cross-attention, residuals, masking) with everyday analogies: <a href="https://www.aheadmint.com/articles/transformer-architecture" rel="noopener noreferrer">Transformer Architecture Explained</a> on AheadMint.</p> <p>If you've got a clearer mental model for Q/K/V, share it in the comments. Run It Twice, Charge Once: Idempotency Keys in n8n

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

<p><em>This is part of my build-in-public series on running LLM workflows in n8n in production. Everything here is from real templates I sell and support — the mistakes are mine, the fixes are tested.</em></p> <h2> The customer got charged twice, and every log said "success" </h2> <p>A workflow sent a payment, then a message, then a record update. One night the provider call timed out — not failed, timed out. n8n did the sensible thing and retried. The retry succeeded. So did the first attempt, it turned out: the timeout was on the way back, not on the way in. The customer was charged twice, messaged twice, and every log said "success," because each execution had, in isolation, succeeded.</p> <p>Retries fix "not yet" failures. They create duplicate side effects. Any workflow that retries — and any workflow that replays from a dead-letter queue, or resumes from a checkpoint — will eventually run the same side effect twice. If that side effect is sending a message, charging a card, or creating a record, "eventually" is a bug report, not a theory.</p> <h2> An idempotency key is a promise about the second run </h2> <p>The fix is one extra field, carried through the whole workflow: an idempotency key. It identifies the intended operation, not the attempt. The same key on a second attempt must produce the same result as the first — without doing the work again.</p> <p>The key has to be stable across retries, replays, and restarts. That rules out anything generated inside the attempt: a fresh UUID per run is a new operation every time, which is exactly what you are trying to prevent. The key comes from the job itself: the job id plus the operation name is the usual shape — <code>job-4821:charge</code>, <code>job-4821:notify</code>. Same job, same operation, same key, no matter how many times it runs.</p> <h2> Check the key before the side effect, not after </h2> <p>Ordering is the whole mechanism, and it is easy to get backwards. The workflow must look up the key before it performs the side effect, not log it afterwards:</p> <ol> <li>Before the charge, the send, or the create, check a small store for this key.</li> <li>If a completed result exists for the key, return that result and skip the side effect entirely. The retry becomes a no-op that reports the original outcome.</li> <li>If no result exists, perform the side effect, then store the result under the key — and the store write must be part of the same step, not a best-effort log line afterwards.</li> </ol> <p>Step 3 is where most hand-rolled versions break. If the workflow charges the card and then crashes before recording the key, the retry sees no key and charges again. The record has to be written as close to the side effect as the system allows, and the window between them is the window where duplicates still live. Where the provider offers a native idempotency key — Stripe is the classic example — use it: the provider's store is atomic in a way your workflow's two-step version is not, and passing your key through means the provider itself dedupes the second call.</p> <p>The store does not need to be fancy. A table with the key, the operation, the result, and a timestamp is enough. What it must be is durable and shared: not execution-local state, not a variable that dies with the run, and visible to every retry path — the ordinary retry, the DLQ replay, and the checkpoint resume. A key that only one retry path checks is a key that the other paths will ignore.</p> <h2> Keys expire, results do not vanish silently </h2> <p>Two practical details. First, keys need a retention policy. Keep them at least as long as your longest retry and replay window — if a DLQ entry can be replayed a week later, a key that expired after a day will not protect it. Second, a stored result is a decision, not just a cache entry: when a retry returns a stored "already charged" result, that outcome should be visible in the job record, so a human reading the run can tell "skipped as duplicate" from "never ran." A silent no-op looks identical to a skipped step in the logs, and the next person debugging will not know which one happened.</p> <p>This is a different job from the failure classification in the poison-message piece and the retry budget in the backoff piece. Classification decides whether to retry at all; the retry budget decides how many times. Idempotency decides what the second attempt is allowed to do. All three have to hold: a workflow that retries without idempotency will eventually double-charge; a workflow with idempotency but no classification will retry poison inputs forever, harmlessly but pointlessly.</p> <h2> The test is a double delivery, not a happy path </h2> <p>Testing this means deliberately delivering the same job twice and asserting three things: the side effect happened exactly once, the second run returned the first run's result, and the job record shows the second run as a duplicate skip rather than a fresh success. The test I actually run is boring and specific: one job, two deliveries — one of them forced by killing the run between the side effect and the record, if the system allows it — and a count of side effects at the end. Anything more than one means the key is not being checked where it matters.</p> <h2> The principle </h2> <p>A retry is a second attempt at the same operation, and the system has to treat it that knows that. Give every side effect a key derived from the job and the operation, check it before acting, store the result with it, and let the provider dedupe where it can. The workflow gets slightly slower — one lookup per side effect — and in return a timeout stops being a double charge. When a run is retried, and it will be, the question should never be "did we already do this?" The key should already have answered it.</p> <p><em>I'm building <a href="https://payhip.com/haopengailab" rel="noopener noreferrer">AI Automation Lab</a> — production-ready n8n workflow templates. The free <a href="https://payhip.com/b/ulER8" rel="noopener noreferrer">AI Hook Generator</a> shows how I structure real workflows; my open-source templates live at <a href="https://github.com/zhp910318/n8n-ai-automation-lab" rel="noopener noreferrer">github.com/zhp910318/n8n-ai-automation-lab</a>.</em></p>
