Staying Evergreen: How we automated secure access and repo hygiene in a shared org

📅 Oct 15, 2026  |  Category: World  |  Read Source →

<p class="wp-block-paragraph">Working with outside collaborators can add more work for a repository owner. You need to confirm who still needs access, change permissions as projects evolve, and archive repositories once they&rsquo;ve served their purpose.</p> <p class="wp-block-paragraph">To keep up, repository owners need to track collaborators, deadlines, and follow-ups for each repository. As a project grows, that manual housekeeping becomes harder to keep up with and easier to defer.</p> <p class="wp-block-paragraph">We faced this problem in a shared organization where GitHub employees (&ldquo;Hubbers&rdquo;) collaborate with customers and partners on product trials and professional services engagements. Our answer was <strong>Evergreen</strong>, a GitHub App built with native GitHub features. The workflows below exhibit a pattern you can adapt for your own organization.</p> <h2 class="wp-block-heading" id="h-meet-evergreen">Meet Evergreen</h2> <p class="wp-block-paragraph">Evergreen is a GitHub App that automates organization hygiene through two workflows:</p> <ol class="wp-block-list"> <li><strong>Outside collaborator access reviews.</strong> Every quarter, each repo&rsquo;s outside collaborators are reviewed. Keep who you need, and everyone else is removed.</li> <li><strong>Stale repository detection and archival.</strong> Repos with no human activity past a threshold get flagged, warned, and (if still untouched) archived.</li> </ol> <p class="wp-block-paragraph">Two design principles shaped everything:</p> <p class="wp-block-paragraph"><strong>Fail secure.</strong> If nobody responds to an access review, we don&rsquo;t leave access in place and hope for the best. We revoke it. The safe outcome is the <em>default</em> outcome.</p> <p class="wp-block-paragraph"><strong>Never destroy anything.</strong> Evergreen will <strong>never</strong> delete a repository or its contents. Archived repos are recoverable, and every access change is written into the repo&rsquo;s tracking issue, so reverting a mistake is as easy as a copy-paste to Copilot.</p> <h2 class="wp-block-heading" id="h-how-it-works-one-brain-many-hands">How it works: One brain, many hands</h2> <p class="wp-block-paragraph">Under the hood, Evergreen is a small Go webhook server running in a container. But the interesting part is the <em>choreography</em>. Every moving piece is a stock GitHub feature: a GitHub App, scheduled actions, webhooks, issues, custom properties, and plain files in a repo. Nothing exotic to reinvent.</p> <h3 class="wp-block-heading" id="h-a-controller-that-keeps-time">A controller that keeps time</h3> <p class="wp-block-paragraph">A dedicated <strong>controller repo</strong> acts as Evergreen&rsquo;s clock and its memory. Four scheduled GitHub Actions workflows fire <code>repository_dispatch</code> events on a quarterly cadence, and the app wakes up and does the work:</p> <figure class="wp-block-table"><table class="has-fixed-layout"><thead><tr><th><strong>Day</strong></th><th><strong>Workflow</strong></th><th><strong>What happens</strong></th></tr></thead><tbody><tr><td>1st</td><td>Stale repo review</td><td>Flag repos with no recent human activity, open a warning issue</td></tr><tr><td>8th</td><td>Access review</td><td>Snapshot outside collaborators, open a checklist issue per repo</td></tr><tr><td>16th</td><td>Stale repo cleanup</td><td>Archive repos still stale after the grace period</td></tr><tr><td>23rd</td><td>Access cleanup</td><td>Auto&#8209;revoke access for any review left unanswered</td></tr></tbody></table></figure> <p class="wp-block-paragraph">Reviews open two weeks before their cleanup runs, and there&rsquo;s a hard grace period baked in so a stray manual run can never fast&#8209;forward the guillotine. Each workflow also supports <code>workflow_dispatch</code>, so we can trigger any step by hand as needed.</p> <h3 class="wp-block-heading" id="h-state-you-can-git-blame">State you can <code>git blame</code></h3> <p class="wp-block-paragraph">Evergreen tracks every repo&rsquo;s status as a JSON file (one per repository) committed to the controller repo under <code>state/repos/&lt;repo_id&gt;.json</code>. The snapshot of who had access, when the review opened, the deadline, who decided, and what happened all lives there. Here&rsquo;s a completed review where a Hubber kept Alice&rsquo;s access and let Bob&rsquo;s lapse:</p> <div class="wp-block-code-wrapper"> <pre class="wp-block-code has-custom-css "renewed", "collaborators_at_open": [ { "login": "alice", "name": "Alice Example", "permission": "admin" }, { "login": "bob", "name": "Bob Example", "permission": "write" } ], "renewed_logins": audit trail.</strong> Want to know why someone lost access last spring? <code>git log</code> the state file. There&rsquo;s no separate database or bespoke audit pipeline to track.</p> <h3 class="wp-block-heading" id="h-issue-ops-everywhere-it-matters">Issue&#8209;ops, everywhere it matters</h3> <p class="wp-block-paragraph">Evergreen does its talking through issues inside each repository. When an access review kicks off, every repo gets a checklist issue:</p> <figure class="wp-block-image size-full"><img alt="Screenshot of an access review issue titled &ldquo;[ACTION REQUIRED] Access Review &ndash; 2026-04-13.&rdquo; Outside collaborators Alice Example, with admin access, and Bob Example, with write access, have unchecked boxes. Instructions say to select anyone who should keep access, then close the issue. A warning states that if no action is taken by April 27, all listed access will be automatically revoked." class="wp-image-99535" height="221" src="https://github.blog/wp-content/uploads/2026/10/674986199-ee305d10-3419-4270-a829-41ed3da29fae.png?resize=528%2C221" width="528" /></figure> <p class="wp-block-paragraph">The interaction model is delightfully simple: <strong>check the boxes for who stays, then close the issue.</strong> That&rsquo;s it. When the issue closes, Evergreen listens for the <code>issues.closed</code> webhook event, reads the checkboxes, retains the checked collaborators, and revokes the rest, then posts a receipt comment listing exactly what it kept and what it removed.</p> <figure class="wp-block-image size-full"><img alt="Quarterly outside-collaborator access review flowchart. A dispatch snapshots outside collaborators and opens a checklist issue in each repository. If a team member closes the issue, checked collaborators retain access and unchecked collaborators have access revoked. If no one responds by the deadline, everyone&rsquo;s access is automatically revoked. Both paths log the decision in the issue and state." class="wp-image-99534" height="417" src="https://github.blog/wp-content/uploads/2026/10/674985578-53474bf2-cd36-4345-96ef-24c79268a858.png?resize=2000%2C417" width="2000" /></figure> <h3 class="wp-block-heading" id="h-only-the-right-humans-can-pull-the-lever">Only the right humans can pull the lever</h3> <p class="wp-block-paragraph">Closing an access review issue is a privileged action, so Evergreen guards it. If someone who <em>isn&rsquo;t</em> a Hubber closes an issue, the app quietly reopens it and posts a note explaining why. Decisions only count when they come from the people authorized to make them.</p> <h3 class="wp-block-heading" id="h-informing-the-right-people">Informing the right people</h3> <p class="wp-block-paragraph">Here&rsquo;s a subtle problem: we know the people who need to respond to a review are Hubbers, but we didn&rsquo;t always know <em>which</em> Hubber(s) owned a given repository.</p> <p class="wp-block-paragraph">Evergreen resolves the right people to notify through a fallback chain:</p> <ol class="wp-block-list"> <li>If a repo sets an <code>evergreen_repo_owner</code> custom property (a <code>@user</code> or <code>@org/team</code>), use it.</li> <li>Otherwise, look at recent issue and commit authors and cc the ones who are on the access review team, i.e., the Hubbers actually working in that repo.</li> </ol> <p class="wp-block-paragraph">The result: the right owners get pinged automatically, without anyone maintaining a spreadsheet of &ldquo;who owns what.&rdquo;</p> <h3 class="wp-block-heading" id="h-fail-secure-and-fail-closed">Fail secure, and fail <em>closed</em></h3> <p class="wp-block-paragraph">When a review deadline passes with no response, cleanup revokes every collaborator in the snapshot. We were careful about a subtle edge case: what if some removals succeed while others hit a transient API error? Marking the review &ldquo;done&rdquo; while a removal is still outstanding would be a quiet inconsistency, and we didn&rsquo;t want that.</p> <p class="wp-block-paragraph">So Evergreen fails <strong>closed</strong>. If any removal fails, the review stays pending and the issue stays open, and the next run retries the stragglers. It only records &ldquo;revoked&rdquo; once every removal actually succeeded. And whatever gets removed is written into the issue, so restoring access is a matter of re&#8209;adding the handles it listed.</p> <h2 class="wp-block-heading" id="h-the-user-experience-automation-that-feels-considerate">The user experience: automation that feels considerate</h2> <p class="wp-block-paragraph">Automated housekeeping has a reputation for being the office smoke alarm: loud, easy to ignore, and usually going off while you&rsquo;re cooking something perfectly fine. We worked hard to make Evergreen feel like the opposite:</p> <ul class="wp-block-list"> <li><strong>It comes to you.</strong> The work happens as an issue in <em>your</em> repo.</li> <li><strong>It tags the right people.</strong> No &ldquo;who owns this?&rdquo; archaeology.</li> <li><strong>It&rsquo;s crystal clear about the ask.</strong> Every issue states what to do, the exact deadline, and precisely what happens if you ignore it.</li> <li><strong>It nudges before it acts.</strong> A reminder comment lands before the deadline: no surprise revocations.</li> <li><strong>It has an escape hatch.</strong>&nbsp;Org owners (Hubbers) can opt out by setting a custom property (<code>evergreen_exempt_from_access_review</code> or <code>evergreen_exempt_from_archive</code>).</li> </ul> <h2 class="wp-block-heading" id="h-rolling-it-out-carefully">Rolling it out carefully</h2> <p class="wp-block-paragraph">Automation that manages access and archives repositories deserves a careful rollout, especially into a large, active org (ours has 1,400+ Hubbers, and many more customers and partners). We wanted the very first run to be a complete non&#8209;event. A few practices got us there:</p> <p class="wp-block-paragraph"><strong>Dry&#8209;run first.</strong> Evergreen ships with a <code>DRY_RUN</code> mode that logs every write it <em>would</em> make without touching a single collaborator or repo. We ran it against the real org and read the logs like tea leaves until we trusted the decisions it wanted to make.</p> <p class="wp-block-paragraph"><strong>Overcommunicate.</strong> Before flipping the switch, we broadcast what was coming, when, and what people needed to do, so the first issue anyone saw wasn&rsquo;t a surprise. We found that when you&rsquo;re telling a large group the same thing for the seventh time, it&rsquo;s often when many are still hearing it for the first time.</p> <p class="wp-block-paragraph"><strong>Watch everything with Splunk.</strong> Evergreen emits structured <code>logfmt</code> logs to a dedicated Splunk index. That observability is how we caught edge cases in the wild (empty collaborator lists, unusual permissions, repos with issues disabled) and tightened the logic before they mattered.</p> <p class="wp-block-paragraph"><strong>Respect the platform&rsquo;s speed limits.</strong> When you open issues and post comments across <em>every</em> repo in a big org, you slam into GitHub&rsquo;s <strong>secondary rate limits for content creation</strong>: 80 requests/minute and 500/hour. While this is a thoughtful preventative control to avoid system abuse, it requires a bit of intention when automating IssueOps at large scale.</p> <p class="wp-block-paragraph">So Evergreen paces itself <em>by construction</em>. It processes repos in batches, spaces out each content&#8209;creating call by a couple of seconds, and sleeps between batches to let the rolling window clear, and it only counts the repos that actually create content, so a quiet quarter where nothing&rsquo;s eligible still runs fast. We opted for proactive avoidance over reactive back&#8209;off.</p> <h2 class="wp-block-heading" id="h-lessons-we-re-taking-with-us">Lessons we&rsquo;re taking with us</h2> <ul class="wp-block-list"> <li><strong>Make the safe path the default path.</strong> Fail secure, then make responding easy enough that failing secure rarely triggers.</li> <li><strong>Use the primitives you already have.</strong> Issues, webhooks, custom properties, and git history did the work of a bespoke UI, a job queue, and an audit database.</li> <li><strong>Meet people where they work.</strong> An issue in your repo beats a dashboard you&rsquo;ll never open.</li> <li><strong>Logs are a revert button.</strong> Writing every change into the issue turned &ldquo;oops&rdquo; into &ldquo;paste these three handles into a Copilot session.&rdquo;</li> <li><strong>Respect the limits.</strong> At org scale, rate limits aren&rsquo;t an edge case: they&rsquo;re the design constraint.</li> </ul> <h2 class="wp-block-heading" id="h-keep-your-org-evergreen">Keep your org evergreen</h2> <p class="wp-block-paragraph">Routine hygiene is the kind of work that&rsquo;s easy to defer and perfect to automate. The trick isn&rsquo;t heroic cleanup sprints: it&rsquo;s making the boring, safe thing happen on a schedule, with a friendly face and an undo button.</p> <p class="wp-block-paragraph">That&rsquo;s Evergreen. And because it&rsquo;s built entirely from native GitHub features, you can stand up the same pattern yourself.</p> <div class="wp-block-group post-content-cta has-global-padding is-layout-constrained wp-block-group-is-layout-constrained"> <p class="wp-block-paragraph"><a href="https://docs.github.com/apps/creating-github-apps">Ready to make repository hygiene routine?</a> Start with one recurring access or archival task, then use GitHub Apps, actions, issues, and custom properties to automate the problem away.</p> </div> <p>The post <a href="https://github.blog/engineering/platform-security/staying-evergreen-how-we-automated-secure-access-and-repo-hygiene-in-a-shared-org/">Staying Evergreen: How we automated secure access and repo hygiene in a shared org</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>

GitHub availability report: September 2026

📅 Oct 14, 2026  |  Category: World  |  Read Source →

<p class="wp-block-paragraph">Our last update covered content through August. We did not publish another in September while other public content addressed the August 17 outage. This edition covers progress over the past two months.</p> <p class="wp-block-paragraph"><strong>The short version of August and September</strong>: we reduced shared-database pressure, added overload controls, created headroom for GitHub Actions, expanded failure containment for pull requests, and moved more production workloads to Azure. Significant incidents, a capacity pause, and a missed migration target show that the work is not complete.</p> <p class="wp-block-paragraph">By October 7, 120 of 160 production services were deployed in Central US, and 13 of 51 primary MySQL databases had moved. Azure also handled 65.4% of read traffic for GitHub&rsquo;s core application, 48.3% of Git read traffic, and 80.2% of stream-processing traffic. These percentages measure different workloads and should not be added.</p> <p class="wp-block-paragraph">We paused Central US deployments and traffic increases on September 11 because capacity was uneven across availability zones. Permanent ramps resumed September 18 after temporary relief, but durable capacity work continues, with a goal of unlocking all available capacity by the end of October. We missed our aggressive September 30 goal to deploy every production service there. During a planned database failover, an automated emergency process disconnected Central US database copies and disrupted customers in that region. We disabled that process during planned handoffs while improving recovery.</p> <p class="wp-block-paragraph">Outside the regional migration, 24 authentication-core tables moved off GitHub&rsquo;s oldest shared database, removing approximately one million queries per second from its replicas. The database cluster supporting issues and pull requests removed approximately 980 million unnecessary edit-history rows, creating an estimated 1.8 terabytes of recoverable storage. Weekly deadlocks fell approximately 77% from their June peak, and continuous cleanup now prevents the same unbounded growth from returning.</p> <p class="wp-block-paragraph">Half of sampled pull request traffic can now continue with limited functionality when a shared dependency fails. Production results showed several read operations remained available during a shared-database incident. Database traffic routing can also add capacity automatically during spikes; one group expanded from 14 to 19 instances during a September 23 increase in pull request activity. A production overload control now lets responders protect higher-priority API and web workflows by rejecting lower-priority requests before broader saturation. Operator documentation and training are complete.</p> <p class="wp-block-paragraph">GitHub Actions also gained operating headroom. From 2,500 requests to 24: Rebuilding star history without the stargazers

📅 Oct 14, 2026  |  Category: World  |  Read Source →

<p class="wp-block-paragraph">Maintainers look at star history to answer a practical question: did a launch, release, or event change a project&rsquo;s trajectory? To reconstruct that curve from the GitHub API, tools had to request pages of stargazer records (each person who currently stars the repository and when they starred it), keep the timestamps, and throw the identities away.</p> <p class="wp-block-paragraph">Over time, that design created problems at both ends. Identities were available for bulk collection, so bad actors started scraping public stargazer lists for spam and phishing campaigns. For highly starred repositories, the endpoint could also make the database process many thousands of entries to return a single page.</p> <p class="wp-block-paragraph">The fix seemed clear: return counts instead of people. But returning less data didn&rsquo;t actually make the query any cheaper.</p> <p class="wp-block-paragraph">Now maintainers have a direct way to get the curve: we built an endpoint that returns up to 30 weeks of daily star counts in a single request, with no identities attached. Keeping that cheap to serve meant reducing how much data the database processed, not just how much it returned, and the endpoint does that by <strong>filtering stars by time before it counts anything</strong>.</p> <h2 class="wp-block-heading" id="h-what-maintainers-need-from-star-history">What maintainers need from star history</h2> <p class="wp-block-paragraph">We first addressed the immediate risks to developers and to our database by <a href="https://github.blog/changelog/2026-06-30-upcoming-access-restrictions-to-public-api-endpoints-and-ui-views/">restricting stargazer and watcher lists to repository administrators and collaborators</a>. After the access change, callers without the required permission could receive an empty response or a <code>403 Forbidden</code> response.</p> <p class="wp-block-paragraph">That change also cut off tools that had used the old response to calculate star history, often without displaying or otherwise using the usernames it returned. So we talked with maintainers and tool builders to understand what they still needed. They used star history as an approximate signal of interest: to compare activity before and after a release, or to see whether an announcement reached new developers. What they cared about was the curve.</p> <p class="wp-block-paragraph">The old API response had made identity look like part of that contract because every timestamp arrived attached to a user. In practice, tools such as Star History needed counts and dates, not usernames or other user data. Once identity was no longer part of the requirement, we could design an aggregate endpoint for the actual job: retrieving changes in star counts over time at a useful resolution.</p> <blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"> <p class="wp-block-paragraph">When the API change disrupted Star History, users rallied around the project. GitHub&rsquo;s Community team listened and connected us with product engineering, who dug into our use case and worked alongside us to design a purpose-built endpoint. A difficult situation became a constructive collaboration between GitHub, Star History, and the broader community&mdash;ultimately leading to a better solution.</p> <cite>Tianzhou Chen, star-history.com maintainer and Bytebase co-founder</cite></blockquote> <h2 class="wp-block-heading" id="why-the-original-endpoint-was-expensive">Why the original endpoint was expensive</h2> <p class="wp-block-paragraph">Once we knew what maintainers needed, the next step was understanding why the original design couldn&rsquo;t provide it cheaply. The original <code>GET /repos/{owner}/{repo}/stargazers</code> endpoint was built to answer a simple question: who starred this repository? It returned a paginated list of people, and if the request specified a custom media type, each entry also included when the star was created.</p> <p class="wp-block-paragraph">The star model was built for the same job. It records the current set of people who have starred a repository, which keeps showing a star count or a list of stargazers simple. It was not designed as a historical event log: when someone removes a star, that record is removed. When tools began using the list as a time series, reconstructing a growth curve meant retrieving individual identities and processing every current star. Because each page held at most 100 people, the work grew with the repository&rsquo;s popularity: building the full curve for <code>react/react</code>, with about 251,000 stars, took about 2,511 requests, so tools often ran into rate limits or sampled pages instead of reading them all.</p> <p class="wp-block-paragraph">Serving a page required the database to query the repository&rsquo;s current stars. Due to a bug in the pagination implementation, every request also counted all of those stars to work out how many pages existed, even though the caller received only one page of up to 100 people. On a highly starred repository, that meant counting many thousands of entries on every request. In the week before we restricted access, nearly 37,000 of these count queries ran slowly enough to be logged, averaging nearly 3 seconds each, and database safeguards killed more than 1,000 of them, which contributed to request timeouts.</p> <p class="wp-block-paragraph">The chart below shows what all that counting cost. After we restricted access, the database served about 60% fewer stargazer requests, and the total time it spent on the count query fell by about 80%.</p> <b></b><b></b><b></b><b></b> <div class="ghchart" id="gh-chart-total-query-duration"></div> <h2 class="wp-block-heading" id="approaches-we-considered">Approaches we considered</h2> <p class="wp-block-paragraph">Removing identities handled the privacy requirement. The harder part was keeping each request from scanning the repository&rsquo;s entire current star set.</p> <h3 class="wp-block-heading" id="keeping-events-without-identities">Keeping events without identities</h3> <p class="wp-block-paragraph">Our first spike kept one record per star and returned the <code>starred_at</code> value without the stargazer&rsquo;s identity for callers who lacked collaborator access. At first, this looked like the quickest path forward, because it directly served the request we had heard from tool builders. It also closed the identity-harvesting path with a relatively small change to the existing serialization and authorization flow.</p> <p class="wp-block-paragraph">This approach addressed identity exposure and would have allowed existing tools to keep working. But API consumers would still have to paginate through and process potentially many thousands of individual records to build an aggregate history. It also tied the new use case to an endpoint and pagination model designed for listing people rather than retrieving trends.</p> <h3 class="wp-block-heading" id="aggregating-then-paginating">Aggregating, then paginating</h3> <p class="wp-block-paragraph">Aggregation seemed like the obvious next step. Instead of returning one row per star, the query could group stars into daily or weekly buckets, sort those buckets, and paginate the much smaller result.</p> <p class="wp-block-paragraph">The problem was where pagination happened. In a straightforward SQL query, the database first finds all stars for the repository, groups them into buckets, and sorts those buckets. For <code>react/react</code>, reading the full history that way would have meant examining roughly 6 million rows, because every one of the 24 requests would have reprocessed all of its stars. To reduce the query cost, we had to narrow the rows before aggregation began.</p> <h2 class="wp-block-heading" id="filtering-by-time-before-grouping">Filtering by time before grouping</h2> <p class="wp-block-paragraph">The design we shipped paginates star history by calendar week. For each request, it translates <code>page</code> and <code>per_page</code> into an indexed <code>created_at</code> range, filters the stars to those weeks, and then groups the matching records into daily counts. A response includes up to 30 weeks, and increasing <code>page</code> moves backward through the repository&rsquo;s history.</p> <div class="wp-block-code-wrapper"> <pre class="wp-block-code language-plaintext"><code>indexed date range -&gt; group rows in that range -&gt; daily buckets -&gt; response</code></pre> <svg class="octicon octicon-copy js-clipboard-copy-icon" height="16" version="1.1" viewBox="0 0 16 16" width="16" xmlns="http://www.w3.org/2000/svg"><path d="M0 6.75C0 5.784.784 5 1.75 5h1.5a.75.75 0 0 1 0 1.5h-1.5a.25.25 0 0 0-.25.25v7.5c0 .138.112.25.25.25h7.5a.25.25 0 0 0 .25-.25v-1.5a.75.75 0 0 1 1.5 0v1.5A1.75 1.75 0 0 1 9.25 16h-7.5A1.75 1.75 0 0 1 0 14.25Z"></path><path d="M5 1.75C5 .784 5.784 0 6.75 0h7.5C15.216 0 16 .784 16 1.75v7.5A1.75 1.75 0 0 1 14.25 11h-7.5A1.75 1.75 0 0 1 5 9.25Zm1.75-.25a.25.25 0 0 0-.25.25v7.5c0 .138.112.25.25.25h7.5a.25.25 0 0 0 .25-.25v-7.5a.25.25 0 0 0-.25-.25Z"></path></svg><svg class="octicon octicon-check js-clipboard-check-icon" height="16" version="1.1" viewBox="0 0 16 16" width="16" xmlns="http://www.w3.org/2000/svg"><path d="M13.78 4.22a.75.75 0 0 1 0 1.06l-7.25 7.25a.75.75 0 0 1-1.06 0L2.22 9.28a.751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018L6 10.94l6.72-6.72a.75.75 0 0 1 1.06 0Z"></path></svg></div> <p class="wp-block-paragraph">With the date range applied first, each request processes the weeks being returned instead of every current star in the repository. For tools, that means one request now covers up to 30 weeks of history, no matter how many stars the repository has. For <code>react/react</code>, that&rsquo;s about 24 requests instead of about 2,511, and the database examines each star about once (roughly 251,000 rows) across the full history. This fits the primary use case because maintainers usually inspect growth across weeks or around a known release, launch, or event. Week-based ranges also align with other repository activity APIs: the response follows the same shape as the <a href="https://docs.github.com/rest/metrics/statistics#get-the-weekly-commit-activity">weekly commit activity endpoint</a>, <code>GET /repos/{owner}/{repo}/stats/commit_activity</code>.</p> <p class="wp-block-paragraph">The time-range design limits each request to a defined period, but it does not limit the number of stars within that range. A week with an unusually large number of stars can therefore still produce a slow or expensive query. The normal request path no longer queries every current star, but exceptionally dense weeks remain a scaling limitation.</p> <p class="wp-block-paragraph">Comparing the performance of the old and new API paths also surfaced other places where GitHub was counting stars on demand. We found the same pattern on the repository stargazers page on GitHub.com and updated it to use the repository&rsquo;s cached star count. Slow queries from that page, which had numbered in the hundreds each week, dropped to zero. We recently shipped a similar fix to other stargazer API endpoints.</p> <p class="wp-block-paragraph">The chart below shows slow and killed stargazer count queries each week, by where they came from.</p> <b></b><b></b><b></b> <div class="ghchart" id="gh-chart-stargazer-slow-killed-queries"></div> <h2 class="wp-block-heading" id="h-what-we-learned">What we learned</h2> <ol class="wp-block-list"> <li><strong>A smaller response does not always mean a cheaper query.</strong> <code>LIMIT</code> and <code>OFFSET</code> reduced the number of results returned, but they did not reduce the grouping and sorting the database had already done. We had to look at the order in which the work happened.</li> <li><strong>Start with what people are actually trying to do.</strong> Maintainers needed to compare trends. A list of identities was simply how the old endpoint happened to provide the underlying data.</li> <li><strong>Return only what the use case needs.</strong> Anything more is data someone else can misuse. Once we understood the job, we could remove individual identities without taking away the information maintainers relied on.</li> <li><strong>Be clear about the tradeoffs that remain.</strong> The new endpoint is safer and more predictable, but calendar boundaries, removed stars, and unusually dense weeks still affect what it can return. Those details are part of the API contract too.</li> </ol> <p class="wp-block-paragraph">Restricting the original endpoint addressed the immediate problem. Listening to maintainers gave us something <strong>better</strong> than what we started with: star history that&rsquo;s easier to get, cheaper to serve, and safer for everyone who stars a project.</p> <div class="wp-block-group post-content-cta has-global-padding is-layout-constrained wp-block-group-is-layout-constrained"> <p class="wp-block-paragraph"><a href="https://docs.github.com/rest/activity/starring#get-repository-star-history">Get repository star history</a>, then share feedback in the <a href="https://github.com/orgs/community/discussions/206104">GitHub Community discussion</a>.</p> </div> <p>The post <a href="https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/">From 2,500 requests to 24: Rebuilding star history without the stargazers</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>
