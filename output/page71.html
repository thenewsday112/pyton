From 2,500 requests to 24: Rebuilding star history without the stargazers

📅 Oct 14, 2026  |  Category: World  |  Read Source →

<p class="wp-block-paragraph">Maintainers look at star history to answer a practical question: did a launch, release, or event change a project&rsquo;s trajectory? To reconstruct that curve from the GitHub API, tools had to request pages of stargazer records (each person who currently stars the repository and when they starred it), keep the timestamps, and throw the identities away.</p> <p class="wp-block-paragraph">Over time, that design created problems at both ends. Identities were available for bulk collection, so bad actors started scraping public stargazer lists for spam and phishing campaigns. For highly starred repositories, the endpoint could also make the database process many thousands of entries to return a single page.</p> <p class="wp-block-paragraph">The fix seemed clear: return counts instead of people. But returning less data didn&rsquo;t actually make the query any cheaper.</p> <p class="wp-block-paragraph">Now maintainers have a direct way to get the curve: we built an endpoint that returns up to 30 weeks of daily star counts in a single request, with no identities attached. Keeping that cheap to serve meant reducing how much data the database processed, not just how much it returned, and the endpoint does that by <strong>filtering stars by time before it counts anything</strong>.</p> <h2 class="wp-block-heading" id="h-what-maintainers-need-from-star-history">What maintainers need from star history</h2> <p class="wp-block-paragraph">We first addressed the immediate risks to developers and to our database by <a href="https://github.blog/changelog/2026-06-30-upcoming-access-restrictions-to-public-api-endpoints-and-ui-views/">restricting stargazer and watcher lists to repository administrators and collaborators</a>. After the access change, callers without the required permission could receive an empty response or a <code>403 Forbidden</code> response.</p> <p class="wp-block-paragraph">That change also cut off tools that had used the old response to calculate star history, often without displaying or otherwise using the usernames it returned. So we talked with maintainers and tool builders to understand what they still needed. They used star history as an approximate signal of interest: to compare activity before and after a release, or to see whether an announcement reached new developers. What they cared about was the curve.</p> <p class="wp-block-paragraph">The old API response had made identity look like part of that contract because every timestamp arrived attached to a user. In practice, tools such as Star History needed counts and dates, not usernames or other user data. Once identity was no longer part of the requirement, we could design an aggregate endpoint for the actual job: retrieving changes in star counts over time at a useful resolution.</p> <blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"> <p class="wp-block-paragraph">When the API change disrupted Star History, users rallied around the project. GitHub&rsquo;s Community team listened and connected us with product engineering, who dug into our use case and worked alongside us to design a purpose-built endpoint. A difficult situation became a constructive collaboration between GitHub, Star History, and the broader community&mdash;ultimately leading to a better solution.</p> <cite>Tianzhou Chen, star-history.com maintainer and Bytebase co-founder</cite></blockquote> <h2 class="wp-block-heading" id="why-the-original-endpoint-was-expensive">Why the original endpoint was expensive</h2> <p class="wp-block-paragraph">Once we knew what maintainers needed, the next step was understanding why the original design couldn&rsquo;t provide it cheaply. The original <code>GET /repos/{owner}/{repo}/stargazers</code> endpoint was built to answer a simple question: who starred this repository? It returned a paginated list of people, and if the request specified a custom media type, each entry also included when the star was created.</p> <p class="wp-block-paragraph">The star model was built for the same job. It records the current set of people who have starred a repository, which keeps showing a star count or a list of stargazers simple. It was not designed as a historical event log: when someone removes a star, that record is removed. When tools began using the list as a time series, reconstructing a growth curve meant retrieving individual identities and processing every current star. Because each page held at most 100 people, the work grew with the repository&rsquo;s popularity: building the full curve for <code>react/react</code>, with about 251,000 stars, took about 2,511 requests, so tools often ran into rate limits or sampled pages instead of reading them all.</p> <p class="wp-block-paragraph">Serving a page required the database to query the repository&rsquo;s current stars. Due to a bug in the pagination implementation, every request also counted all of those stars to work out how many pages existed, even though the caller received only one page of up to 100 people. On a highly starred repository, that meant counting many thousands of entries on every request. In the week before we restricted access, nearly 37,000 of these count queries ran slowly enough to be logged, averaging nearly 3 seconds each, and database safeguards killed more than 1,000 of them, which contributed to request timeouts.</p> <p class="wp-block-paragraph">The chart below shows what all that counting cost. After we restricted access, the database served about 60% fewer stargazer requests, and the total time it spent on the count query fell by about 80%.</p> <b></b><b></b><b></b><b></b> <div class="ghchart" id="gh-chart-total-query-duration"></div> <h2 class="wp-block-heading" id="approaches-we-considered">Approaches we considered</h2> <p class="wp-block-paragraph">Removing identities handled the privacy requirement. The harder part was keeping each request from scanning the repository&rsquo;s entire current star set.</p> <h3 class="wp-block-heading" id="keeping-events-without-identities">Keeping events without identities</h3> <p class="wp-block-paragraph">Our first spike kept one record per star and returned the <code>starred_at</code> value without the stargazer&rsquo;s identity for callers who lacked collaborator access. At first, this looked like the quickest path forward, because it directly served the request we had heard from tool builders. It also closed the identity-harvesting path with a relatively small change to the existing serialization and authorization flow.</p> <p class="wp-block-paragraph">This approach addressed identity exposure and would have allowed existing tools to keep working. But API consumers would still have to paginate through and process potentially many thousands of individual records to build an aggregate history. It also tied the new use case to an endpoint and pagination model designed for listing people rather than retrieving trends.</p> <h3 class="wp-block-heading" id="aggregating-then-paginating">Aggregating, then paginating</h3> <p class="wp-block-paragraph">Aggregation seemed like the obvious next step. Instead of returning one row per star, the query could group stars into daily or weekly buckets, sort those buckets, and paginate the much smaller result.</p> <p class="wp-block-paragraph">The problem was where pagination happened. In a straightforward SQL query, the database first finds all stars for the repository, groups them into buckets, and sorts those buckets. Returning fewer buckets would shrink the JSON response, but it would not reduce the expensive grouping and sorting the database had already performed. For <code>react/react</code>, reading the full history that way would have meant examining roughly 6 million rows, because every one of the 24 requests would have reprocessed all of its stars. To reduce the query cost, we had to narrow the rows before aggregation began.</p> <h2 class="wp-block-heading" id="filtering-by-time-before-grouping">Filtering by time before grouping</h2> <p class="wp-block-paragraph">The design we shipped paginates star history by calendar week. For each request, it translates <code>page</code> and <code>per_page</code> into an indexed <code>created_at</code> range, filters the stars to those weeks, and then groups the matching records into daily counts. A response includes up to 30 weeks, and increasing <code>page</code> moves backward through the repository&rsquo;s history.</p> <div class="wp-block-code-wrapper"> <pre class="wp-block-code language-plaintext"><code>indexed date range -&gt; group rows in that range -&gt; daily buckets -&gt; response</code></pre> <svg class="octicon octicon-copy js-clipboard-copy-icon" height="16" version="1.1" viewBox="0 0 16 16" width="16" xmlns="http://www.w3.org/2000/svg"><path d="M0 6.75C0 5.784.784 5 1.75 5h1.5a.75.75 0 0 1 0 1.5h-1.5a.25.25 0 0 0-.25.25v7.5c0 .138.112.25.25.25h7.5a.25.25 0 0 0 .25-.25v-1.5a.75.75 0 0 1 1.5 0v1.5A1.75 1.75 0 0 1 9.25 16h-7.5A1.75 1.75 0 0 1 0 14.25Z"></path><path d="M5 1.75C5 .784 5.784 0 6.75 0h7.5C15.216 0 16 .784 16 1.75v7.5A1.75 1.75 0 0 1 14.25 11h-7.5A1.75 1.75 0 0 1 5 9.25Zm1.75-.25a.25.25 0 0 0-.25.25v7.5c0 .138.112.25.25.25h7.5a.25.25 0 0 0 .25-.25v-7.5a.25.25 0 0 0-.25-.25Z"></path></svg><svg class="octicon octicon-check js-clipboard-check-icon" height="16" version="1.1" viewBox="0 0 16 16" width="16" xmlns="http://www.w3.org/2000/svg"><path d="M13.78 4.22a.75.75 0 0 1 0 1.06l-7.25 7.25a.75.75 0 0 1-1.06 0L2.22 9.28a.751.751 0 0 1 .018-1.042.751.751 0 0 1 1.042-.018L6 10.94l6.72-6.72a.75.75 0 0 1 1.06 0Z"></path></svg></div> <p class="wp-block-paragraph">With the date range applied first, each request processes the weeks being returned instead of every current star in the repository. For tools, that means one request now covers up to 30 weeks of history, no matter how many stars the repository has. For <code>react/react</code>, that&rsquo;s about 24 requests instead of about 2,511, and the database examines each star about once (roughly 251,000 rows) across the full history. This fits the primary use case because maintainers usually inspect growth across weeks or around a known release, launch, or event. Week-based ranges also align with other repository activity APIs: the response follows the same shape as the <a href="https://docs.github.com/rest/metrics/statistics#get-the-weekly-commit-activity">weekly commit activity endpoint</a>, <code>GET /repos/{owner}/{repo}/stats/commit_activity</code>.</p> <p class="wp-block-paragraph">The time-range design limits each request to a defined period, but it does not limit the number of stars within that range. A week with an unusually large number of stars can therefore still produce a slow or expensive query. The normal request path no longer queries every current star, but exceptionally dense weeks remain a scaling limitation.</p> <p class="wp-block-paragraph">Comparing the performance of the old and new API paths also surfaced other places where GitHub was counting stars on demand. We found the same pattern on the repository stargazers page on GitHub.com and updated it to use the repository&rsquo;s cached star count. Slow queries from that page, which had numbered in the hundreds each week, dropped to zero. We recently shipped a similar fix to other stargazer API endpoints.</p> <p class="wp-block-paragraph">The chart below shows slow and killed stargazer count queries each week, by where they came from.</p> <b></b><b></b><b></b> <div class="ghchart" id="gh-chart-stargazer-slow-killed-queries"></div> <h2 class="wp-block-heading" id="h-what-we-learned">What we learned</h2> <ol class="wp-block-list"> <li><strong>A smaller response does not always mean a cheaper query.</strong> <code>LIMIT</code> and <code>OFFSET</code> reduced the number of results returned, but they did not reduce the grouping and sorting the database had already done. We had to look at the order in which the work happened.</li> <li><strong>Start with what people are actually trying to do.</strong> Maintainers needed to compare trends. A list of identities was simply how the old endpoint happened to provide the underlying data.</li> <li><strong>Return only what the use case needs.</strong> Anything more is data someone else can misuse. Once we understood the job, we could remove individual identities without taking away the information maintainers relied on.</li> <li><strong>Be clear about the tradeoffs that remain.</strong> The new endpoint is safer and more predictable, but calendar boundaries, removed stars, and unusually dense weeks still affect what it can return. Those details are part of the API contract too.</li> </ol> <p class="wp-block-paragraph">Restricting the original endpoint addressed the immediate problem. Listening to maintainers gave us something <strong>better</strong> than what we started with: star history that&rsquo;s easier to get, cheaper to serve, and safer for everyone who stars a project.</p> <div class="wp-block-group post-content-cta has-global-padding is-layout-constrained wp-block-group-is-layout-constrained"> <p class="wp-block-paragraph"><a href="https://docs.github.com/rest/activity/starring#get-repository-star-history">Get repository star history</a>, then share feedback in the <a href="https://github.com/orgs/community/discussions/206104">GitHub Community discussion</a>.</p> </div> <p>The post <a href="https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/">From 2,500 requests to 24: Rebuilding star history without the stargazers</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>

<p>The United Kingdom has issued economic sanctions against <strong>Cryptomus</strong>, a chameleonic cryptocurrency platform that experts say serves as a major conduit for payments related to ransomware, narcotics, darknet markets, fraud and cybercrime services that are helping Russia circumvent existing financial restrictions.</p> <div class="wp-caption aligncenter" id="attachment_74482" style="width: 758px;"><img alt="" class=" wp-image-74482" height="378" src="https://krebsonsecurity.com/wp-content/uploads/2026/10/heleketsupportbot.png" width="748" /><p class="wp-caption-text" id="caption-attachment-74482">Heleket&#8217;s support agent on Telegram claims, despite all evidence to the contrary, that it is not affiliated with Cryptomus. The sanctions freeze any Cryptomus assets at U.K. banks, and bar British companies from offering it any business, virtual or otherwise. Also targeted in these sanctions were the virtual payment platforms <strong>VexPay</strong>, <strong>TokenSpot</strong>, and the <strong>Tsunami Payments service</strong>.</p> <p>As explained in our December 2024 investigation, &#8220;<a href="https://krebsonsecurity.com/2024/12/how-cryptocurrency-turns-to-cash-in-russian-banks/" rel="noopener" target="_blank">How Cryptocurrency Turns to Cash in Russian Banks</a>,&#8221; Cryptomus has been a key payment processor for dozens of Russian cryptocurrency exchanges and websites hawking cybercrime services. The company has changed its name several times since emerging in 2022, most recently to &#8220;<strong>Heleket</strong>&#8221; last year after Canada levied <a href="https://krebsonsecurity.com/2025/10/canada-fines-cybercrime-friendly-cryptomus-176m/" rel="noopener" target="_blank">a record CAD $176 million fine</a> against the platform for anti-money laundering violations.</p> <p>The blockchain data-crunching firm <strong>Chainalysis</strong> said the U.K. sanctions target the broader infrastructure supporting Russia&#8217;s wartime economy.</p> <p>&#8220;Cryptomus and Heleket have emerged as major payment hubs for illicit activity,&#8221; Chainalysis <a href="https://www.chainalysis.com/blog/uk-sanctions-cryptomus-heleket-tokenspot/" rel="noopener" target="_blank">wrote</a> in an October 8 blog post. &#8220;Together, these services received more illicit funds across tracked categories than the mixers in our dataset and the number of illicit counterparties surged to more than 900 in a single month in late 2025.&#8221;</p> <div class="wp-caption aligncenter" id="attachment_74472" style="width: 759px;"><a href="https://krebsonsecurity.com/wp-content/uploads/2026/10/cryptomus-bot-down.png" rel="noopener" target="_blank"><img alt="" class="wp-image-74472" height="538" src="https://krebsonsecurity.com/wp-content/uploads/2026/10/cryptomus-bot-down.png" width="749" /></a><p class="wp-caption-text" id="caption-attachment-74472">The Cryptomus support bot on Telegram, responding on Oct. 8 to an inquiry by saying the platform was suddenly unable to process transactions.</p></div> <p>In April 2026, the blockchain analysis firm <strong>TRM Labs</strong> <a href="https://www.trmlabs.com/resources/intel-library/cryptomus" rel="noopener" target="_blank">found</a> Cryptomus had processed more than $7 billion in transactions since its inception in 2022, including transactions associated with child sexual abuse material vendors, terrorist financing networks, and human trafficking operations.</p> <p>TRM noted that Cryptomus&#8217;s transaction volume cratered after the platform instituted new &#8220;know your customer&#8221; or KYC rules, and that the cryptocurrency platform responded to the Canadian fines by launching Heleket as a parallel service that continued to offer no-KYC payment processing.<span id="more-74435"></span></p> <p><strong>Richard Sanders</strong> is a blockchain analyst and investigator who spent months mapping out Cryptomus&#8217;s payment infrastructure and transacting with its customers. Sanders said the U.K. sanctions on Cryptomus are important because Canada&#8217;s fine against the platform was ultimately unenforceable and uncollectible.</p> <p>&#8220;A fine doesn&#8217;t stop a cryptocurrency payment processor from processing payments,&#8221; Sanders <a href="https://lnkd.in/p/e4EkbB-x" rel="noopener" target="_blank">wrote on LinkedIn</a>. &#8220;Sanctions kill the operation. We are now facing two generational transformations that are fundamentally reshaping how we view the cybersecurity landscape:</p> <ol class="wp-block-list" start="1"> <li class="wp-block-list-item"><strong>AI is increasing the speed and scale of cyberattacks</strong><br /><br />AI-orchestrated attacks are increasing the scale, speed, and sophistication of attacks, giving adversaries new ways to operate and compressing the time between vulnerability discovery and exploitation. These capabilities amplify risks such as credential theft, key exfiltration, and signing abuse.<br /><br /><a href="https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management" rel="noopener noreferrer" target="_blank">Keys and credentials are high-value control assets</a>. When compromised, they can enable attackers to impersonate trusted entities, bypass security controls, authorize malicious operations, expose sensitive data, and undermine software security defenses. Protecting these assets requires infrastructure with layered, hardened protections capable of withstanding sustained attacks across multiple concurrent attack vectors.</li> </ol> <ol class="wp-block-list" start="2"> <li class="wp-block-list-item"><strong>Quantum computing is changing the cryptographic risk horizon</strong><br /><br />Quantum computing promises transformative advances, but it also presents a risk to many of today’s cryptographic algorithms. <a href="https://www.microsoft.com/en-us/research/project/post-quantum-cryptography/" rel="noopener noreferrer" target="_blank">A sufficiently powerful quantum computer could break widely used public-key cryptography</a>, undermining digital signatures, authentication, and identity verification.<br /><br />Post-quantum cryptography was once viewed as an important but distant technology shift. Advances in quantum computing have changed that perspective as organizations recognize the urgency, scale, and complexity of the transition. <a href="https://techcommunity.microsoft.com/category/post-quantum-crypto-tech/blog/post-quantum-crypto-tech-blog" rel="noopener noreferrer" target="_blank">HSM-backed signing infrastructure will be among the first critical systems to migrate</a>, requiring HSMs that support post-quantum cryptography and are interoperable with classical HSMs to support migration.</li> </ol> <p class="wp-block-paragraph">These emerging threats motivated the development of <a href="https://learn.microsoft.com/en-us/azure/security/fundamentals/azure-integrated-hardware-security-module-overview" rel="noopener noreferrer" target="_blank">Azure Integrated HSM</a>, which was designed to meet rigorous security standards for hardware-based key protection, while also accelerating Microsoft&#8217;s transition to post-quantum cryptography through scale deployments of quantum resilient integrated HSMs.</p> <p class="wp-block-paragraph"><a href="https://github.com/microsoft/AziHSM-Guest" rel="noopener noreferrer" target="_blank">Azure Integrated HSM</a> introduced a workload-attached HSM that performs cryptographic operations closer to the workload while keys remain continuously protected within the HSM security boundary. This architecture strengthens key protection, improves cryptographic performance, offers crypto-agility, and provides a simpler operational model.</p> <p class="wp-block-paragraph">Tessera is an evolution of Azure’s first integrated HSM model, incorporating insights gained from deploying Azure Integrated HSM at scale, and advances the technology through collaboration in the Open Compute Project, with the goal of broadly addressing the challenges of key and credential management in the era of AI and quantum computing.</p> <h2 class="wp-block-heading" id="eliminating-key-management-anti-patterns"><strong>Eliminating key management anti-patterns</strong></h2> <p class="wp-block-paragraph">In central HSM deployment models, HSM infrastructure is separate from compute resources, requiring cryptographic operations to traverse the network. The resulting latency and operational dependencies can lead enterprises to adopt workarounds that improve performance or availability but unintentionally weaken key protections. Some of these common key-management anti-patterns include:</p> <ul class="wp-block-list"> <li class="wp-block-list-item">HSM keys may act as certificate authorities and endorse externally generated keys. These keys can then serve as trusted delegates without receiving the same hardware protection. </li> </ul> <ul class="wp-block-list"> <li class="wp-block-list-item">HSM generated keys may be created as extractable and exported from the HSM in wrapped form. When used outside of the HSM the keys may not receive assurance levels equivalent to a FIPS 140-3 Level 3 HSM and become more susceptible to exfiltration or misuse. </li> </ul> <p class="wp-block-paragraph">Other anti-patterns include caching keys outside of HSMs for resilience, using software-held keys to reduce network latency to remote HSMs, sharing keys and security domains to simplify governance, and relying on proprietary protocols for interoperability. These practices intend to prioritize operational flexibility but can make key protection, policy enforcement, and auditable provenance less consistent across environments, undermining the security value HSMs are designed to provide. </p> <p class="wp-block-paragraph">The goal of Project Tessera is to advance the integrated HSM model to address these challenges in the industry, without compromising on security. <p>Today, we’re announcing <a href="https://aws.amazon.com/lambda/lambda-web-functions/">AWS Lambda Web Functions</a>, a new form factor that lets you run standard HTTP web applications on Lambda without rewriting your code into an event handler. You can take a standard port-listening server built with Express, Hono, Fastify, Next.js, or any Node.js framework, deploy it with a single command, and Lambda automatically handles scaling, multi-region distribution, and active CPU billing. No adapters, no infrastructure to manage, and no framework lock-in.</p> <p>With this launch, AWS Lambda now offers three distinct form factors, each built on the same Firecracker isolation technology and designed for a different programming model.</p> <p><strong>Lambda Event Functions</strong> are what you already know as Lambda functions. They use the event-driven, single-concurrent handler model with wall-clock billing. We’re introducing the “Event Functions” name to highlight that programming model: your function receives an event, processes it, and returns a response. The event-driven programming model is ideal for event processing, queue consumers, and invocations triggered by other AWS services.</p> <p><strong>Lambda Web Functions</strong> use an HTTP-native programming model with multi-concurrent execution and active CPU billing. Your code listens on a port and handles standard HTTP requests. That programming model is ideal for web applications, API backends, and interactive HTTP workloads where multiple concurrent requests and I/O-heavy processing are the norm.</p> <p><strong>Lambda MicroVMs</strong> provide isolated, stateful sandbox environments with customer-managed lifecycles for running untrusted or user-generated code.</p> <p>The three complement each other. An application might use Event Functions for asynchronous backend processing, Web Functions for the user-facing API and server-side rendering layer, and MicroVMs for interactive code execution features, all within the same AWS account and sharing the same operational model.</p> <p><span style="text-decoration: underline;"><strong>Why Web Functions<br /> </strong></span>Modern web applications need to serve global audiences with fast, consistent response times while giving developers the freedom to use standard frameworks and iterate quickly. Building this today typically requires assembling multiple infrastructure components, configuring multi-region deployments, setting up latency-based routing, and tuning billing models to avoid paying for I/O wait. Developers often find themselves adapting their application code to fit a specific compute model rather than deploying the HTTP server they already have.</p> <p>Lambda Web Functions removes this complexity. Each execution environment handles multiple requests simultaneously (up to 128 concurrent requests per environment), which means a burst of incoming traffic can share warm environments instead of mapping each request to a new one. Web Functions meter the CPU time your code uses, so time spent waiting on a database query or an API call consumes little CPU. Memory is metered for as long as the execution environment exists. For I/O-heavy web workloads like server-side rendering, API backends, and AI inference endpoints streaming token responses, this can reduce compute costs.</p> <p><span style="text-decoration: underline;"><strong>Let’s try it out<br /> </strong></span>To get started, I wrote a simple Express.js server. This is the same code I run locally with <code>node index.js</code>, no Lambda-specific adapters or wrappers required.</p> <pre><code class="language-javascript">import express from 'express'; const app = express(); const [host, port] = process.env.AWS_LAMBDA_HTTP_ENDPOINT.split(':'); app.get('/', (req, res) =&gt; { res.json({ message: 'Hello from Lambda Web Functions!' }); }); app.listen(port, host, () =&gt; { console.log(`Server running on port ${port}`); }); </code></pre> <p>The only difference from running locally is the <code>AWS_LAMBDA_HTTP_ENDPOINT</code> environment variable, which Lambda sets to the host and port your server must listen on. To run locally, set it yourself, for example <code>AWS_LAMBDA_HTTP_ENDPOINT=127.0.0.1:3000 node index.js</code>.</p> <p>With my code ready, I deployed using the <a href="https://aws.amazon.com/cli/">AWS Command Line Interface (AWS CLI)</a>:</p> <pre><code>aws lambda-web deploy --name my-web-app --code ./my-app </code></pre> <p>One command. No prior resource setup. The CLI bundled my source, created the Web Function, published its first revision, attached a Web Function endpoint, and returned a live HTTPS URL in under a minute.</p> <p>A revision is an immutable snapshot of the code I deployed. The endpoint is the HTTPS URL that routes traffic to a revision, or splits traffic across revisions. Those are the resources I use to iterate and to control how traffic moves to new code.</p> <p>I tested it immediately:</p> <pre><code>$ curl https://&lt;domain-id&gt;.&lt;shard-id&gt;.lambda-web.us-east-1.on.aws/ {"message":"Hello from Lambda Web Functions!"} </code></pre> <p>Next, I wanted my application to serve users in Europe and Asia with lower latency. I redeployed with multiple regions:</p> <pre><code>aws lambda-web deploy --name my-web-app --code ./my-app \ --regions us-east-1,eu-west-1,ap-northeast-1 </code></pre> <p>Lambda Web Functions replicated my code to all three regions and configured latency-based routing automatically. Each request now routes to the Region with the lowest latency for the caller, on a best-effort basis, through one global URL (<code>&lt;domain-id&gt;.lambda-web.global.on.aws</code>).</p> <p>When I updated my code and ran the same deploy command again, the CLI detected the existing function, uploaded the new revision, and pointed the endpoint at it. Total turnaround from code change to live: seconds.</p> <p>For production workflows that require a more gradual rollout, I can shift traffic between revisions with a single API call:</p> <pre><code>aws lambda-web update-web-function-endpoint \ --function-name my-web-app \ --endpoint-name dev \ --auto-deployment-mode Disabled \ --revision-weights '[{"revisionId": "&lt;current-revision-id&gt;", "weight": 90}, {"revisionId": "&lt;new-revision-id&gt;", "weight": 10}]' </code></pre> <p>This sends 90% of endpoint traffic to the current revision and 10% to the new one, giving me a canary deployment without additional tooling.</p> <p><span style="text-decoration: underline;"><strong>Better together with Amazon CloudFront<br /> </strong></span>For applications that combine static and dynamic content, Web Functions works well alongside <a href="https://aws.amazon.com/cloudfront/">Amazon CloudFront</a>. You can select a Web Function endpoint as the origin for your CloudFront distribution. Static assets are served from the cache while dynamic requests route to your Web Function, giving you CDN performance for static content with serverless compute for the dynamic parts.</p> <p>Web Functions improves the private-origin experience with CloudFront.&nbsp;With this launch, you attach CloudFront <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-origin.html">origin access control (OAC)</a> to a Web Function endpoint instead. CloudFront signs requests to the origin, and the endpoint allows only your distribution to invoke it. You get the same private-origin pattern CloudFront already provides for <a href="https://aws.amazon.com/s3/">Amazon Simple Storage Service (Amazon S3)</a>, without exposing the endpoint or adding custom authorization to your app.</p> <p><span style="text-decoration: underline;"><strong>Now available<br /> </strong></span>AWS Lambda Web Functions is available today in US East (N. Virginia), US East (Ohio), US West (Oregon), Asia Pacific (Tokyo), and Europe (Ireland). Web Functions run Node.js 24 (nodejs24.x) on Arm64 at launch and support Amazon Virtual Private Cloud (VPC) connectivity, allowing your function to access resources that exist within a VPC.</p> <p>To get started, deploy your first Web Function in under a minute:</p> <pre><code>aws lambda-web deploy --name hello-world --hello-world </code></pre> <p>For pricing details, visit the <a href="https://aws.amazon.com/lambda/pricing/">AWS Lambda pricing page</a>. To learn more, see the <a href="https://docs.aws.amazon.com/lambda/latest/dg/web-functions.html">Lambda Web Functions documentation</a>.</p>
