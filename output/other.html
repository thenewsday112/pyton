Make Playwright Email Tests Explain Their Waits

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Email verification tests often fail in a confusing way: the browser is on the right page, the message eventually arrives, and the test still reports only Timeout 30000ms exceeded.

That error is not a diagnosis. It does not tell you whether the application never sent the message, the inbox query used the wrong address, the provider was slow, or the assertion looked for an old message. When an email test is part of a Playwright suite, the wait itself should leave evidence.

The symptom: a test that waits but cannot explain why

A common first draft looks roughly like this:

await page.getByRole('button', { name: 'Create account' }).click(); await inbox.waitForMessage({ subject: 'Verify your email' }); await expect(page.getByText('Account verified')).toBeVisible();

The code is readable, but waitForMessage may hide several different operations. It may create an inbox, poll a mailbox, filter messages, and extract a link. If all of those steps share one timeout, the failure has no useful boundary.

I prefer a test to answer four questions: which mailbox was allocated, when was the message expected, what messages were observed, and why did the final candidate pass or fail? This is especially important when a team searches for phrases such as “temp mail so” or “temp mail email” while comparing test-inbox options. The search phrase is not a test contract; the observable message is.

Model the email flow as observable states

Treat the inbox interaction as a small state machine rather than one long sleep:

  1. allocated: the test owns a unique address.
  2. triggered: the application accepted the signup request.
  3. observed: at least one message was returned.
  4. matched: the message has the expected sender, subject, and correlation value.
  5. consumed: the verification link was opened once.

Each state should have a timestamp and a small diagnostic payload. If a run reaches observed but never reaches matched, you have a filtering or application-content problem. If it never reaches observed, investigate delivery, the sender, or the inbox service. The distinction saves a surprising amount of re-running.

Build a bounded inbox probe

The probe should poll at a fixed interval, stop at a deadline, and return the messages it saw. Do not use an unbounded retry helper that turns every failure into “try again.” A bounded probe makes the delivery timeout a visible part of the test design.

type ProbeResult = { state: 'matched' | 'timed-out'; messageId?: string; seenSubjects: string[]; }; async function waitForVerification( inbox: InboxClient, address: string, token: string, deadlineMs = 20_000, ): Promise<ProbeResult> { const started = Date.now(); const seenSubjects = new Set<string>(); while (Date.now() - started < deadlineMs) { const messages = await inbox.list({ to: address }); for (const message of messages) { seenSubjects.add(message.subject); if (message.text.includes(token)) { return { state: 'matched', messageId: message.id, seenSubjects: [...seenSubjects] }; } } await new Promise((resolve) => setTimeout(resolve, 1_000)); } return { state: 'timed-out', seenSubjects: [...seenSubjects] }; }

The exact inbox client will differ, but the shape is portable. Notice that the probe returns subjects even on timeout. A timeout with an empty list points in a different direction than a timeout where three unrelated messages arrived.

Capture evidence at every decision

Attach the probe result to the Playwright test, along with the allocated address, correlation token, and trigger timestamp. Keep the message body out of ordinary logs if it can contain user data; a subject, message ID, and redacted excerpt are usually enough.

It also helps to record the application request ID. That gives you a join between browser actions, server logs, and inbox data. For CI, save this small JSON object as an artifact:

{ "address": "run-1842@example.test", "triggeredAt": "2026-10-31T11:20:00Z", "state": "timed-out", "seenSubjects": ["Welcome"], "requestId": "signup-7f2a" }

This same one-change-set thinking for CI infrastructure is useful when the test depends on more than the browser; a related example is one-change-set thinking for CI infrastructure. The goal is not to collect every log, but to preserve the smallest chain of evidence that explains a failure.

A Playwright example

The test can now make the failure boundary explicit:

const mailbox = await inbox.allocate(`pw-${test.info().workerIndex}`); const token = crypto.randomUUID(); await page.getByLabel('Email').fill(mailbox.address); await page.getByLabel('Signup token').fill(token); await page.getByRole('button', { name: 'Create account' }).click(); const result = await waitForVerification(inbox, mailbox.address, token); await test.info().attach('email-probe.json', { body: JSON.stringify({ address: mailbox.address, token, result }, null, 2), contentType: 'application/json', }); expect(result.state, `Inbox subjects: ${result.seenSubjects.join(', ')}`).toBe('matched');

If several tests can trigger the same mailbox, queue email checks instead of duplicating them, as shown in queue email checks instead of duplicating them. A unique lease per test is simpler, but queueing can be the safer option when the provider has strict limits.

Failure analysis checklist

When this test fails, check the evidence in this order:

  • No messages observed: verify the sender accepted the request, the test address is correct, and the inbox provider is reachable from CI.
  • Messages observed, no match: inspect subject filters, token generation, and whether an older message was selected.
  • Match found, link fails: check URL environment, link expiry, and whether the link was already consumed by a retry.
  • Only parallel runs fail: look for reused addresses, shared inbox filters, or a race in cleanup.
  • Failures appear randomly: compare delivery latency and polling deadlines before adding retries.

Small search typos such as temp gamil com should stay out of selectors and assertions. They can be useful as plain-text content only when you are explicitly testing search or input normalization; otherwise they add noise.

Keep the wait boring and repeatable

Reliable email testing is less about finding a magic timeout and more about giving every wait a purpose. Allocate a mailbox, trigger one action, poll within a deadline, record what appeared, and assert on a correlation value. The test don't need to be clever; it needs to make the next failure understandable.

That workflow turns flaky email verification from a vague browser timeout into a bounded QA signal. Once the evidence is stable, you can tune delivery budgets with confidence instead of hiding the problem behind another retry.

Two Redis Ports, One TLS Boundary

A Redis Cluster node can expose a client port and a cluster bus port. The first carries application commands; the second carries node-to-node cluster traffic. Enabling TLS only for application clients leaves a second network path that deserves its own review.

The cluster bus is a separate path

Redis documentation describes each cluster node as needing a client TCP port, commonly 6379, and a cluster bus port. The bus port is used for cluster communication. It is not an ordinary application endpoint, even when it is reachable from the same network segment.

The TLS documentation states that tls-cluster yes enables TLS for the cluster bus and cross-node connections when Redis Cluster is used. Replication links are another communication path. Teams should check the relevant replication setting as well if replicas are part of the deployment.

The practical consequence is that a network scan can find two listeners and report different protocol behavior. A client certificate policy on the application endpoint does not automatically describe the cluster bus. Inventory both ports, the listening addresses, and the certificate or key material used by each node.

Shared names are not shared trust

Cluster nodes need a consistent view of node identity and reachability. Certificate names, client authentication requirements, and address announcements can affect both security and cluster formation. Changing a certificate can break a node's connection to peers even when ordinary clients still connect.

Use a test cluster with the same node count and network layout as production, if possible. Verify peer discovery, failover, and a rolling restart. Check that a node rejects a client certificate it should not trust. Then check cluster traffic from an address that should not be a member. Test both client and peer paths before treating the rollout as complete.

Avoid placing files with cluster credentials or private keys in a container layer that is copied to every role. Mount them with the right ownership and rotate them through a process that accounts for all nodes. Keep the private key out of logs and command arguments.

Announcement addresses need review

Redis Cluster is sensitive to how nodes announce addresses and ports. A setting that works inside one Docker network may produce an address that remote clients or peers cannot reach. This can lead an operator to broaden firewall rules until the cluster works, which is a poor way to discover the intended network boundary.

Record the announced address, client address, and bus address separately. Compare them with the DNS names and network policies used by applications. If a proxy or NAT layer changes the path, document the translation and test from both sides.

A rollout checklist

  1. Confirm that the client and bus ports are both in the asset inventory.
  2. Review tls-cluster and replication TLS settings on every node.
  3. Verify certificate names, trust roots, and client-authentication policy.
  4. Test peer join, failover, and restart on a disposable cluster.
  5. Test denied peer and client paths from outside the intended networks.
  6. Keep a rollback node configuration and a certificate rollback path.

After rollout, monitor for nodes that repeatedly join and leave or report certificate errors. A cluster that appears healthy from one node can still have one peer using a weaker path. The useful evidence is a complete map of listeners and a tested rejection for each path, with no unencrypted bus ports left behind.

  • Redis TLS documentation
  • Redis cluster specification

Our maintenance mode is one boolean in a TypeScript file, and it taught us that our sign-in pages are not public

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Nakodo has a maintenance mode. The whole of it is this file, src/lib/maintenance.ts, 15 lines:

// On while the database is down for maintenance; off again, and deployed, once // it's back. While on: // - the app and the sign-in pages show /maintenance instead (src/proxy.ts), so // nobody can sign up, sign in or change anything; // - the crons skip their runs (src/lib/cron.ts); the first run after it's off // picks the work up where it was left; // - Stripe's and Resend's webhooks answer 503, so they send the event again // later, and the other endpoints that need the database answer 503 too; // - creators' opt-out and unsubscribe links say to come back later. // The public pages stay up: they never touch the database. export const MAINTENANCE = false; export function maintenanceResponse(): Response { return new Response("Down for maintenance", { status: 503, headers: { "Retry-After": "600" } }); }

No feature flag service, no environment variable, no row in a table. A constant, read in ten places, and changing it is a commit and a deploy.

It has been true once, on 12 October 2026, for 23 minutes. Both flips are in the history:

8efb633 2026-10-12 15:05:09 Add maintenance mode for database downtime 5bd22d3 2026-10-12 15:28:33 Disable maintenance mode

The ten call sites

Writing a kill switch is easy. Deciding what it means is the work, and it means something slightly different in each of the ten places that read it.

The proxy, first, because it covers everything a browser asks for:

if (MAINTENANCE) { const path = request.nextUrl.pathname; if (isPublicPath(path) && !isSignInPath(path)) return NextResponse.next(); if (path.startsWith("/api/")) return maintenanceResponse(); return NextResponse.rewrite(new URL("/maintenance", request.url)); }

Three answers in three lines: public pages carry on, API routes get the 503, everything else is rewritten to a page that says we will be back. A rewrite rather than a redirect, so the URL the visitor came for stays in the address bar and works when they reload it later.

The cron jobs, through one function:

export async function cronSkipReason(): Promise<string | null> { if (MAINTENANCE) return "maintenance"; try { await withTimeout(db.execute(sql`select 1`), 10_000, () => new Error("timed out")); return null; } catch (e) { console.error("cron: the database isn't answering, skipping this run", e); return "database unreachable"; } }

Two reasons to skip, and the flag is the cheap one: it costs no round trip. The important property is that a skipped run starts nothing, so nothing is left half done, and the queue is picked up by the next run as if the gap had not happened. Two of the four crons run every five minutes, so a 23-minute window is about nine skipped runs between them.

The two webhook endpoints, which get the 503 for a specific reason. Both Stripe and our mail provider retry a failed delivery with backoff, so a 503 means "ask again" and the event is not lost. A 200 with the body thrown away would be a lost subscription change or a lost bounce. This is the one place where answering with an error is the careful behaviour and answering successfully is the destructive one.

The two public pages behind email links, the opt-out page and the unsubscribe page, which render a different component:

if (MAINTENANCE) return <BackSoon />;

These are the ones I care most about, because the person clicking them did not choose a moment. They are 20 lines of "this link cannot do anything right now, open it again in a little while", with no form and no database read, and they are the reason the one-click endpoints answer 503 rather than pretending: a mail client that gets a 503 from a one-click unsubscribe will show the user that it failed, which is correct, instead of telling them they are unsubscribed when nothing was written.

The refactor it forced

The commit that added all this also changed a file that has nothing to do with maintenance, and that change is the most durable thing to come out of the feature:

const PUBLIC_PREFIXES = [ ... - "/login", - "/forgot-password", - "/reset-password", - "/auth/", ]; +const SIGN_IN_PREFIXES = ["/login", "/forgot-password", "/reset-password", "/auth/"]; + export function isPublicPath(path: string): boolean { - return PUBLIC_EXACT.has(path) || PUBLIC_PREFIXES.some((p) => path.startsWith(p)); + return PUBLIC_EXACT.has(path) || [...PUBLIC_PREFIXES, ...SIGN_IN_PREFIXES].some((p) => path.startsWith(p)); +} + +// The sign-in flow: public, but it needs the database. +export function isSignInPath(path: string): boolean { + return SIGN_IN_PREFIXES.some((p) => path.startsWith(p)); }

Before that commit, "public" meant one thing in this codebase: no session required. The auth boundary only ever asked that question, so one list was enough.

Maintenance mode needs a different question: does this page need the database. Those two sets overlap but are not the same, and the login page is exactly where they come apart. It is public, anybody can open it, and it is useless while the database is down, because signing in writes a session and reads a profile.

So now there are two predicates. isPublicPath answers the auth question and still includes the sign-in pages. isSignInPath carves out the four prefixes that are public but database-dependent. The proxy's maintenance branch is the only caller that needs both, and the line reads exactly like the sentence that justifies it: public, and not sign-in.

I would not have found that distinction by thinking about it. I found it by needing the app to be half up.

The page that refuses to exist while the app is up

export default function MaintenancePage() { if (!MAINTENANCE) redirect("/login"); ...

The maintenance page guards itself, which means the flag is checked twice on the same request: once in the proxy to decide to rewrite there, once in the page to decide whether it is allowed to render.

That is not belt-and-braces for its own sake. Without the guard, /maintenance would be a real, reachable, indexable page claiming the app is down, at all times, for anybody who guessed the URL. With it, the URL only means anything during a window.

You can check the current state from outside:

$ curl -sI https://nakodo.app/maintenance | grep -i location location: /login?next=%2Fmaintenance

That redirect is actually the other layer talking. /maintenance is not in the public path list, so a signed-out request to it is sent to the login page by the normal auth check before the page runs at all. A signed-in visitor gets there and the page's own guard sends them to the same place. Two different mechanisms, one destination, and either way the answer is "there is nothing here right now", which is the truth.

Why a constant and not a flag service

The obvious objection to a committed boolean is that turning it on requires a build. On this project that is a deploy of a couple of minutes, and it has a property I have come to want: the switch leaves a commit, with a timestamp and a message, in the same history as everything else. The two lines above are a complete incident record.

The alternatives I did not take, and why:

  • an environment variable would also need a redeploy on our host for a running deployment to see it, so it costs the same couple of minutes and leaves no record;
  • a flag in Redis would be instant, and would put the switch in a second service that can have its own bad day, while the thing we are defending against is the database being unavailable;
  • a flag in the database is obviously circular.

What a constant cannot do is be flipped by somebody who cannot deploy, or be flipped automatically when the database goes down on its own. The second one is a real gap, and it is partly covered by the select 1 in cronSkipReason above: the background work stops by itself when the database stops answering, whether or not anybody set the flag. The pages behind the login do not, and a visitor during an unplanned outage gets an error boundary rather than the polite page. If I were to extend this, that is the piece I would build next, and it would not be a nicer switch: it would be the proxy noticing.

What stays up

The 76 pages in the sitemap are unaffected by any of this, and the schema comment that promises it is checkable:

$ grep -rl "@/db" "src/app/(marketing)" src/content | wc -l 0

Not one file under the marketing routes or the content directory imports the database. The guides, the pricing page, how it works and every niche page are built from arrays in the repository at deploy time, so they are not "up because the database is up", they are up because they have never needed it. That is what the proxy's first branch is protecting: during the 23 minutes in October the public half of the site was serving exactly what it serves now.

That is the real shape of a maintenance mode, and it is mostly not the switch. It is knowing, per route, which of the two questions you are asking: does this need a user, or does this need the data.

One installer filename lives in three files, and the version number lives in a header nothing reads

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Notifio ships three installers: one NSIS setup for Windows and two DMGs for Mac, because a universal build would bundle two copies of Chromium. They are built locally, uploaded to Cloudflare R2 under fixed object keys, and served through an API route that presigns a URL and redirects to it.

That means one filename, notifio-arm64.dmg, has to be written identically in three files that know nothing about each other.

The triangle

First, electron-builder decides what the file on disk is called:

"mac": { "target": [{ "target": "dmg", "arch": ["arm64", "x64"] }], "artifactName": "notifio-${arch}.dmg" }, "win": { "target": ["nsis"], "artifactName": "notifio-setup.exe" }

Second, the release script decides what to upload and under what key, and its comment is doing all of the work that a type would otherwise do:

// Artifact name -> content type. Names must match package.json build.artifactName // and the FILES map in server/src/app/api/download/[platform]/route.ts. const ARTIFACTS = { win: [{ file: 'notifio-setup.exe', contentType: 'application/octet-stream' }], mac: [ { file: 'notifio-arm64.dmg', contentType: 'application/x-apple-diskimage' }, { file: 'notifio-x64.dmg', contentType: 'application/x-apple-diskimage' }, ], };

Third, the web app decides which key to presign for a given download button:

const FILES: Record<string, string> = { "mac-arm64": "notifio-arm64.dmg", "mac-x64": "notifio-x64.dmg", win: "notifio-setup.exe", };

Three files, two packages, one of them a desktop app and one a Next.js site, and the only thing keeping them in step is a sentence in a comment. Change artifactName and the build succeeds, the upload succeeds for the two files that still match, and the third fails with "Artifact missing" if you are lucky or uploads nothing if you changed all of them. Change only the download route and the build and upload both pass, and the download page serves a 403 from R2 for a key that is not there.

In fairness to the release script, it does not take electron-builder's word for anything. It checks that each expected artifact exists and that it was modified during this run:

const stat = fs.statSync(full); if (stat.mtimeMs < buildStart - 5000) { fail( `${file} was not rebuilt (last modified ${stat.mtime.toISOString()}).\n` + ' The build reported success but produced no new artifact.' ); }

So a renamed artifact is caught on the build side. It is the web side that has no idea.

The keys are fixed, so a release overwrites

The comment at the top of the release script states the consequence rather than burying it:

/** * R2 object keys are fixed (the download API serves them by name), so a release * overwrites the previous one. See RELEASES.md. */

There is a --archive flag that also uploads notifio-setup-1.1.0.exe alongside, and it is opt-in and off by default. So in the normal case there is exactly one copy of each installer and no history, which means no rollback: shipping a broken build and shipping the fix are the same operation at the same key.

What I did not appreciate until I went looking is that every upload records its version anyway:

const res = runAws([ 's3', 'cp', local, `s3://${r2.bucket}/${key}`, '--endpoint-url', r2.endpoint, '--content-type', contentType, '--metadata', `version=${version}`, ... ], r2);

And reads it back as part of the verify step, comparing the remote size against the local one:

if (head.ContentLength !== size) { fail(`Size mismatch for ${key}: local ${size} bytes, remote ${head.ContentLength} bytes`); } const remoteVersion = head.Metadata?.version ?? '?'; info(`\x1b[32mok\x1b[0m ${key} ${humanSize(head.ContentLength)} version=${remoteVersion}`);

That is the only code in either package that reads it. The download route presigns a GET and redirects. It does not look at the metadata, it does not surface a version, and nothing on the website knows which build it is handing you.

One byte is enough to find out

The object metadata is served on the download response, so you can read it from outside with a range request for a single byte. Grab the redirect target first, since the presigned URL only lives for 60 seconds:

$ for p in win mac-arm64 mac-x64; do loc=$(curl -s -D- -o /dev/null "https://notifio.app/api/download/$p" \ | grep -i '^location:' | sed 's/^[Ll]ocation: //;s/\r//') echo "== $p" curl -s -r 0-0 -D- -o /dev/null "$loc" \ | grep -iE "^(content-range|last-modified|x-amz-meta-version)" done == win Content-Range: bytes 0-0/237616310 Last-Modified: Tue, 28 Jul 2026 11:35:55 GMT x-amz-meta-version: 1.0.3 == mac-arm64 Content-Range: bytes 0-0/291511009 Last-Modified: Tue, 22 Sep 2026 12:24:46 GMT x-amz-meta-version: 1.1.0 == mac-x64 Content-Range: bytes 0-0/301712899 Last-Modified: Tue, 22 Sep 2026 12:25:03 GMT x-amz-meta-version: 1.1.0 Platform Key Size Version Uploaded Windows notifio-setup.exe 237,616,310 1.0.3 28 July Mac arm64 notifio-arm64.dmg 291,511,009 1.1.0 22 September Mac x64 notifio-x64.dmg 301,712,899 1.1.0 22 September

I have written before about the two months between those dates, and the conclusion there was that nothing in the product can tell you which version you are downloading. That still holds for the product, and it is less true than I thought of the system around it. The answer has been sitting in x-amz-meta-version on every object since the first upload, written by the release script, verified by the release script, and read by nobody after that.

The reason for the split is structural rather than careless. Installers are not cross-buildable, and the script refuses rather than pretending:

fail( `Cannot build ${impossible.join(' + ')} on ${os.platform()}.\n` + ` Installers are not cross-buildable here: run this script on a ${impossible.includes('mac') ? 'Mac' : 'Windows machine'}, ` + `then use --skip-build to upload artifacts copied over from the other machine.` );

A release is therefore two machines, and a release that only happens on one of them leaves the other key untouched at whatever version it last was. The script even says so at the end of a single-platform run. It just says it in a terminal that nobody is looking at two months later.

Why HEAD does not work

The obvious way to read that metadata is a HEAD request, and it returns 403. The presigned URL is signed for a specific operation, which you can see in the query string it hands you:

...&X-Amz-Expires=60&X-Amz-SignedHeaders=host&x-amz-checksum-mode=ENABLED&x-id=GetObject

x-id=GetObject is part of the signed material, so switching the verb invalidates the signature. A range GET is still a GET, which is why one byte works where zero bytes does not. The release script does use head-object, but it does so with the R2 credentials directly rather than through a presigned link, so it is not constrained the same way.

The 60 second expiry is deliberate and documented in the route:

// Presigned URL valid for 60 seconds — enough for the browser to start the // download without permanently exposing the file.

Which is the right trade for a download button and is also why the shell loop above has to fetch a fresh redirect for each platform rather than reusing one.

One more number worth looking at

The release script requires the AWS CLI, and explains why:

fail( 'AWS CLI not found. It is used to upload files larger than R2\'s 300MB web UI limit.\n' + ... );

The x64 DMG is 301,712,899 bytes. That is 287.7 MiB, so it is under 300MB if you mean the binary kind and over it if you mean the decimal kind. Either way the biggest artifact is now sitting on the exact boundary that the dependency exists to get around, and it is only that size because each installer bundles its own Chromium. The afterPack hook already deletes the browser for the architecture that build will never run, which is the only reason it is not twice as large.

What I would change

Both fixes are small and neither is about the upload.

The filename triangle wants one shared constant, and it cannot have one, because app/ and server/ are separate packages that do not import each other. The next best thing is a test in server/ that reads app/package.json, expands ${arch} and asserts the resulting set equals the values of FILES. It is a ten-line test that converts a comment into a failure.

The version header wants a reader. The download route already talks to R2 with credentials; a HeadObjectCommand before the redirect would let the download page print the version and build date next to each button. That is a real feature for a desktop app whose update mechanism is reinstalling, and the data is already there. The only reason it is not on the page is that nobody thought to ask the object what it was.

If you want to run the range-request loop above against the live endpoints, it is three HTTP requests and three bytes, and it will tell you more about what Notifio currently ships than the download page itself will.
