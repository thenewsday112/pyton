Stripe failed payment emails: a dunning flow that recovers revenue (Node.js)

📅 Oct 31, 2026  |  Category: Business  |  Read Source →

Failed payments are the quietest kind of churn. Nobody decided to leave: a card expired, a bank flagged a renewal, a corporate card hit its limit. If nobody tells the customer, Stripe retries a few times, gives up, and the subscription ends.

Stripe will send a basic failed payment email for you (Settings → Billing → Subscriptions and emails). It's worth turning on, but it's one generic email. A short sequence that explains what happened, links straight to a page where the customer can fix it, and stops the moment they pay recovers noticeably more.

This post walks through building that flow on Stripe webhooks in Node.js: the events you need, the timing, the copy, and the edge cases that make dunning emails go wrong.

The events that matter

You need three webhook events:

Event What it tells you invoice.payment_failed A charge attempt on an invoice failed. Fires on the first attempt and on every automatic retry. invoice.paid The invoice was paid, either by a retry or by the customer. This is your "stop emailing" signal. customer.subscription.updated / customer.subscription.deleted The subscription moved to past_due, unpaid or canceled after retries ran out.

The invoice object on invoice.payment_failed carries most of what an email needs:

  • id: the invoice ID. It stays the same across every retry of that invoice, which makes it the right key for "one recovery flow per failed invoice".
  • attempt_count: 1 on the first failure, then increments with each retry.
  • next_payment_attempt: a Unix timestamp for the next automatic retry, or null when Stripe will not retry again.
  • hosted_invoice_url: Stripe's hosted page where the customer can pay this invoice with a new card.
  • amount_due and currency: for "Your $49.00 payment didn't go through".
  • customer and customer_email.

Step 1: receive and verify the webhook

Verify the signature against the raw body. Parsing JSON first breaks verification, which is the number one "why does my Stripe webhook fail" issue.

import express from "express"; import Stripe from "stripe"; const stripe = new Stripe(process.env.STRIPE_SECRET_KEY); const app = express(); app.post( "/webhooks/stripe", express.raw({ type: "application/json" }), async (req, res) => { let event; try { event = stripe.webhooks.constructEvent( req.body, req.headers["stripe-signature"], process.env.STRIPE_WEBHOOK_SECRET ); } catch (err) { return res.status(400).send(`Webhook Error: ${err.message}`); } // Acknowledge fast, do the work in a queue. await enqueue("stripe-event", { id: event.id, type: event.type, data: event.data.object }); res.json({ received: true }); } );

Two things to get right here:

  1. Return 2xx quickly. Stripe retries webhooks it considers failed (for up to three days in live mode). If you send emails inline and your email provider is slow, Stripe times out, retries, and you send the same email twice.
  2. Deduplicate by event.id. Even with fast responses, Stripe can deliver an event more than once. Store processed event IDs (a unique index is enough) and skip repeats.

Step 2: decide what to send

Here's a sequence that works for most B2B SaaS:

When Email Goal First failure (attempt_count === 1) "Your payment didn't go through" Calm, factual, one button to update the card. ~3 days later, still unpaid "Quick reminder: update your card" Shorter. Mention what they'd lose (their data, their team's access). Final retry (next_payment_attempt === null) "Last chance before your subscription is canceled" Clear deadline, same single button. After cancellation "Your subscription was canceled" How to reactivate in one click. No guilt.

The key detail: drive the flow off the first failure, not every failure. invoice.payment_failed fires on every retry. If you send an email per event, a customer on Stripe's default Smart Retries schedule (Stripe's recommended default is up to 8 tries within 2 weeks) can get eight near-identical emails. Start one flow when attempt_count === 1, and use next_payment_attempt === null to trigger the final notice.

async function handleStripeEvent({ id, type, data }) { if (await alreadyProcessed(id)) return; if (type === "invoice.payment_failed") { const invoice = data; if (invoice.attempt_count === 1) { await startDunningFlow({ invoiceId: invoice.id, email: invoice.customer_email, amount: formatMoney(invoice.amount_due, invoice.currency), payUrl: invoice.hosted_invoice_url, }); } if (invoice.next_payment_attempt === null) { await sendFinalNotice(invoice.id); } } if (type === "invoice.paid") { await stopDunningFlow(data.id); // keyed by invoice ID } await markProcessed(id); } function formatMoney(amountInCents, currency) { return new Intl.NumberFormat("en-US", { style: "currency", currency: currency.toUpperCase(), }).format(amountInCents / 100); }

(Zero-decimal currencies like JPY don't divide by 100. If you bill in them, check the currency before formatting.)

startDunningFlow should schedule the follow-ups as delayed jobs (BullMQ, Sidekiq, Cloud Tasks, whatever you use) and re-check the invoice status before each send:

async function sendReminderIfStillUnpaid(invoiceId) { const invoice = await stripe.invoices.retrieve(invoiceId); if (invoice.status !== "open") return; // paid, voided or uncollectible: stop await sendEmail("dunning-reminder", { invoice }); }

The re-check is cheap insurance. Webhooks arrive out of order sometimes, and "we already charged you, please pay" is the fastest way to get a support ticket.

Step 3: where the button should go

Your email needs one button that lets the customer fix the problem in under a minute. You have two good options:

  • hosted_invoice_url: Stripe's hosted invoice page. The customer can pay that exact invoice with a new card, no login needed. Best for the dunning emails themselves.
  • The Stripe customer portal: lets the customer replace their default payment method for future invoices too. Portal session URLs are short-lived, so don't paste one into an email. Link to a route in your app that creates a session on click:
app.get("/billing/update-card", requireLogin, async (req, res) => { const session = await stripe.billingPortal.sessions.create({ customer: req.user.stripeCustomerId, return_url: "https://app.example.com/settings/billing", }); res.redirect(session.url); });

Avoid sending people to a generic "log in to your account" page. Every extra step loses recoveries, and a customer whose card failed is not in the mood to hunt through settings.

Step 4: the copy

Dunning emails are transactional in tone even though they feel like marketing. A few things consistently help:

  • Lead with the fact, not the apology. "Your $49.00 payment for Acme Pro didn't go through" beats "Uh oh! Something went wrong."
  • Say what happens next and when. "We'll try again on November 4. If it still fails, your workspace will be paused on November 12."
  • Never blame the customer. Most failures are expired cards or bank fraud filters. "Your bank declined the charge" is accurate and neutral.
  • One button. "Update payment method". Not a menu of links.
  • Send from a human-looking address, and let replies land in a real inbox. People reply to dunning emails with "I changed jobs, can you invoice my new company?", and those are recoveries too.

A first email can be this short:

Subject: Your Acme payment didn't go through

Hi Sam,

We tried to charge $49.00 for your Acme Pro plan, but your bank declined it. This usually means the card expired or was replaced.

[Update payment method]

We'll retry automatically on November 4. Nothing changes in your account until then.

If you have questions, just reply to this email.

Edge cases that cause double (or wrong) emails

These come up in almost every dunning implementation:

  1. Two invoices fail at once. A customer with two subscriptions can have two open invoices. Key the flow by invoice ID, not by customer, or the second failure gets swallowed (or the first payment stops both flows).
  2. Customer pays between retries. Handled by invoice.paid plus the status re-check before each send.
  3. Manual invoices. Invoices with collection_method: "send_invoice" have no automatic retries, so next_payment_attempt is null from the start. Decide whether they get the same flow or a different "your invoice is overdue" email.
  4. One-off invoices. Not every failed invoice belongs to a subscription. Check billing_reason (subscription_create, subscription_cycle, subscription_update) if you only want to chase renewals.
  5. API version drift. Stripe's 2025-03-31 (basil) API moved some invoice fields, for example the subscription reference now lives under invoice.parent.subscription_details. Pin your webhook endpoint's API version and read fields that exist in it.

Measuring it

Track two numbers:

  • Recovery rate: failed invoices that end up paid ÷ failed invoices. Split it by "paid by automatic retry" and "paid after an email click". Automatic retries recover some without any email, and you want to know what the emails add.
  • Time to recovery: days from first failure to payment. If most recoveries happen after email 1, your later emails can be gentler; if they cluster at the final notice, the deadline is doing the work.

If you'd rather not maintain this

Full disclosure: I build Sequenzy, an email platform for SaaS, and this flow is one of the first things founders set up with it. You connect Stripe, and failed invoices arrive as a saas.payment_failed event carrying invoiceId, attemptCount, amountDueFormatted, hostedInvoiceUrl and willRetry. A sequence triggered on the first attempt and stopped by the matching saas.purchase handles the "one flow per invoice, stop on payment" logic above without your own queue. The Stripe integration docs show the setup.

Whether you build it yourself or not, the pattern is the same: start on the first failure, key by invoice, re-check before every send, and make the button go straight to a page where the customer can pay.

Building a BaZi Calculator That Shows Its Time Assumptions

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

A BaZi chart looks deceptively simple: four columns, eight Chinese characters. But behind those characters are several difficult engineering decisions about time, calendar boundaries, and which traditional rules are being applied.

If those assumptions stay hidden, users cannot tell whether they are looking at a calculation problem or an interpretation problem. Building a useful Four Pillars calculator means making that boundary explicit.

The eight characters are not the hardest part

The Year, Month, Day, and Hour pillars are generated from birth details. The difficult part is deciding what “the hour of birth” actually means.

Historical time zones and daylight-saving changes matter. A time entered as 23:30 may fall into a different local-hour slot after historical offsets are applied. Near some boundaries, even a few minutes can affect the chart.

That is why storing the original input and the normalized time separately is useful. It gives the application something concrete to display and makes errors reproducible.

Solar terms define more than the season

The month pillar in BaZi is tied to solar terms rather than Gregorian calendar months. The Year pillar is traditionally associated with the beginning of spring, not January 1 or the Lunar New Year date.

We therefore treat solar-term boundaries as calculated events, not cosmetic labels. The chart engine determines which side of each boundary the timestamp belongs to before interpretation begins.

True solar time should be an explicit option

True solar time adjusts civil time for longitude and the equation of time. Some BaZi practitioners use it; others do not.

There is no responsible way to silently choose one position for every user. The setting needs to remain visible, and comparisons must state whether true solar time was enabled.

Keep calculation separate from interpretation

We use a deliberately narrow boundary:

  1. Calendar and time normalization determine the pillars.
  2. Rule profiles determine the traditional relationships displayed.
  3. Generated explanations describe those facts without inventing or changing them.

That separation makes it possible to test the structural layer independently. It also prevents a language model from “fixing” a chart that the calculation layer says is correct.

Test around the edges

The most valuable tests are not examples in the middle of a month or a two-hour branch. They are cases near timezone transitions, solar-term changes, date-line crossings, and historical offsets.

A calculator earns trust by agreeing with itself under those conditions. Showing the normalized input, timezone source, solar-term boundary, and active rule profile makes that agreement inspectable.

Five things to know before you build on the USAJOBS Search API

📅 Oct 31, 2026  |  Category: Travel  |  Read Source →

USAJOBS publishes an official Search API (data.usajobs.gov/api/Search) for US federal job announcements. We built a scheduled job feed on it, and these are the details that shaped the code. Disclosure: the hosted version at the end is ours, and we charge for it.

1. Pay comes with an interval code

Each pay range comes with a RateIntervalCode: PA for per year, PH for per hour, plus PD, PW, BW and PM for daily, weekly, biweekly and monthly. To compare jobs on salary, convert everything to a yearly figure. We use 2,087 hours for a year of hourly pay (the federal standard), 260 days, 52 weeks, 26 pay periods or 12 months. Filter on the top of the range, or you'll drop hourly jobs that pay well.

2. One query stops at 10,000 results

The API won't page past 10,000 results for one query. A broad search such as "all jobs posted this month" can hit that limit without telling you. Narrow it by location, agency, occupational series or a posted-within window, and log it whenever a query reaches the limit, so a short result is never mistaken for a complete one.

3. Ask for public jobs explicitly

Many announcements are open only to current federal employees or particular groups. If your users are the general public, request WhoMayApply=Public. It's also the only option the API serves to a key that hasn't been given extra authorisation.

4. Codes need a lookup table

Schedule, appointment, service type and travel come back as codes. Map them to words (Full-time, Permanent, Competitive, Occasional travel) before anyone downstream sees them, or every consumer ends up writing their own mapping.

5. Announcements contain contact details

Rows can carry an agency contact email and phone number, and the announcement text can include more of them, sometimes with a named person. Unless your use case needs them, drop the contact fields and mask emails and phone numbers in free text. Don't store full announcement text by default.

Why a Website Is Not Indexed: A Practical Diagnostic Workflow

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

When a page is missing from search results, the fastest next step is not to change every SEO setting on the site. Pick one important URL, establish what you expect to happen, and follow the evidence from discovery through crawling, indexing, and canonical selection.

This guide uses Google Search Console and Yandex Webmaster as examples of sources of diagnostic information. Interfaces and report labels can change. Check the current guidance for each service and avoid assuming that the two search engines make identical decisions.

Start with a specific page and a clear expectation

Choose an important public URL: a service page, a category, or an article intended for search visitors. Copy the complete address, including the protocol, host, path, trailing slash, and any parameters. Confirm that it is published and that the page is intended to be public.

A page opening in your browser proves that your browser received a response. It does not prove that a search engine received the same content, added that URL to its index, or will display it for every query. Similarly, a search using the site: operator is a useful clue, not a complete inventory of indexed pages.

Inspect the exact URL in the available webmaster tools. Record the date, reported status, any stated reason, and the selected canonical URL if the service provides it. Compare the information separately for each search engine. A live availability check and a report about a previously processed version answer different questions: a successful live test is not proof that the latest version is already indexed.

If an entire site appears affected, sample different page types. When the home page, a category, a product, and a new article all fail in the same way, look for a common infrastructure or configuration change. If only one group is affected, inspect the relevant template or section.

Check the response and redirect chain

Open the page without logging in when it is supposed to be public. With a developer, inspect the HTTP response and the final address after redirects. A browser can display a friendly error template, a login page, or a placeholder even when the underlying response is not what you expect.

Use the symptom to choose the next investigation:

  • A server error or timeout: investigate availability, resource pressure, and logs.
  • A forbidden response or login requirement: confirm whether the restriction is intended and review the relevant access rules.
  • A missing or removed page: determine whether it should be restored or has a relevant replacement.
  • A redirect: check where it ends and whether the destination matches the intended page.
  • A successful response: inspect the actual content and indexing signals; status alone does not guarantee indexing.

For a hypothetical example, a URL ending in /service/ might redirect to /services/. Decide which page is supposed to be primary and inspect the final destination. Redirecting every missing page to the homepage just to avoid an error can send visitors to an unrelated destination.

Security filters may return different responses to different requests. Work with the administrator to examine evidence before changing a rule. Do not open private or staging sections simply to make a crawler pass, and do not trust a user-agent label alone as proof of a search crawler's identity.

Separate crawl restrictions from indexing instructions

The robots.txt file controls crawling for applicable user agents and paths. Check the correct host and protocol, and identify the rule affecting the target page. An old staging rule or a deployment mistake may prevent a search crawler from fetching an intended public section.

A crawl restriction is not the same as reliable access control or guaranteed removal from an index. An address may be known from other sources even if its contents cannot be fetched. Protect confidential content with appropriate authentication and authorization.

Next inspect indexing directives in the HTML and HTTP response headers. A noindex instruction may come from a template, a page-level setting, or server configuration. Find the origin of an unintended directive before changing it, and protect sections that the team deliberately keeps private.

An important interaction: if crawling is blocked, the crawler may not retrieve the page and see a noindex instruction on it. Choose a remedy based on the actual objective: make a public page eligible for indexing or restrict access to private content. Do not apply a blanket fix to both.

Investigate duplicates and canonical signals

Several URLs can represent similar content: versions with parameters, different hosts, or alternate paths. Decide which URL should be primary, then compare the redirect destination, internal links, canonical link, and any canonical information in the webmaster tool.

A canonical link expresses a preference; it does not guarantee that a search engine will select that version. Conflicting signals deserve investigation. A product page pointing to an entire category, or two distinct services pointing to the same canonical address, may reflect a template mistake. It might also be intentional, so establish the business purpose before editing.

Do not assume that every parameterized page should be excluded. Some filters or variations may serve a distinct purpose. Classify them into desired landing pages, duplicates, and operational URLs, then test changes on representative examples.

Look at discovery, sitemaps, and content

Check whether important pages are reachable through useful internal links. An isolated URL may be harder to discover. A sitemap can help communicate desired URLs, but it does not guarantee a crawl, indexing, or ranking.

Keep sitemap entries aligned with the intended public URLs. Review whether listed addresses resolve successfully, redirect unexpectedly, or include deliberately closed pages. A successful sitemap fetch is a property of the file; it is not confirmation that every listed page is indexed.

Inspect the main content. Does it answer a distinct user need? Is it available without a login when the page is intended for public search? If essential text or links depend on JavaScript, use the available inspection tools and developer diagnostics to see what a search engine can actually process in that implementation. One successful browser view does not establish identical behavior for every crawler.

Content quality is not an instant technical switch. Still, removing empty placeholders and resolving near-identical pages helps clarify the purpose of each URL for both visitors and search systems.

Work through a concrete example

Suppose a service page is public but an inspection report says the specific URL is not indexed. The requested address redirects to a second URL, while the canonical link on that page points to a third. The navigation and sitemap still use the first.

  1. Confirm the intended primary URL with the site owner.
  2. Check the final response, public access, relevant crawl rules, and indexing directives.
  3. Align redirects, canonical signals, internal links, and sitemap entries where appropriate.
  4. Test the actual published page and record exactly what changed.
  5. Recheck the same URL in each search system and use a supported recrawl or reprocessing request where appropriate.

This is an illustrative sequence, not proof that conflicting signals are always the cause. If the diagnostic tool reports a different problem, investigate that evidence first.

Keep an issue log after the fix

For each URL, record the page type, intended role, observation date, service-specific status, response and final URL, important directives, change made, and owner. Note a date for a follow-up check.

Do not promise a universal indexing deadline. Search systems may need time to discover and process changes, and submitting the same request repeatedly does not guarantee faster inclusion. If the result has not changed, verify that the deployed page is the intended version and that the original cause was actually removed.

Avoid three common mistakes: removing every restriction without understanding why it exists, treating a sitemap as an indexing command, and changing a whole site after examining one example. A small, documented sample makes it easier to identify a shared cause without exposing private sections or creating new redirect problems.

Paste failing Playwright into the agent, not into Slack

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Last week a checkout e2e failed on main. Someone screenshot the red CI job, dropped it in Slack, and three of us spent twenty minutes guessing which locator drifted. Then I pasted the raw Playwright error — stack, expected vs received, the page URL from the trace — into the agent and asked it to propose a one-file fix. Ten minutes later we had a patch and a short note on why the locator was brittle.

Failing Playwright output is dense, boring, and perfect for an agent. Slack is for decisions. Mixing those two jobs is how flaky tests stay flaky.

What the agent actually needs from a failure

A red badge and “checkout is broken” is not a prompt. Agents fix tests when you give them the same artifacts you’d open yourself:

  • The exact assertion message (expected / received / timeout)
  • The stack pointing at the test file and line
  • The page URL (or route) at failure time
  • Any trace / screenshot path if CI uploaded one
  • The command that ran (pnpm test:e2e --grep checkout)

Playwright’s default reporter already prints most of that. Copy the failure block. Don’t paraphrase it into “the submit button didn’t work.”

I keep a tiny paste template so I don’t forget pieces:

## Playwright failure (paste raw) Command: pnpm exec playwright test e2e/checkout.spec.ts --project=chromium CI job: main / e2e / #4821 <<< paste the failure block here, including Expected/Received and stack >>> Trace zip (if any): artifacts/trace-checkout.zip Goal: smallest fix in the test OR one related page object — do not rewrite the suite Out of scope: changing product behavior, deleting assertions "to make green"

That last line matters. Agents love to “fix” a red test by weakening it.

Why Slack threads make flaky tests worse

Slack is great for “is this a real regression or CI flake?” It’s bad for debugging locators:

  • Screenshots lose the selector string and timeout numbers
  • People reply with hunches (“maybe the spinner?”) before anyone reads the stack
  • The original error scrolls away; the agent never sees it
  • You get five parallel theories and zero pasted artifacts

I still post a one-liner in Slack after I have a plan: “checkout e2e: locator for pay CTA drifted after the redesign — patch in PR #…”. The debugging happens with the agent and the raw log, not in the channel.

A workflow that sticks

  1. Reproduce locally once if CI is flaky-suspicious — same project, headed if needed. If it only fails under load, say that in the prompt.
  2. Paste the failure + the test file path into the agent. Attach the relevant page-object file if the stack points there.
  3. Constrain the edit: “one test file + at most one page object; keep assertion intent; prefer getByRole over CSS.”
  4. Ask for a hypothesis first, then the patch. I want to read “the button text changed from Pay to Place order” before I accept a locator rewrite.
  5. Re-run the single test and paste the green (or still-red) output back. Don’t merge on vibes.

Example constraint I reuse:

You are fixing ONE Playwright failure. Do not expand coverage. Rules: - Prefer getByRole / getByLabel over CSS / XPath - Do not remove waits by deleting the assertion - Do not add `waitForTimeout` - If the app copy changed, update the locator and note the copy change in the PR body - If the failure looks like a real product bug, STOP and say so — do not paper over it in the test

That stop rule is the whole point. Green tests that hide broken checkout are worse than a red CI job.

What “good” agent output looks like

I reject patches that only say “updated selector.” I want:

  • Root cause in one sentence (copy change, timing, wrong frame, strict-mode dual match)
  • Diff limited to the failing path
  • Same assertion meaning (still checking the user can place an order)
  • Optional: a note if the test was asserting implementation detail (class names) and should move to role/label

If the agent rewrites three unrelated specs “while here,” I throw the patch away and tighten the prompt.

Flakes vs bugs — make the agent choose

Paste this when you’re unsure:

Classify first: A) Product regression — leave the test failing; describe what to verify in the app B) Test drift — locator/copy/timing; propose the minimal test fix C) Infra flake — suggest a stable wait (network idle / attached) without sleep Do not mix A and B in one PR.

Agents default to B because editing tests is easy. Forcing the classification catches the “we made CI green and checkout is still broken” failure mode.

Traces without dumping a novel into chat

If you have a Playwright trace, don’t paste the whole JSON. Point the agent at:

  • the failing action name from the trace UI
  • the snapshot HTML path if it’s small
  • or a short description: “click Pay → expect order confirmation; timed out waiting for #confirmation”

Better: upload the trace as a CI artifact and paste the URL + the failing step title. The agent still needs the assertion text; the trace is supporting evidence.

What I stopped doing

  • Dropping only screenshots into Slack and hoping someone “knows that page”
  • Letting the agent add waitForTimeout(2000) as a “fix”
  • Accepting suite-wide locator refactors for one red test
  • Merging “fixed flaky test” PRs with no root-cause sentence

Paste the failure. Constrain the blast radius. Make the agent classify bug vs drift. Then tell Slack what you decided — not how you got there.

CVE-2026-119207: Asymmetric Resource Consumption in pypdf Dictionary Parser

Vulnerability ID: CVE-2026-119207
CVSS Score: 7.1
Published: 2026-10-30

CVE-2026-119207 (GHSA-4vqv-7265-gm2w) is an asymmetric resource consumption and denial-of-service (DoS) vulnerability in the open-source Python PDF manipulation library pypdf. In versions prior to 6.21.3, the DictionaryObject.read_from_stream method fails to bound exception message lengths when encountering malformed, unclosed dictionary structures in strict mode. When nested dictionary parsing fails, each level catches the inner exception and raises a new PdfReadError initialized with the string representation (exc.repr()) of the caught exception. This recursive wrapping causes geometric string expansion across the call stack, enabling a minimal PDF payload of a few hundred bytes to exhaust gigabytes of heap memory and crash the host Python process.

TL;DR

Versions of pypdf prior to 6.21.3 suffer from geometric exception string expansion when parsing nested, unclosed PDF dictionaries with strict=True. A tiny crafted PDF payload can force the parser to allocate gigabytes of memory via recursive exc.repr() wrapping, resulting in an Out-Of-Memory (OOM) denial of service.

How to Tell What Claude Code and Codex Forget When They Compact a Session

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

Engineer's view. This is a process restart with a handoff note. Whatever the process wrote down or saved to disk comes back. Whatever sat only in memory is gone, and nothing errors. A coding agent's memory is its conversation, so values it read but never wrote down vanish, and it must read them again.

TL;DR. A compacted agent keeps your instructions and its own edits, but loses most of what it only read. Whether a fact survives depends on how it entered the session, so you can predict the loss and tell the summary what to keep.

Explain Like I'm 5

You are building a huge model castle, and your table is full. So you ask a friend to write a
short note about the castle, then you clear the table.

The note says what you were told to build and which towers you finished. It does not list every
piece you looked at in the box. Those are still in the box, so you can look again.

But some pieces you borrowed for a minute, and they went back to a friend's house. If the note
does not mention them, you will not remember them, and you cannot go look.

So before you clear the table, tell your friend what to put in the note.

The Problem

You have shipped this bug already, in a system with no model in it.

Your service held a session cache in process memory. A deploy restarted it. The health check went
green and the error rate stayed flat. Then users started logging in again, because the sessions
never reached disk. Nothing crashed. The process simply came back without the state that had only
lived in memory.

A coding agent has the same split, and it restarts in the middle of your work.

Its working memory is the conversation. When that fills, the agent runs compaction: it
replaces the conversation with a summary and carries on. In my test session, 78,642 tokens became
2,632. That is 97% gone in about twenty seconds, and the session looks healthy afterward.

The agent then keeps working from the note. If a detail is missing, you see no error. You only see
it read the same file twice, or ask something you already answered. Worse, the detail may have
come from a test run or a web page that no longer exists.

You could treat this as bad luck. It is not. What survives follows a rule.

The fix: know which lane each fact is in, tell the summary what to keep, and write anything you
cannot regenerate to a file before compaction runs.

The Fix: Sort Facts by How They Entered the Session

Compaction is a rebuild, not a shortening. The new context comes from three lanes.

What reloads from disk?

Claude Code reloads the root CLAUDE.md, auto memory and the plan file. It also re-reads up to
five recent files, each under 5,000 tokens. Rules with paths: and nested CLAUDE.md files are
different: they entered as messages, so they get summarized. They load again only when the agent
touches a matching file.

What does a budget keep?

Codex's open-source compaction path keeps your recent messages word for word, up to 20,000 tokens,
walking newest to oldest. It adds a summary and re-injects its starting context. Older messages
depend on the summary.

Which facts does the summary drop?

I tested this rather than assume it. I planted facts in real Claude Code sessions, compacted them,
then asked from memory with tools off. Each of three sessions read 25 small config files.

Every instruction survived, and so did all ten edited files, even after a second compaction. The
agent said so plainly when a value was gone, even when told never to answer "unknown".

The summary kept what mattered to the work so far. In an earlier run, the last task counted timeouts
over 5000. Of six values I probed, only the two timeouts over 5000 survived.

What This Means for You

When this matters. You run long sessions in Claude Code, Codex or any agent that summarizes its
history. It matters most when the agent reads something it cannot read again: a failed test run, a
production log, a web page, or the output of a command that changes state.

How it affects you. A file on disk costs you one more read. The agent gets it back and you pay
tokens. A one-time output costs more, because the evidence is gone. The agent will then rerun the
command, or reason from a vague line in the note. Long sessions may lose more than my small test
did. Factory ran probe questions after compression on 36,611 production messages. All three methods
scored worst on tracking files, at 2.19 to 2.45 out of 5, even though each kept instructions well.

What to do about it. Start with no setup. Before you compact, name what matters:

/compact Keep the exact failing test names, error strings and ids.

A line like that, naming the values I needed, took my test from 0 to 36 of 36.

Next, watch for the moment that hurts. When the agent reads something you cannot regenerate, ask it
to save the facts to a notes file. A file sits in the disk lane.

Then fix the repeated cases. Move a rule that must always hold into your root rules file. Add a hook
that restores your working state after every compaction. Finally, audit a real session to see your
own numbers.

Implementing It

The change.

Four jobs, and one person may do all of them.

Job 1, whoever drives the session. Save anything you cannot regenerate, then compact at a task
boundary with a focus. Codex takes a compaction prompt in its config, so the same habit can be set
once there. In ~/.codex/config.toml:

compact_prompt = "Summarize this session. Keep exact error strings, ids, file paths and test names."

Job 2, whoever owns the repo's agent setup. Check which lane your rules are in. A rule with
paths: enters as a message, so its survival is up to the summary until the agent touches a
matching file again. My short test kept one, but the docs warn it can go. If it must hold across
compaction, move it to the root file. Then add a section the summarizer reads, in CLAUDE.md:

# Compact Instructions Keep exact error strings, failing test names, ids and every file edited.

Add a hook for state that changes. A SessionStart hook with the compact matcher runs after
every compaction, and its output joins the new context. In .claude/settings.json:

{ "hooks": { "SessionStart": [ { "matcher": "compact", "hooks": [ { "type": "command", "command": "git status --short; cat notes/session.md 2>/dev/null" } ] } ] } }

Job 3, whoever builds their own agent. Do not trust a summary with the file list. Keep it as data
in your loop, and put it back after you summarize.

def rebuild(history, pinned, ledger, summarize, keep_tokens=20_000): recent = newest_user_messages(history, keep_tokens) note = summarize(history, focus="exact errors, ids, decisions") edited = "Files edited: " + ", ".join(sorted(ledger.edited)) return [*pinned, *recent, edited, note]

Job 4, whoever wants the numbers. code_example.py needs no model. It reads a session transcript,
finds each compaction, and checks which identifiers reached the summary, grouped by lane. Run it on
one of your own sessions:

python3 code_example.py ~/.claude/projects/<project>/<session>.jsonl

An identifier here means an exact string such as a port, path or error code. On 40 compactions
from my own sessions, 4% of the identifiers the agent only read reached the summary, against 19% of those the agent or I wrote. An exact-string match undercounts paraphrase, so
trust the gap more than the percentages.

How you know it worked.

Probe it. Fork a session right after a compaction, turn tools off, and ask for five facts you need.
Offer "UNKNOWN" as an answer so a miss is visible. In Claude Code:

claude -p --resume "$SESSION" --fork-session --tools "" \ "From memory, no tools. Which files did you edit? What was the exact error? Reply UNKNOWN if unsure."

Before your change, count the misses. After it, the same probe should return your focus items
exactly. Also watch re-reads: the same file read twice right after a compaction means the note
missed it.

When Managing Compaction Is the Wrong Tool

When the task is short. A session that never fills its context never compacts. Spending effort on a
hook then buys nothing.

When the facts are on disk and cheap to read. Losing a value from a config file costs one more
read. Asking the summary to keep every value makes the note longer, and a long note costs tokens on
every later turn. Keep what is expensive to get back.

When you should start over. If the next task is unrelated, /clear is better than any summary. Old
context crowds the new work, however well it was compressed.

When the work belongs elsewhere. Send large research to a subagent, so the reads never enter your
main conversation at all.

My test has limits too. It used small synthetic sessions on one model, and I did not run the Codex
side. Run the probe on your own work before you trust these numbers.

Three questions before you add a hook:

  • Which fact, if lost, could the agent not get back?
  • Does that fact reach the model through a file, or only through a message?
  • Would a probe after compaction return it exactly?

Glossary

  • compaction — replacing a conversation with a shorter summary so the agent can keep working.
  • lane — the route a fact takes through compaction: reloaded, kept by budget, or summarized.
  • probe — a question asked after compaction to test whether a fact survived.
  • focus — an instruction telling the summary what to keep, as in /compact with text after it.
  • identifier — an exact string such as a port, id, file path or error code.

15 İşlemde 15 Başarı: Kağıt Üzerinde Test Yaptım ve Sonucu Hüsran Oldu

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

Olay nasıl başladı

Borsa verileriyle uğraşırken kendimi bir anda mükemmel bir strateji bulmuş gibi hissettim. Python kullanarak geçmiş veriler üzerinde bir tarama yaptım ve kendi yazdığım basit bir algoritmayı çalıştırdım. Elimdeki veriler bist üzerinden aldığım kısa vadeli hareketlerdi. Algoritmam o kadar güzel çalışıyordu ki kendi kendime neden daha önce bunu yapmadım diye sordum. Tam 9 saat boyunca kağıt üzerinde test yaptım. Bu süreç içinde tam 15 işlem gerçekleştirdim. İşin ilginç yanı şu ki 15 işlemin 15 tanesi de artıda kapandı. Toplam kazanç küçüktü ama tutarlılık beni resmen büyülemişti. Sanki para basan bir makine yapmıştım. Kağıt üzerinde her şey kusursuz görünüyordu. Hiç zarar etmeden günü kapatmak insana büyük bir özgüven veriyor. Ancak bu durumun sadece bir hayal olduğunu anlamam uzun sürmedi. Canlı veriye geçtiğim anda işler tamamen değişti. Kağıt üzerindeki o büyülü başarı bir anda toz olup gitti. Nerede hata yaptığımı anlamak için verileri tekrar incelemeye başladım. Meğerki o 9 saatlik test sürecinde kendimi kandırmışım. Geriye dönük testin ne kadar tehlikeli olabileceğini o an anladım. Başarılı gibi görünen stratejim aslında sadece veriyi doğru okuyamadığım için öyle görünüyormuş.

Bu nerede karşına çıkar

Bu problem genelde trading stratejileri geliştiren herkesin karşısına çıkar. Veri analizi yaparken veya bir ajan yazarken geçmiş verileri kullanmak çok caziptir. Çünkü elinizde bitmiş bir olaylar zinciri vardır ve siz bu zinciri istediğiniz gibi bükebilirsiniz. Özellikle bist gibi piyasalarda yüksek frekanslı veriyle uğraşırken bu tuzağa düşmek çok kolaydır. Bir mumun kapanışını beklemek yerine o mumun içindeki veriyi sanki mum kapanmış gibi kullanmaya başlarsınız. Bu durum sadece borsa verilerinde değil aslında zaman serisi analizi yapan her alanda karşınıza çıkabilir. Bir modelin eğitim verisiyle test verisi birbirine karıştığında veya geleceğe ait bilgi geçmiş verinin içine sızdığında benzer sonuçlar alırsınız. Kod yazarken her şeyin yolunda gittiğini sanırsınız ancak gerçek hayatta sistem hiçbir şey tahmin edemez hale gelir. Ben de tam olarak bu noktada takıldım. Kendi yazdığım ajan modeli geçmişin güvenli limanında harikalar yaratıyordu ama piyasanın belirsizliğine çıktığı an savunmasız kaldı. Bu durum sadece benim başıma gelmiyor. Profesyonel traderlar bile bazen bu hatayı yaparak büyük kayıver veriyor. Veriyle uğraşırken her zaman tetikte olmanız gerekiyor.

Kök neden

Asıl sorun geleceğe sızan veri meselesi. Bir mumun kapanış değerini o mum kapanmadan kullanırsan strateji geleceği bilir hale gelir. Benim kodumda yaptığım hata tam olarak buydu. Kod şu şekildeydi:

def strateji_kontrol(mum_verisi): if mum_verisi.kapanis > mum_verisi.acilis: return alim_yap return bekle

Bu küçük kod parçası mumun kapanış değerini o anki veri içinde okuyor. Aslında mum henüz kapanmamışken ben kapanış fiyatını biliyormuşum gibi işlem yaptırıyordum. Bu durum algoritmanın geleceği görmesini sağlıyor. Tabii ki geriye dönük testte her şey mükemmel görünür. Çünkü algoritma aslında o fiyat seviyesine gelindiğinde ne olacağını zaten biliyor. Bu bir analiz değil sadece veriyi kopyalamak oluyor. Geleceğe sızan veri, stratejinizin performansını yapay bir şekilde yükseltir. Siz de bu yapay yükselişe kanıp canlı piyasaya girersiniz. Ancak canlı piyasada mum kapanmadan kapanış fiyatını bilme şansınız yok. Bu yüzden stratejiniz anında başarısız olur. Kök neden bu kadar basit ama bir o kadar da yıkıcı. Veriyle oynarken zaman akışını bozmamak gerekir. Her adımda sadece o ana kadar olan bilgiyi kullanmalısınız. Geleceğe sızan veri, testinizin güvenilirliğini tamamen yok eder. Bu yüzden geriye dönük testin güzel görünmesi stratejinin iyi olduğunu değil, testin çok kolay olduğunu gösterir.

Çözüm

Çözüm için yaklaşımımı tamamen değiştirdim. Önce ileriye dönük kağıt testi yapmaya karar verdim. Yani sistemi çalıştırıp piyasa verisini gerçek zamanlı olarak izledim ama gerçek para kullanmadım. Bu yöntem geleceğe sızan veriyi tamamen ortadan kaldırıyor. Çünkü sistem sadece o anki veriyi görüyor. Ardından küçük bir tutarla canlıya geçtim. Küçük tutar dedim çünkü kaybetme ihtimalini göze alarak sistemi test etmem gerekiyordu. Kademeli büyütme ise en sağlıklı yol oldu. Her aşamada aynı ölçümleri tekrar aldım. Başarıyı sadece kağıt üzerindeki sayılarda değil, canlı piyasadaki tepkilerde aradım. Kodumu şu şekilde güncelledim:

def kontrollu_strateji(gecmis_veriler): bitmis_mumlar = gecmis_veriler[:-1] if bitmis_mumlar[-1].kapanis > bitmis_mumlar[-1].acilis: return alim_yap

Bu kod ile sadece kapanmış olan mumlara bakarak karar veriyorum. Geleceğe dair hiçbir veri içermiyor. Bu şekilde test ettiğimde kağıt üzerindeki o 15te 15 başarısı yerini daha gerçekçi sonuçlara bıraktı. Bazen zarar ettim ama en azından sistemin gerçekten nasıl çalıştığını öğrendim. Kademeli büyütme sayesinde riskimi kontrol altında tuttum. Her aşamada verileri kaydedip bir önceki testle kıyasladım. Böylece stratejimin gerçekten çalışıp çalışmadığını anladım. Çözüm sadece kod değil, aynı zamanda disiplinli bir test süreciydi.

[[GÖRSEL2]]

Yolda çıkan hatalar

Bu süreçte çok fazla hata yaptım. En büyük hatam acele etmekti. Kağıt üzerindeki ilk test sonuçlarını görünce hemen zengin olacağımı düşündüm. Canlıya geçerken sistemi yeterince stres testine sokmadım. Piyasanın ani hareketlerinde kodumun nasıl tepki vereceğini hiç düşünmedim. Bir başka hata ise veri gecikmesi oldu. Kağıt üzerinde test ederken verinin anlık geldiğini varsaymıştım ama canlı piyasada veri gelişi bazen gecikiyor. Bu gecikme stratejimin yanlış zamanda işlem yapmasına neden oldu. Hatalarımı gidermek için her işlemi günlük olarak not ettim. Hangi işlem neden başarılı oldu veya neden başarısız oldu diye tek tek baktım. Kodumda yaptığım hataları ayıklamak için bol bol log dosyası tuttum. Loglar sayesinde nerede yanlış karar verdiğimi görebildim. Bir hata daha yaptım: sadece tek bir varlık üzerinde test yaptım. Bu da stratejimin sadece o varlığa özel olduğunu gösterdi. Farklı varlıklarda denediğimde stratejimin hiç de o kadar iyi olmadığını gördüm. Tüm bu hatalar bana testin sadece sayılardan ibaret olmadığını, sistemin her koşulda dayanıklı olması gerektiğini öğretti. Hatalarımı kabullenmek ve onlardan ders çıkarmak süreci daha sağlıklı hale getirdi.

Alternatifler

Alternatif olarak farklı kütüphaneler kullanabilirdim ama ben kendi basit yapımı tercih ettim. Başka insanlar daha karmaşık makine öğrenmesi modelleri kullanıyor. EU KIDS Act Proposal Sets New Age and Safety Rules for Online Platforms

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

The European Commission has proposed the EU KIDS Act, a Regulation that would establish EU-wide age rules and safety-by-design obligations for online platforms and related services used by children and teenagers. Published on September 17, 2026, the proposal would affect how social platforms, apps, online games, app stores and AI companions verify age, configure feeds and interactions, and handle data relating to minors.

The central shift is clear: platforms would need to demonstrate that services are age-appropriate and safe by design, rather than placing most responsibility on children, parents or regulators after harm occurs. The Commission's official EU KIDS Act announcement presents the proposal as part of a broader effort to harmonize child-safety rules across the EU and avoid differing national requirements.

For companies building services that may attract minors, the proposal is not simply an age-gate issue. It would place product design, moderation, data practices and parental controls closer to the center of compliance planning. The Act remains a proposal, and the Commission's public consultation is open until December 3, 2026.

What the EU KIDS Act would change

The proposal sets out age-based rules for social media accounts. Children under 13 would be prohibited from holding accounts. Users aged 13 and 14 could use guardian-assisted accounts, subject to strict controls. From age 15, users could have autonomous accounts only on services considered safe by design.

Age group Proposed social media account rule Key condition Under 13 Accounts prohibited No social media account access 13 to 14 Guardian-assisted accounts Daily time limit and parental approval of contacts 15 and over Autonomous accounts permitted Service must be safe by design

The Act would also reverse the practical burden of proof for platforms. Instead of relying chiefly on users or authorities to identify unsafe experiences, providers would have to show that their service is appropriate for minors. Very Large Online Platforms, defined in the proposal as platforms with 45 million or more monthly users, would face independent audits.

Age assurance is a core implementation issue. The Commission proposes certified age checks that use privacy-preserving approaches, including zero-knowledge techniques. The package also envisages a free EU age-verification option and eventual use of the European Digital Identity Wallet. These mechanisms matter because platforms would need to establish age and, where relevant, guardianship without unnecessarily collecting or retaining sensitive personal information.

Safety-by-design becomes a product requirement

The EU KIDS Act proposal reaches beyond account creation. It would require platforms, apps and AI companions to build safer defaults into feeds, interactions and feature design. The proposal specifically targets addictive design patterns, including endless autoplay, intrusive notifications, streaks and rewards tied to engagement.

For teams responsible for digital products, the most consequential changes would likely include:

  • Feed and notification redesign to avoid prohibited engagement mechanisms.
  • Safer default settings rather than expecting younger users to locate and enable protections.
  • Limited profiling of minors and clearer user controls over relevant settings.
  • Contact and interaction safeguards, including parental approval of contacts for guardian-assisted accounts.
  • Age-rating and verification integration in online games and app stores.
  • Pre-launch risk testing for AI companions, alongside restrictions on default activation and coercive interactions involving minors.

The proposal's treatment of AI chatbots and AI companions is particularly notable. It recognizes that conversational systems can create risks distinct from traditional social feeds. Services used by minors would need safeguards designed to prevent coercive interactions, and providers would need to test risks before launch. The proposal would integrate with existing EU frameworks, including the Digital Services Act and the AI Act, rather than operate as an isolated child-safety regime.

What compliance could mean for smaller platform teams

The research does not provide cost estimates, so businesses should be wary of treating any single budget figure as definitive. However, the proposal points to several likely cost and operational drivers: integrating certified age checks, adapting account flows, revising recommendation and notification systems, building parental controls, updating data practices, and testing products for risks to minors.

Those changes may be especially material for a smaller company that has relied on standard analytics, third-party identity tools or engagement-focused product patterns. A business operating an app, game, community or AI experience should first determine whether minors can access it in the EU, whether the service is designed to attract them, and which product features create contact, profiling or engagement risks.

A practical early review can focus on four questions:

  1. Who can access the service? Map current age rules, onboarding flows and the ability to distinguish a guardian-assisted account from an autonomous one.
  2. Which features shape behaviour? Review autoplay, notifications, streaks, rewards, recommendations, direct messaging and contact discovery.
  3. What data is used for younger audiences? Identify profiling, analytics and data flows connected to minors, then assess whether they can be limited or redesigned.
  4. How would safeguards be tested? Document risk testing for AI companions and other features that can influence or contact younger users.

The proposal's use of the DSA enforcement framework adds weight to these preparations. The Commission would directly supervise the largest platforms, and non-compliance could lead to fines of up to 6% of worldwide turnover. Smaller services may not face the same direct supervision model, but the proposed safety-by-design duties would still make early product assessment valuable.

For businesses considering AI features, age assurance and safe interaction design should not be treated as a late legal review. They influence the choice of tools, the information an AI system can access, default user settings and the testing required before a feature reaches younger users.

Frequently Asked Questions

What is the EU KIDS Act?

The EU KIDS Act is a European Commission proposal for a Regulation intended to strengthen online safety for minors through EU-wide age rules, age verification and safety-by-design obligations for platforms and related services.

Would the EU KIDS Act ban social media for children under 13?

The proposal would prohibit social media accounts for children under 13. It would allow guardian-assisted accounts for users aged 13 and 14, while autonomous accounts from age 15 would be limited to services considered safe by design.

What product features would the proposal restrict?

The proposal would prohibit addictive designs such as endless autoplay, intrusive notifications, streaks and rewards for engagement. It would also require safer defaults, limited profiling and explicit user controls.

How would the proposal affect AI companions used by minors?

AI chatbots and AI companions used by minors would face restrictions on default activation, safeguards against coercive interactions and pre-launch risk testing under the proposal.

When could the EU KIDS Act take effect?

The European Commission has published a formal proposal, not a final Regulation. Public consultation on the proposal is open until December 3, 2026, and the supplied material does not provide a final adoption or application date.

Conclusion

The EU KIDS Act proposal would make child safety a more direct product-design obligation for online services operating in the EU. Its proposed age rules, privacy-preserving verification and restrictions on engagement features signal that platforms should begin examining how minors access and experience their products while the legislative process continues.

By: Isak Möller

Marco Guida has been assigned the Milan-Inter game this evening, set to officiate his 44th game involving the Rossoneri. 

Emotions will undoubtedly be running high at San Siro this evening. Before the game, Milan will induct Ricky Kaka into the Hall of Fame, which will be a great moment for him and the fans present. Then, the Rossoneri will have to get a win to avoid dropping too far behind.

In short, it’s a game that means a lot in the red and black parts of the city. Gerry Cardinale stressed his desire to come out on top tonight and most likely, there will be some tough moments for the referee to handle. Let’s just hope there is no controversy on that front.

Positive record, besides the kick

AIA have assigned Marco Guida to this game, which makes sense considering how experienced the 45-year-old referee is. If we look at his record with Italian teams, Milan are actually the side that he has officiated the most, reaching 43 games so far.

Milan have won 20, drawn 11 and lost 12 with Guida as the referee, receiving ten penalties and nine red cards across the 43 games. A pretty good record, especially when you consider that Guida has often been assigned to high-profile games in the last few years.

It will be Guida’s first Milan game of the season, but in 2025-26, he officiated Juventus-Milan (0-0), Milan-Roma (1-0), Lazio-Milan (1-0), Como-Milan (1-3), Lazio-Milan (1-0), Milan-Cagliari (1-2). The last obviously stands out as a really bad one, but that was the Rossoneri’s own doing.

There was a little bit of controversy last season, more specifically in the win against Roma, as Guida kicked Alexis Saelemaekers after the Giallorossi missed a penalty. The incident was quickly forgotten but at the time, it angered Milan a lot.
